#### F03 附注：域存储增强方案（本地文件权威版）

**约束与难点**——为什么不迁外部存储，以及不迁也要解决什么：

域校验在请求热路径上（每轮对话入口都要过 `DOMAIN_NOT_CALLABLE` 一关），一旦域存储依赖 DB/配置中心，该组件故障就被放大成全局不可用；而服务端的定位是轻量自部署，8 份落盘配置（domains.json 就在其中）零外部依赖是既有哲学，域存储是其中最不能破的一处。但纯单文件有三个真实问题：**损坏即丢全部人工域**（实测 `DomainStore.load()`：读失败按空配置继续跑 + `assertWritable()` 禁止覆盖写——有止损、无恢复，缺的是自动回退到上一个好版本）；**无版本无回滚**（`save()` 全覆盖写，误删域触发级联清理后不可逆）；**多实例下各节点本地文件互相漂移**（F13 多实例的前置依赖）。

**决策**——权威仍在本地文件，补三样东西：

1. **形态**：`domains.json` 保持权威快照（存量部署零迁移），文件内增加单调递增 `version` 字段；同目录新增 `domains-history/v<N>.json` 历史版本库，每次变更落一份快照，限额滚动（保留最近 100 份或 50MB，超出删最旧）。
2. **损坏恢复三级**：当前文件读损坏 → 自动回退最近一个有效历史快照（WARN 日志 + 审计事件，服务不中断）；全部快照无效 → 拒绝启动（域是安全边界，此处 fail-closed，不放行）；写入侧继续用 `AtomicFiles` 原子落盘，写坏不影响权威文件。
3. **回滚即变更**：管控台选历史版本回滚时，把该快照原子写为权威文件并 `version+1`——回滚是一次普通的新变更，不是时间倒流，避免出现比"当前"还旧的幽灵版本被再次选中。
4. **多实例传播（不引新存储环境）**：复用既有强依赖 Redis 做**版本信号通道**——写节点变更后 `version+1` 并向 `domainplane:domain:version` 频道 publish；其他节点订阅/定期比对，落后则从写节点 HTTP 拉取权威文件。Redis 不可用时：单机场景无影响（本就没有多实例问题），多实例场景各节点按本地文件继续服务（已知可能陈旧，日志标注版本落后）。**本地文件是唯一权威存储，Redis 只传版本信号，不存域数据**。
5. **乐观并发**：管控台域变更接口携带 `baseVersion`，服务端校验当前版本匹配才接受，否则返回 `409`（段位落 40xxx 入参段）——多实例下杜绝后写覆盖先写，且不需要引入 leader 选举。
6. **删除语义：软删三阶段**。已核实现有删除链路（`AdminDomainController#delete`）：级联范围比预想的更全（Redis 记忆/检查点/归档/倒排索引/滚动摘要 → 知识索引+切片预览+检索器缓存 → 提示词/模型绑定/MCP 绑定/工具派生记录 → 删域+`domains.json` 覆盖写），且**已有"停掉在飞会话再删"机制**——删域前 `cancellationRegistry.runningKeys()` 找出该域链上在跑的会话，`requestStopAndAwait` 请求停止并等待标记释放，停不掉（卡在长耗时工具）就抛 `ORCHESTRATION_FAILED` 拒绝删除。所以软删不是推翻现有机制，而是补它盖不住的三个缺口：
   - **缺口一 · INTERRUPT 挂起会话无收尾**：`runningKeys()` 只含"执行中"的轮次，待人工审批的挂起会话不在其列——删域后其检查点被清，`resume` 直接 `SESSION_NOT_FOUND`，审批悬案（待批准的破坏性工具）静默蒸发，审批人再无入口批准或拒绝。
   - **缺口二 · 长耗时工具卡死 = 删除永远失败**：停不掉就抛错，运维每次重试都要再等一轮超时，死结无解。
   - **缺口三 · 误删不可逆**：无版本无回滚（见难点）。

   软删三阶段：
   - **阶段一 · 删除请求 = 软删**：域置 `deletedAt` 标记，**不移出注册表、不触发任何级联清理、不改 `isCallable`**（结构判据保持纯净：已登记 ∧ 显式可调用 ∧ 叶子，与 `DomainRegistry.isCallable` 注释口径一致）；拒绝新开轮靠一道**独立于结构判据的生命周期闸门**——`chat()` 在 `checkDomain` 结构校验通过后查 `pendingDelete`，命中即拒（`DOMAIN_PENDING_DELETE`，不静默回落默认域）；**这道闸门只挂 chat，resume 不挂**（原因见下方坑位对入口守卫的核对结论）；管控台可**撤销删除**（清除标记即恢复，也是一次 `version+1` 的普通变更，天然进历史版本库）。
   - **阶段二 · 宽限期**（默认 24h，与检查点 TTL 对齐，可配置；置 0 = 维持现有立即删语义）：软删期间域**完整留在注册表内**（可调用标记与四维绑定原样不动），`INTERRUPT` 挂起的会话允许 `resume` 收尾——入口闸门不拦 resume，其余既有闸门天然够用：域在注册表内 → `knownDomains` 通过；无检查点 → 既有拒绝路径；resume 从检查点恢复、**不重跑装配**（用冻结的最后一份有效装配完成审批——批准或拒绝都行，让悬案落地）；工具复核走 `isToolVisible → visibleIn(domain)`，与可调用性无关，软删不误伤。在飞的轮次不受影响（见下方坑位对"轮内解析"的修正说明）；管控台展示「该域 N 个活跃会话，X 后彻底删除」。
   - **阶段三 · 宽限期到，硬删**：跑既有级联清理 + `runningKeys` 停会话检查照旧；变化点是**强杀合法化**——宽限期已给足（默认 24h：新开轮早已被拒、悬案早已催办），仍停不掉的会话不再整体拒绝删除，可强杀后清理（fail-closed 的判据从"删不掉"改为"宽限期已支付代价，不再无限等待"——死结由此解开）；运维也可在宽限期内手动强制（force）。
   - **强杀的机械代价（不是免费午餐）**：running 标记在 `finally` 里释放（记忆/检查点写完之后），卡在长耗时工具里的会话永远到不了 `finally`——这正是现有 `requestStopAndAwait` 超时即拒删的成因。强杀 = 不等标记释放直接跑级联清理，容忍卡死线程最终返回时向已删域写孤儿键（记忆/检查点）。缓解：域已出注册表，这些键没有消费方（resume 会被 `DOMAIN_NOT_FOUND` 拦在门外），检查点另有 TTL 自然过期；必要时加兜底任务按 `deletedAt` 扫描回收。
   - 全流程（软删/撤销/硬删/强杀）记审计。

**代价与坑**：

- **回滚是有损操作**：被回滚掉的时间里创建的域连同其提示词/工具绑定一起消失（级联语义），管控台回滚前必须展示 diff 与影响面（将新增/删除哪些域、波及哪些绑定），不能一个"确定"按钮了事。
- **版本号不能取系统时钟**：多节点时钟漂移会让版本比较失效，单调计数器在本地用 `max(history)+1`，多实例下用 Redis `INCR` 分配。
- **历史版本库是可重建数据**，按项目"派生数据可重建"口径对待，限额滚动即可，不做 TTL 精细管理；但**回滚操作本身按有损数据对待**，必须留审计。
- **与 P2「域变更事件化」的重合**：本方案的 Redis 版本信号通道提前实现了事件化的基础设施（发布/订阅），P2 剩余的"缓存失效/审计/索引联动"消费端仍待排期——即信号先通车，消费者后上。
- **文件权限**：`domains.json` 与 `domains-history/` 收紧为属主 600，同目录 `accounts.json` 已有先例，不新增例外。
- **排期耦合**：本方案是 F13 多实例的前置（多实例要求域配置一致），建议与 F13 绑在同一波施工，单独提前做的收益有限。
- **软删把"删除"从瞬时操作变成跨 24h 的状态机**：管控台删除确认的语义要改（确认 = 进入宽限期倒计时，不是"删完了"），且要处理宽限期内再次删除/撤销的竞态；`deletedAt` 是声明存意图，闸门读取时计算——**软删不改结构判据（`isCallable` 保持纯净），它是一道独立的生命周期闸门**，"派生值不进存储"仍然成立。
- **入口守卫坑（第二次核对新发现，第一轮漏掉）**：`resume()` 与 `chat()` **共用同一道 `checkDomain`**（`AgentOrchestrationService:1601` 与 `:800` 两处入口），唯一判据源是 `isCallableDomain → DomainRegistry.isCallable`。因此**不能把 `!pendingDelete` 并进 `isCallable`**——那样阶段二"允许 resume 收尾"会被自己的入口闸门当场拦死（`DOMAIN_NOT_CALLABLE`），且新开轮错误码从计划的 `DOMAIN_PENDING_DELETE` 退化为 `DOMAIN_NOT_CALLABLE`，"不存在/已软删/删除受阻"三者区分不成立。`isCallable` 的消费方也不止入口：公开 API `/api/agent/domains`（`DomainController:48`）、管控台域列表（`AdminController:679`）、删除返回体（`AdminDomainController:335`）、启动日志（`DomainConfiguration`）、12 处测试断言（`DomainSemanticsTest`）都会跟着变味——结构语义被生命周期状态污染。正解即阶段一的双轨：结构判据不动，生命周期闸门只挂 chat。展示侧（客户端可选域清单、管控台下拉）过滤 pendingDelete 域是**展示层**的事，不能靠改判据实现。
- **软删方案的有效性依赖一条实测边界，已核实**：`agentNode` 每次迭代按**本轮冻结的 `StreamContext.domainId`** 重读模型解析与工具路由（源码注释称"执行单元内取一次，与域、提示词同一条冻结规则"）——不是"开轮解析一次、轮内不读"。因此软删期间域**必须留在注册表内且装配解析所需的一切原样保留**（可调用标记、四维绑定都不动，只加生命周期标记），轮内解析才不会炸；一旦软删就把域移出注册表，在飞会话的下一次 agent 迭代立刻失败。这是本方案与现有停会话机制的分工线：软删管"授权撤销但解析不炸"，硬删前的 `runningKeys` 检查管"物理移除前先停飞"。
- **错误码调整**：新增 `DOMAIN_PENDING_DELETE`（软删域**新开轮**被拒——只出现在 chat 入口，宽限期内的 resume 不挂这道闸门）；`DOMAIN_DELETE_BLOCKED` 场景收窄为"硬删清理已启动后拒绝撤销"（清理进行中不可逆，撤销来晚了一步，竞态拒绝）；宽限期置 0 的兼容路径保留现有 `ORCHESTRATION_FAILED`（停不掉即拒删）。`DOMAIN_NOT_CALLABLE` 与上述几者的区别要在文案里说清（结构上不能当入口 / 已软删待删 / 删除竞态是三种运维动作，不是一回事）——且注意软删域在结构上**仍是**可调用单元，这套区分依赖阶段一"不改 `isCallable`"的决策才成立。

#### F04 附注：存储与召回是一套契约的两侧

**约束与难点**——为什么记忆/检查点/每轮召回必须放在一个部分里看：

三者是一条链上的三件事：**存什么**（记忆/归档/检查点）、**每轮召回什么**（装配/检索/按需取回）、以及两侧之间的**契约**。拆开看会漏掉最核心的一条：**防上下文爆炸与"原始记忆不主动删除"（用户硬约束）是一对矛盾，解法是两侧解耦**——防爆只作用于召回侧（每轮给模型看多少），存储侧只增不减（用户以为还记得的就必须还在）。`DualConstraintChatMemory` 类注释原话："不会为了塞下新消息而丢弃最旧的，静默丢历史会让用户'以为还记得'"；M2 起封顶语义已移除，`capacityFor` 只作自检——上限约束"存了多少"，约束不了"这轮给模型看多少"。

第二个难点是**大文件的三种形态去路完全不同，不能一个机制套所有**：媒体（图/音/视）走暂存区+引用名；文档根本不经对话消息（只能管控台上传 → 分块 → ES，聊天消息只收 TEXT/IMAGE/AUDIO/VIDEO）；工具结果只进当轮不进记忆。把"大文件做成单文件、索引进记忆"会同时破坏这三条链路——文档的检索索引在 ES、媒体的取回索引在归档（只记引用名不记字节）、记忆里唯一的"索引物"是纯文本模型路径下那条 seeImage 提示文本。

第三个难点是**检查点与 F03 软删的时钟耦合**：两边都是 24h——检查点过期 = resume 悬案蒸发，宽限期到 = 软删域硬删，改一个必须改另一个。

**决策**——一套契约，两侧分工：

1. **存储侧三层，只有派生数据可删**：记忆（消息粒度、永久、只增不减；RPUSH 增量追加，回滚只剪尾部）、归档（轮粒度、全流程、只增不改写，闭轮原位 LSET）、检查点（图执行态、24h TTL）。派生数据才允许 TTL 自然回收：倒排索引 30 天（过期降级子串扫描，归档永久所以能力不丢只是变慢）、媒体暂存 30 分钟 + 活动续期（续期集合 = 归档近况窗口内带引用名的附件，滑出窗口不续）。摘要按**档案级**对待——有损压缩，过期后重放归档也复原不出同一份措辞。
2. **召回侧每轮固定五段**：系统提示（不进预算）+ 摘要段（≤2000）+ 相关轮卡片（≤5 张×80 token，来自倒排索引）+ 近况窗口（≤60%×24000≈14400，来自记忆尾部 LRANGE，消息块原样带所以图片不丢）+ 本轮提问（永占）。预算每轮按模型窗口再收窄（窗口 − 输出预留 − 1024 安全边际，下限 512）。
3. **降级链**（历史超预算时）：摘要按行截、保留最近的 → 卡片从末位砍 → 近况窗口**从最老整轮丢**（2 条一批，避免留孤提问），保底最后 2 条 + 512 硬底。本轮提问永不丢。
4. **引用代替字节**：DELEGATE 路径图片剥出消息、只留引用名清单（教模型调 seeImage）；INLINE 路径 base64 原样进消息、同时存一份暂存区；知识检索 Top8 + 3000 字符只进当轮；`rememberFinalAnswer` 只把 UserMessage + 最终无工具调用的 AiMessage 写进记忆——中间工具调用/结果只进归档 flow。
5. **按需取回都有预算**：seeImage / searchKnowledge / read_history / recall_history 合起来每轮 3 次（`RoundSearchBudget`），防把检索当抛球游戏。
6. **检查点 24h = 软删宽限期 24h**：悬案在宽限期内可 resume 落地，硬删随检查点清理一并蒸发——F03 阶段二"resume 不挂软删闸门"依赖这个时钟对齐。

**代价与坑**：

- **存储无限增长是 accepted cost，不是待办**：用户约束下记忆/归档只增不减，带媒体的会话（INLINE 路径 base64 原样进记忆）单键会持续增大。对策是监控与导出副本，不是删除——任何"清理/瘦身/LRU"需求不得先于这条约束。原计划本块 P0「补摘要 TTL + 记忆/归档自动清理策略（TTL/LRU 可配置）」据此**作废**，改为体量监控 P1。
- **摘要有滞后，拼装必须补缺口**：滚动摘要 + 摘要之后又滑出窗口那几轮的 digest 一起拼，缺口不补历史凭空消失；摘要默认关闭，开启后的质量/成本未验证，按 P2 评估。
- **倒排索引 30 天过期后的检索降级**：过期 → 子串扫描兜底（`fallbackSubstringScan`），归档永久所以不丢能力，但大会话全量子串扫描慢——语义化（混合检索）因此不只是质量问题，也是降级路径的性能问题。
- **INLINE vs DELEGATE 的记忆形态分叉**：同一条 UserMessage 在两条路径下写进记忆的形态不同（带 ImageContent vs 纯文本+引用名），媒体 token 折算（图 800/音 6000/视 12000）必须与之一致，否则容量自检与真实存储分叉。
- **检查点过期与软删硬删是同一时钟的两半**：改宽限期/检查点 TTL 任一项另一项必须同步；且 F03 宽限期到点的定时扫删（`DomainPurgeScheduler`）与检查点清理的顺序要保证"先停飞再清检查点"。
- **与 F09 的边界**：本部分拥有"存什么 ↔ 召回什么"的契约（记忆/归档/检查点/装配/降级/取回预算），F09 拥有提示词本身与上游缓存；预算探针（按模型窗口收窄）是两边的接缝——行为由 F04 定义，元数据由 F09 补。

#### F04 落地记录（2026-10-25，五项全部完成）

**约束与难点**——为什么这五项得按这个做法来：

1. **存储侧那条硬约束先把"清理"这条路堵死了**：记忆/归档只增不减，任何"清理/瘦身/LRU"需求不得先于它。于是"体量监控"从一开始就与"清理"是两回事——运维真正缺的不是删除按钮，是<b>看得见</b>（哪个会话长到该注意了）和<b>搬得走</b>（要迁移、要留存时拿得出完整副本）。把这两个动作做出来，才谈得上"应对增长"。
2. **装配是唯一决策点，但决策不留痕**：装配完只剩一串消息，用户说"它忘了"时无从判断是<b>没召回</b>（卡片段空）还是<b>召回了但被预算砍掉</b>。两者排查方向完全相反：前者要去查检索为什么没命中，后者要去查预算为什么这么小。
3. **关键词路的真正盲区不是"索引没了"**：30 天 TTL 过期有子串扫描兜底；真正的洞是<b>词对不上</b>——"退款流程走多久"勾不回"退款需要几个工作日"那一轮，字面无一重合但说的同一件事。这是加语义路的唯一理由，不是为了"高级"。
4. **摘要与检查点各有各的时钟耦合**：摘要天生滞后（异步 + 阈值门），检查点 TTL 与 F03 软删宽限期是同一时钟的两半。

**决策**——五项各自的落点：

1. **a 装配清单可观测**：新增 `ContextAssemblyReport`（api 契约）+ `AssemblyReportStore`（SPI）+ `RedisAssemblyReportStore`（一会话一 List，只留最近 50 条、30 天 TTL）；`ContextAssembler.assembleWithReport` 是纯函数增量，原 `assemble` 委托它（消息序列一致由测试钉死）；编排层落账失败只告警；管控台 `GET /admin/sessions/assembly`。<b>清单是派生数据，可裁</b>——这与"只增不减"不冲突，那条约束管的是有真相价值的数据，账本不是。
2. **b 历史记忆语义化**：`HistoryVectorIndex`（api）+ `RedisHistoryVectorIndex`（一会话一 Hash，应用内余弦，上限 500 轮）+ `TextEmbedder`（内核定契约、服务端定模型，与 `RollingSummaryService.Summarizer` 同一套路）。混合检索<b>并进</b> `RedisHistorySearch` 而不是新建装饰器：保持 bean 类型不变，删域级联天然覆盖两路。融合用 **RRF（k=10）**而不是加权——关键词分是"词根权重 + 新近衰减"、向量分是余弦，量纲与分布都不同，加权等于让"数值恰好大"的那一路赢。未配向量模型 / 嵌入失败 / 索引为空都只是少一路，退化成纯关键词。
3. **c 体量监控与导出副本**：`RedisSessionStorage` 只读盘点（LLEN / HLEN，全是 O(1)，不做全量读取）+ 导出副本（归档全轮 + 装配清单）；管控台 `GET /admin/sessions/storage` 与 `/export`。<b>接口层没有任何删除动作</b>：一旦有"清理"，它一定会长成"按体量自动清理"，那与硬约束正面冲突——这里把口子收死。
4. **d 检查点持久化**：能力本就具备（`checkpoint-ttl` 置 0 或负数 = 不过期，断点在 Redis 里天然跨重启），缺的只是口径与证据。补齐：配置注释写明改它必须同步 `domain.delete-grace`，加 2 个测试用例把"0 / 负数都不走带 TTL 的 SET"钉死。
5. **e 摘要默认开启评估**：结论是<b>维持默认关闭</b>，理由三条——① 关掉不是没有摘要，digest 拼接照旧覆盖老轮次（历史一条不丢），摘要只是"可读性增强"不是"能力有无"；② 成本是随会话线性增长的额外模型调用，而收益只在"会话很长且常追问旧事"时才显现；③ 质量未验证（无评测集），默认开启等于把未验证的有损压缩作用到所有会话。开启后的自检项：确认 `upToTurnId` 单调（摘要不倒退）、观察每会话额外调用次数与 token、比对开启前后老事追问的命中率。

**代价与坑**（这几条都是实测踩出来的）：

- **"摘要被截光"会被记成"本轮没有摘要段"**：初版把 `summaryDropped` 算在 `if (!clipped.isBlank())` 里，摘要整段被预算砍光时账本写 0，看着像"这轮压根没摘要"。排障时这两者指向完全不同的方向（前者查摘要为什么没生成，后者查预算为什么这么小），测试逼着把记账移到块外。卡片整段让位（预算被前面吃光）同理。
- **向量路没最低分门槛就会拿噪声充数**：余弦检索永远能返回一个"最接近的"，哪怕全都不相关——0.03 的那轮也会排第一，因为它总得有个第一。卡片段只有 5 张位子，噪声进去等于把真正相关的挤掉。加了 `MIN_SIMILARITY = 0.2`：**检索宁可空手（有关键词路与子串兜底顶着），也不要拿噪声充数**。
- **裁剪带迟滞会骗过测试**：向量索引攒够 20 条富余才裁一次，按"上限 + 25"写用例实测得 504 而不是 500（最后一次写入没触发裁剪）。这是设计不是 bug——每轮闭轮都全量读 field 排序不值当。
- **两路素材刻意不同**：关键词路索引 digest + 用户输入 + 回答 + 工具名（认词形，给它全文才准）；向量路只嵌 digest（认语义，给它噪声少的摘要才稳，且嵌入是按字符计费的外部调用）。
- **删域级联漏一路等于没删**：向量索引与倒排索引是同一批轮次的两个影子，漏删一个，删域之后一句旧话还能被另一路勾回来。所以 `deleteByDomain` 里两路都删，且都 fail-closed。
- **导出副本不带记忆**：归档本来就是全流程档案（输入 / 回答 / 工具流 / 用量），记忆只是它的近况视图，副本里带档案就够复盘，也避免把媒体内容块再抄一份。

**实测**：runtime 29 例（新增 6 + 既有装配 23 回归）、infrastructure 21 例（新增 15 + checkpoint 既有 6）全绿。

**4.3 两路召回（分开，各自可选实现）**

public interface KeywordSearcher {

**4.5 `QueryVectorResolver`**（domain 层函数式接口，server 注入 `embeddingModel::embed`）

```java
public interface QueryVectorResolver { float[] embed(String text); }  // 抛异常由编排层按"该路失败"降级
```

**4.5.1 embed 失败必须降级，不是抛异常（一审修订，A2）**：现状每条向量通道各自 embed，某条失败只降级该路、其余通道照常。上移后在 `retrieve` 开头统一 embed，若不用 try-catch 包住，一次 embed 失败会让**整轮检索抛异常**——"链路坏了"与"真没命中"再次同形，调用方会反复换问法重试而不是去查模型配置。契约钉死：embed 失败 → 本轮**全部向量通道标记失败，关键词通道照常执行**；只有全部通道失败才抛（与 4.6 表末行同口径）。必须有用例锁死（`EmbedFailureDegradationTest`）。

**4.6 异常语义表（必须逐条写进接口 javadoc）**

| 方法 | 姿态 | 理由 |
| --- | --- | --- |
| `exists` | **fail-closed（抛）** | 调用方拿它做破坏性决策。写成"查不到=false"，ES 一抖动删域就静默跳过索引删除，同路径域重建后知识原样复活且无报错（设计文档 5.10 第 1 条） |
| `deleteCollection` | fail-closed | 同上 |
| `listCollections` / `count` / `documents` | **fail-open（空/0）** | 管控台只读展示，抛异常整页打不开 |
| `existingDedupKeys` | fail-open + **error 级日志** | 后果是重复写入而不是错数据；warn 会被淹没 |
| 全部检索通道失败 | **抛异常**（`CompositeRetriever` 既有语义） | "链路坏了"不能与"没命中"同形 |

##### 5. 分数契约（最容易做错的一条）

**决策**：`KbHit.score` 只承诺**越大越好、在同一后端同一模态内可比**；**不承诺 [0,1]，不承诺跨后端可比**。阈值参数**不属于 SPI 入参**，是后端自己的配置项。

**被否方案**：把分数统一归一化到 [0,1]。理由：融合层的分数制对每路做 min-max，向量的 `cosine→(c+1)/2` 是线性的、无影响，但 BM25 无上界，压到 [0,1] 只能走 `x/(1+x)` 这类**非线性**变换——min-max 之后分布被改，分数制融合结果静默漂移，而 RRF 轨不受影响，于是"同一份数据、同一套配置"在两种融合下得到不同答案。**统一分区间是伪需求**。

真正要防的是"方言外泄到配置"，用"阈值归后端"解决：

| 配置 | 归属 | ES 后端语义 |
| --- | --- | --- |
| `vector.minScore` | ES 后端专属 | 原始余弦，内部 `+1.0` 偏移（Painless 值域），不外泄 |
| `vector.topK` / `keyword.topK` | 通用 | — |
| `keyword.minimumShouldMatch` | ES 后端专属（BM25 方言） | 有效区间 40%~50%，别凭直觉调大 |

`RetrievalProperties.vectorMinScore` 保留为**废弃兼容键**：启动时若新键未设而旧键存在 → 原样搬到 ES 后端配置并打 WARN，行为完全等价（不需要换算，因为语义没变）。

**红线：ES 适配器的分数必须逐字节等价（一审修订，A7）**。验收靠改造前后比对 10 条 query 的命中集合与顺序，因此平移时这几处**一个数都不许改**：① 写回 metadata 的 `_retrieval_score` 仍是 `h.score()` 原值（即 `cosineSimilarity+1.0` 的结果）；② `minScoreRaw = minScore + 1.0` 偏移照旧；③ `size` / `sort` / `_source` 过滤字段照旧；④ "`text` 为空白则丢弃该 hit"的过滤照旧。动任何一项，基线比对必失败——而失败会被误读成"融合算法被改坏"，排查成本极高。

##### 6. 召回策略与装配校验

以上配置落在 `domainplane.knowledge.*`（yaml，`KnowledgeProperties`）。**P0 不动 `InfraSettings`**（一审修订，A5）：ES 连接地址继续复用 `InfraSettings.es`，管控台「存储配置」页与保存路径零改动；`InfraSettings.VectorStore` 段随 P1 向量库地址一起引入。

```yaml
domainplane:
  knowledge:
    strategy: hybrid          # keyword | vector | hybrid（默认）
    fusion: auto              # score | rrf | auto（沿用 AdaptiveFusionStrategy）
    keyword-backend: es-main
    vector-backend:  es-main
    backends:
      es-main:
        type: elasticsearch   # P0 唯一放行值，其它值启动即报错并列出支持列表
        vector:  { topK: 30, minScore: 0.35 }
        keyword: { topK: 20, minimumShouldMatch: 50% }
```

| strategy | 必需能力 | 不满足时 |
| --- | --- | --- |
| `keyword` | `capabilities.keyword` | **启动失败**，`KNOWLEDGE_BACKEND_MISCONFIGURED(60007)`，文案点名缺哪个后端哪种能力 |
| `vector` | `capabilities.vector` + EmbeddingModel 可用 | 同上 |
| `hybrid` | 两者 + EmbeddingModel | 同上 |

校验器 `KnowledgeBackendValidator` 在两个时机跑：① 应用启动（`StartupSelfCheck` 同族）；② 管控台保存知识库配置时（保存即校验，不把错误留到重启）。**能力不满足必须是启动失败，不是运行时空结果**——运行时空结果会让"配错了"和"知识库是空的"长得一模一样。

两个后端不同（如 keyword 留在 ES、vector 走向量库）时要求 collection 命名同源：命名规则继续由 api 层 `KbIndexes.nameOf(domain)` 作为唯一出口（存量索引名一字不变，零数据迁移）。**不新增 `KbCollections` 包装类（一审修订，C1）**——P0 不改命名，包装层只会是纯转发；多一层间接就多一处"哪天两套命名分叉"的风险。

##### 7. 保存地址：挂哪里

- **P0 不新增地址字段**：ES 后端直接复用 `InfraSettings.es`（管控台「存储配置」页已有，且支持热替换 `SwappableElasticsearchTransport`）。绝不出现"两套 ES 配置"。
- **P1 的向量库地址**：新增 `InfraSettings.VectorStore`（uri / token / collectionPrefix / metric），与 ES、Redis 同族，同走落盘 + 掩码展示 + 连通性测试。
- **热替换边界（必须写进文档）**：连接参数变更可热替换；**后端类型（`type`）与 `strategy` 变更必须重启**——bean 图不同，热替换只会造出半新半旧的装配。管控台在这两项旁明示"保存后需重启生效"。

##### 8. ES 适配器设计（`infrastructure.kb.es`）

##### 9. 写入侧改造

- `KnowledgeBaseService`：字段从 `ElasticsearchClient` 换成 `KnowledgeStore` + `ChunkArchive`；`storeFor()` / `ensureIndex()` / `deleteByDocId()` / `countByDocId()` / `countAll()` / `listIndex()` / `existingIndices()` 逐个改走 SPI。
- `DocumentIngestor.ingestExternalDocuments(docs, esClient, index, store, model)` → `ingest(docs, IngestTarget, model)`，`IngestTarget = record(String collection, KnowledgeStore store, DedupLookup dedup)`。`DedupLookup = Set<String> hashes -> Set<DedupKey>`，由 ES 后端实现。
- **先写后删、回滚、覆盖更新清旧失败只吞日志**三条语义一字不改（设计文档 5.8）。
- 向量化仍在调用侧分批（25 条/批），`write()` 收的是已带向量的 `KbChunk`——把"谁做 embed"钉死在调用侧，后端只管存。
- **`EsIndexManager.DOMAIN_FIELD` 的归属（一审修订，A6）**：删包后 `KnowledgeBaseService` 的两处引用（`upload` 里写入、`domainOf` 里读取）会编译不过。直接用已存在的 `ChunkMetadataKeys.DOMAIN`（同为 `"domain"`），常量随包删除、不搬。
- **补 `ChunkMetadataKeys.CONTENT_HASH`（一审修订，B2）**：`content_hash` 现在是 `AbstractDocumentProcessStrategy` 与 mapping JSON 里的裸字符串，`DedupLookup` 要跨模块用它，补成常量，顺带消掉一个拼写分叉点。

##### 10. ChunkArchive：切片原文的权威源

- 载体：已落地的 `BlobStore`（本地默认，将来可切 S3）。键 `kb/chunks/{indexName}/{docId}.json`——`indexName` 直接用 `KbIndexes.nameOf(domain)` 的全名，**不另造哈希**（一审修订，C1），删域时按前缀列举即可整域清除。
- 写入序：**ingest 成功 → 写 archive → 返回**；archive 写失败不算上传失败（只告警，索引已可用），但必须计入指标。
- 删除：删文档 / 删域级联时一并删（删域顺序：先删 archive 再删 collection，与现在"先删预览 txt 再删索引"同构）。
- **双向对账（一审修订，A3）**：只做"孤儿回收"不够。写序是"索引成功 → 写 archive，失败只告警"，于是会出现"索引有文档、archive 无原文"的**缺档**——换模型重灌时这篇文档会被静默丢掉。对账必须双向：① 孤儿（archive 有、登记表无）→ 删；② 缺档（登记表有、archive 无）→ 从 `KnowledgeStore.scan()` 读回切片**补写**（`scan` 的存在理由正是这一条，而不是重灌主路径）。复用 `MediaBlobSweeper` 的套路（年龄护栏、删不动下轮重试、列举失败整轮跳过），**本次一并交付**。
- 收益：① 换向量模型 = 从 archive 重灌，不再依赖 `storesText`；② 换后端 = 从 archive 重灌到新后端；③ 顺带兑现横切附注"OCR / 语义分块 / 下载原文"缺原文的承诺；④ 切片预览 txt 可直接由 archive 生成，`ChunkExporter` 长期可废（本次保留不动）。
- 与 `ChunkExporter` 的分工（一审修订，B3）：archive 是**原文权威源、重灌输入**；`ChunkExporter` 是"索引视角的人工核对产物"（从索引读回生成预览 txt）。P0 保留 exporter 现状不动（少一处迁移风险），但删域 / 删文档时**两者都要删**，顺序：先删 exporter 预览文件与 archive，再删 collection。

##### 11. 重灌（换模型 / 换后端，同一条路径）

`VectorReindexer` 重写为面向 SPI 的三阶段，**失败语义照搬 fail-closed**：

1. **全捞**：从 `ChunkArchive` 读出全部 collection 的原文（不是从索引捞）；archive 缺档时先按第 10 节双向对账补写。读不全立即抛、不往下走。
2. **重建**：逐个 `deleteCollection` → `ensureCollection(newDims)`。
3. **重灌**：按 25 条/批 embed 后 `write()`；批内向量条数不符直接抛（不能留下"有些切片有向量有些没有"的半成品）。

保留 `ReindexResult(preserved, reindexed)` 逐项相等的核对口径。`store.scan()` 定位为**对账补写 + 兜底**（archive 缺档时补写、archive 全失时兜底重灌），ES adapter 的 `search_after` 翻页逻辑平移进来，含"必须看 total 判取完、拿不到游标宁可中止"两条。

##### 12. 通配检索降级

`KbIndexes.WILDCARD`（未绑域的管控台预览 / 诊断路径）只有 ES 支持。向量库后端 `wildcard=false` 时：该路径降级为 `listCollections()` 枚举后逐 collection 检索关键词路，向量路跳过并 WARN；若 `strategy=vector` 则管控台该路径返回"请先绑定域"提示而不是假装全库检索。

- `DomainChannelProvider` 缓存 key → `backendId|collection|modality`；`evictIndices` 改名 `evict(collection)`，语义不变（删域仍必须失效，否则旧检索器指向已删索引）。
