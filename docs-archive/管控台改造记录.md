## 1. 为什么是"原地修补"而不是"换栈重写"

管控台原本是"服务端直出 + 零依赖静态三件套"：`console.js` 307 行共享库 + `console.css` 680 行 + 12 个页面内联脚本，合计约 5,300 行，无构建、无 lint、无测试。

调研过 amis / HTMX / Vaadin / JeecgBoot 与中间件控制台四大家族，结论一致：这类界面与 XXL-Job、Kafdrop、RabbitMQ Management 同族，是"被时间验证的活法"。RocketMQ 重写控制台的触发点是**复杂交互与 AI 功能**，不是页面数量——本项目 10 个页面还没到那个门槛。

所以只补工程化欠账，**五不动**：后端接口与信封、`CredentialAuthInterceptor`、同源策略（凭证是 HttpOnly Cookie，CORS 默认全关是有意设计）、部署形态（静态资源仍从 classpath 提供）、页面 DOM 结构（视觉替换另走 V 轨）。

## 2. 信封四形态：整个改造唯一的"施工图"

后端返回体有**四种**形态，不是"两套"。这条事实是 P2 的前提，也是后续新加接口时必须对照的约定：

| 形态 | 标识键 | 判定 | 数量 |
| --- | --- | --- | ---: |
| **A** 纯 `code` | `code:0` 成功 / 非 0 失败 | 有 `code` 无 `success` | 15 |
| **B** 双写 | `code` + `success` 都给 | 两者都有 | 16 |
| **C** 纯 `success` | `success:true/false` + `message`/`error`/`detail` | 有 `success` 无 `code` | 11 |
| **D** 裸对象 | 无任何标识，直接是数据体 | 两者都无 | 29 |

**为什么"非 0 即 reject"两头都错**：C 类没有 `code` 字段，沿用 `if (r.code && r.code !== 0)` 会 `undefined` 短路 → **静默吞掉失败**；改成 `if (r.code !== 0) throw` 则 `undefined !== 0` 为真 → **全部误报失败**。所以归一化必须三级降级：

```js
// frontend/src/core/request.js
export function normalize(raw, helpers) {
    if (raw && typeof raw.code === 'number')    return { ok: raw.code === 0, code: raw.code, message: pick(raw, helpers), data: raw }; // A / B
    if (raw && typeof raw.success === 'boolean') return { ok: raw.success, message: pick(raw, helpers), data: raw };                      // C
    return { ok: true, message: '', data: raw };                                                                                          // D
}
```

三条硬约束：`code === 10002` 仍走 `redirectToLogin`（分流留在 `console.js`，api 层不碰）；文案优先级 `detail → error → message` 且**必须过 `sanitizeError`**；B 类不动后端（前端统一按 `code` 判，`success` 冗余留着）。

新增接口时**优先选 A 或 D**：B 类是最阴的一种——两个键都写、前端只用其中一个，改哪边都不会立刻炸，但两边语义迟早分叉。

## 3. 已落地的结构

```text
domainplane-server/
├── frontend/                     # 源码，不进 jar
│   ├── package.json              # esbuild + eslint + prettier
│   ├── build.mjs                 # 自动扫 src/pages/*.js，新增页面不用改配置
│   ├── eslint.config.mjs
│   └── src/
│       ├── console.js            # fetch / 10002 分流 / sanitizeError / 侧栏
│       ├── core/{request,feedback}.js
│       └── pages/*.js            # 每页一个入口
└── src/main/resources/static/console/
    ├── *.html                    # 只留 <script src="assets/page-xxx.js">
    └── assets/
        ├── console.css           # 手写，不参与构建
        ├── console-tokens.css    # Tabler 令牌映射层
        └── page-*.js             # 构建产物，入 git
```

| 项 | 结论 |
| --- | --- |
| 构建工具 | **esbuild**。10 个静态页 + 同源部署，不需要 dev server / HMR / 插件生态；单依赖、<1s、产物可控 |
| TypeScript | **不引入**。「`.ts` + `@ts-nocheck` + 不开 strict」是成本全额、收益≈0 的组合——剩下承担的只是 ESM 打包，而那是 esbuild 本职。需要类型时用 JS + JSDoc + 按文件 `// @ts-check` |
| 源码位置 | 放 `frontend/` 而非 `static/`，避免源码打进 jar |
| 产物 | **入 git**（没上 `frontend-maven-plugin`）。本机 Maven 是离线缓存，装新插件要外网；漂移靠「源码与产物同一个 commit」+「改完必跑构建」兜住 |
| 失败模式 | **改了 `frontend/src` 不跑构建，`assets/` 下还是旧产物，而 jar 仍然能正常打包**——问题只在运行时出现。这是本方案唯一的"必须记住" |

## 4. 踩过的三个坑

1. **`sanitizeError` 曾静默失效**：第一版 `pick()` 写成 `if (typeof raw.sanitizeError === 'function')`，那是在检查**响应体上**有没有这个函数，永远为 false——错误提示一次都没清洗过。靠 `tools/test-normalize.mjs`（17 条断言，覆盖四形态 + 两出口）抓出来。修法是 `pick(raw, helpers)` 用注入的清洗函数。
2. **IIFE 外提会静默弄死按钮**：外提前提是页面没有任何依赖全局函数的内联事件属性。外提前必须全站 grep `onclick="foo()"` 一类写法；有的话先把函数挂到 `window`。当前全站只有 `login.html` 的 `onsubmit="return false;"`，安全。新页面若加这类属性，这条约束就被破坏。
3. **`window.CONSOLE_NO_AUTH_GUARD` 这类置位不能外提**：必须在 `console.js` 之前执行，留在 HTML 内联 script 里。

只引 `tabler-props.css`（纯 CSS 变量），**不引 `tabler.min.css`**（含 Bootstrap reboot，会带来全局副作用；全量文件 635 KB 留在仓库只为将来决策）。

| 项 | 结论 |
| --- | --- |
| 版本 | `@tabler/core@1.6.1`，MIT |

### 6.3 域软删状态可见化（2026-10-30）

删域是**软删**（`AdminDomainController#delete`）：整支树打 `deletedAt`，宽限期（默认 24h，`domainplane.domain.delete-grace`）内只拒新开轮（`DOMAIN_PENDING_DELETE` 10011），在飞会话与 INTERRUPT resume 照常收尾，到点由 `DomainPurgeScheduler`（每分钟扫）硬删；宽限期内 `POST /admin/domains/{id}/restore` 可撤销。

原先管控台只挂一个「待删除」标签，用户不知道多久真删、能不能反悔。已补：

- 详情卡顶部黄色说明条 `.dp-pending-box`：剩余时间 + "期间仍是完整域，只拒新会话" + 两个动作
- 「撤销删除」（走 restore）与「立即彻底删除」（`?force=true`，二次确认写明不可撤销）
- 删除确认弹窗改两段式：第一步标记 + 宽限期可撤销，第二步到点自动清理清单；按钮文案「标记删除」
- 软删后**保留选中态**，让用户当场看到说明条；成功后 toast 提示剩余宽限与撤销入口
- 宽限期时长取自 `GET /admin/domains/storage` 的 `deleteGraceMs`，取不到就只显示「待删除」

### 6.4 存储配置页分区（2026-10-31）

原先三张卡按 ES / Redis / 向量库排，读起来像"三个同级中间件"，但它们的缺省后果差一个量级：Redis 缺了对话直接 90005，ES / 向量库缺了只是知识库不可用。按**"缺了会怎样"**重排：

- 段一「运行状态存储」= Redis 一张卡，放最上（会话记忆 / 中断断点 / 会话归档都落这里）
- 段二「知识库存储」= Elasticsearch + 向量库（可选，不配也能对话）
- 顶部状态行把 Redis 放第一位，全缺时的引导改成"请先填 Redis 地址"
- 分区用既有的 `.seg` + `.seg-note` 版式（与 models 页同款），不新增 CSS 类
- Redis 卡再收一档（只有 4 个字段，与字段数加倍的 ES 卡同间距会显空）：说明框里的折叠说明提到 chips 同一行、卡内边距 20→16、字段距 1rem→0.6rem、字段从三行并成两行（地址+端口 / 库号+密码）、删掉与段说明重复的“必填 / 未配置会怎样”。全部规则以 `.infra-redis` 作用域限定，不动同页另两张卡

顺带补了冒烟脚本的漏洞：`page-infra.js` 的字段全走 `el("x")` 短函数与 `MAP` 元组表，正则只认 `getElementById("x")` 时**这些 id 一个都没被断言过**——重排卡片时漏搬一个 input 完全测不出来。`.workbuddy/smoke.mjs` 断言 1 已扩到 `el("x")` 与 `['x', 'field', 's']` 两种形态。

### 6.5 存储配置页：三段式面板 + 连接可复用（2026-10-31，仅前端结构）

原页面三张厂商卡等于把"在哪台机器""谁做关键词谁做向量""哪个域落哪套"压成一个全局常量。重排成**三段**，每段一个 `.panel`（编号 + 标题 + 说明 + 右侧动作），**段内形态刻意做成三种**——单张表单 / 表格 / 卡片矩阵。形态不同才扫一眼就知道是三件事；三段都堆一样的卡只会读成一张长列表。

- **01 运行状态存储**：Redis 面板，橙色编号。旧 `.infra-redis` 的整卡内边距套到面板上会多出一圈留白，用 `.panel.infra-redis { padding: 0 }` 抵掉。
- **02 连接**：**三段各一张表**，段头编号 `2-1 关键字` / `2-2 向量` / `2-3 原文`，数字徽标与表头底色按段落上色（青 / 靛 / 灰），段间用 26px 分隔 + 上横线。列 = 名称 / 地址（原文段叫「位置」）/ 状态 / 被引用 / 操作。
  - **不做"一张表加类型列"**：三类连接的字段、地址形态、失败后果全不一样（ES 有 IK 分词器与版本判读、向量库看度量与集合前缀、原文存储是对象键），混在一张表里只能靠类型列区分，扫表时反而要多读一列才能判断自己该看哪行。
  - **新增与编辑走遮罩弹窗，且三段各一个、互不共享**（`connModalEs / connModalVec / connModalTxt`，版式复用 models 页的 `.modal-mask` / `.modal-panel.modal-panel-wide`）。三段是三种**用途**（关键字 / 向量 / 原文），ES 只是关键字这一格当前的一种实现——它也能做向量，所以绝不能让三段的新增共用一个弹窗、一套"类型选择"（第一版就犯了这个错：一个弹窗里放三张类型卡，把"加一条关键字连接"和"加一条向量连接"混成了同一个动作）。
    - **2-1 新增是两步**：先出**预设选择**（当前一张卡：Elasticsearch · 关键字索引 · BM25+IK，标「当前唯一支持」），**选中预设才铺配置表单**（连接名称 + 地址/认证/超时）；以后接第二种关键字后端（如 OpenSearch）就是加一张卡，"选谁铺谁的表单"在卡片的 click 里分派。没有可写的后端，按钮叫「加入连接」并明写"只在本页加一行"。
    - 2-1 编辑跳过预设步（es-main 当年已经选过），标题 `编辑连接 · es-main`，保存走真实 `/admin/infra`，成功关窗 + toast。
    - **2-2 向量**：自己的弹窗，与 2-1 同构的两步式。**预设有两张卡**：`Qdrant`（独立向量库 · v1.x，选完铺地址/Token/度量/前缀表单——qdrant-main 的编辑与真实保存也在这张表单上）和 `Elasticsearch`（dense_vector · 8+/9.x，**一张正常的 ES 实例配置表单**：地址/认证/超时照填）。**页面上不出现"复用"概念**：与 2-1 的关键字 ES 是不是同一台机器，由系统在保存时按地址判断、隐含合并（同机 = 同一份索引，不重复建/灌），用户只管填地址——折衷方案（"复用关键字 ES 连接"下拉）被否掉的原因：那是把系统该做的事推给用户选。两个预设的"加入"都只在本页加一行（后端还没有"命名连接"）。
    - **2-3 原文**：自己的弹窗，只有一句"当前内置本地磁盘"——内置的东西没有"新增"可言，但按钮留着，点了给一句实话比没反应强。
    - 新增模式必须**清空表单 + 换掉口令提示**：否则「测试连接」会悄悄测到 es-main 的地址、口令提示还写"当前已配置 el******ic"（那是既有连接的）。清空前的值存 `esFormSnapshot`，取消/完成后 `rawRestore` 还原——**还原时 `undefined` 不能直接塞 value**，输入框会显示字面量 "undefined"（截图才看得出来）。
  - 「被引用」直接列出哪几个存储集在用（改连接前先看影响面）；原文段是内置本地磁盘，只有一行、不可编辑。
  - **`.conn-table` 必须 `table-layout: fixed`**：地址列是长 mono 串，auto 布局会让它把别的列挤扁、表头写的百分比宽度直接失效，单元格与表头对不上（截图里表现为地址内容跑到「名称」表头下面）。

### 6.6 存储配置接后端：连接具名化 + 存储集（2026-10-31，后端改造）

§6.5 里"新增连接 / 槽位 / 命名空间尚未接后端"这一条**已被本节取代**（命名空间除外，见下）。

**难点**：改造前 `InfraSettings` 是三个固定槽（`es` / `redis` / `vectorStore`），`domainplane.knowledge.backends` 在 yaml 里静态声明后端，后端 id 与连接地址绑死。而页面上需要的是"关键字 ES 和向量 ES 各填一次、地址相同时才算同一台"——固定槽表达不了"两个 ES"，静态 bean 图表达不了"保存即生效"。

**决策**（用户拍板：连接具名化 + 存储集；合并判据 = 协议 + 主机 + 端口）：

1. **配置分两层，各管一件事**
   - `connections`：id → 具名连接（`type=elasticsearch|qdrant`），只描述"连哪里"（地址 / 口令 / 超时 / Qdrant 的度量与前缀）。
   - `sets`：id → 存储集，三个槽 `keyword` / `vector` / `text` 各指向一个连接 id，只描述"谁干哪活"。
   - `redis` 不参与：它是平台自身基础设施（会话语义按 sessionId 主键），单例、不按用途分。
2. **后端 id 就是连接 id**。省掉一整层映射：页面上那行 `es-main`、存储集里引用的、注册表里的，是同一个字符串，排障时一个 id 就能在页面上找到对应行。连接参数（`min-score` / `minimum-should-match` / `top-k`）仍按 id 从 yaml 的 `backends` 读；yaml 里没有的连接走废弃兼容键的默认值，**不打 WARN**（管控台新建的连接本来就不会出现在 yaml 里）。
3. **同实例合并按物理地址，不按对象引用**。`knowledge` 层给 `KnowledgeBackend` 加了 `location()`（ES = `scheme://host:port`，主机名小写化；Qdrant = 规范化 uri），`RetrievalPlan.writeStore()` 由"两个后端是不是同一个对象"改成"两个后端的 location 是不是同一个"。这是**整节的关键**：页面上关键字槽和向量槽是两条独立配置，用户填了同一台 ES 的地址，两个后端是不同对象、却是同一个索引——按引用比会扇出成两路，同一批切片写两遍、计数翻倍、去重键撞自己。
4. **注册表可整份替换**。新增 `LiveKnowledgeBackendRegistry`（一次换全套，没有 `put`，读侧永远看到旧的或新的、不会看到混合体），挂成 `InfraSwappable`，与 ES / Redis 代理在同一轮 `swap()` 里跑。`RetrievalPlan` 的两个角色 id 由构造参数改成 `Supplier`，保存即生效，不用重启。
5. **多 ES 连接需要多客户端**。新增 `EsClients` 客户端池（按连接 id 缓存、指纹变了才重建、旧客户端宽限 30 秒关闭）；**平台默认那台不重复建**——连接 id 等于 `defaultEsConnectionId()`（= 关键字槽那个）时直接复用平台可热替换的客户端，常见形态只有一份连接池。
6. **合并口径只有一个方向**：管控台配过连接就以管控台为准；一条都没配过时用 yaml 的 `backends` 合成连接与默认存储集。`InfraSettings.configured` 这个位用来区分"还没配过"和"用户显式清空了"——没有它，删掉最后一条连接后 yaml 那条会复活，用户永远删不掉表里那一行。

**代价与坑**：

- 旧配置文件（`{"es":{…},"vectorStore":{…}}`）由 `InfraSettingsStore.load()` 在读盘时迁移：`es` → 连接 `es-main`，`vectorStore` → 连接 `qdrant-main`，默认存储集的 keyword/vector 都绑 `es-main`。**`qdrant-main` 刻意留成未绑定**：旧文件里有它的地址只说明用户填过，不说明它在生效（改造前 `vector-backend` 在 yaml 里写的是 ES），直接绑上等于升级时静默换后端。
- `InfraSettingsStore` 的 mapper 关掉了 `FAIL_ON_UNKNOWN_PROPERTIES`：解析失败会置 `loadFailed` 并拒绝后续写入（防覆盖清空），也就是一个多出来的键就能把整份存储配置变成只读——多一个不认识的键只该被忽略。
- 存储集卡片上的**「命名空间」已去掉**。后端没有这个能力（索引名走 `KbIndexes.nameOf(域)`，全链路十几处），留着就是一个填了不起作用的输入框。多套数据隔开靠 Qdrant 连接自己的 `collectionPrefix`。
- 域级绑定存储集**没做**（现阶段所有域都用默认存储集）。
- 保存接口是**整份覆盖**（连接与存储集按数组传，落盘才转成 id 为键的对象）：不做增量补丁，"少传一条当没动过"会让删掉的行在重启后复活。口令留空 = 不修改，按**连接 id** 补齐（不按"第一个 ES"——不同实例之间绝不能串口令）。
- 页面侧：`CONNS` / `PROFILES` 两个假数据数组删掉了，连接增删改与槽位绑定都走 `/admin/infra`；删除连接前先查引用，被存储集占用的直接拦下并点名是哪几个集。

相关类：`InfraSettings`（重写）/ `InfraSettingsHolder`（合并口径 + 按 id 补口令）/ `InfraSettingsStore`（迁移）/ `InfraSettings` 的消费方改 `defaultEs()` / `KnowledgeBackendsConfiguration`（按连接建后端 + 可重建）/ `LiveKnowledgeBackendRegistry`（新）/ `EsClients`（新）/ `RetrievalPlan`（Supplier 角色 + location 合并）/ `KnowledgeBackend.location()` / `EsKnowledgeBackend`、`QdrantKnowledgeBackend`（带 location）/ `DomainChannelProvider.evictAll()`（后端集合换了要清检索器缓存）/ `AdminController` 的 `/admin/infra`、`/admin/infra/test`。

**收盘补的四件事**（同日，接口验完之后用真实响应跑布局验收时暴露出来的）：

1. **连接要带 `usage`**。`GET /admin/infra` 原来的 `connectionBody` 只给 id/type/location，页面只能按类型猜归属（ES→2-1、Qdrant→2-2）——于是"用 ES 做向量"这条正常配置会被画到关键字表里、向量表里却没有它。现在 `Connection.effectiveUsage()`（缺省按类型落位，老配置不会消失）随接口下发，页面照 `usage` 分组。
2. **槽位要校验能力，不只校验存在**。`checkSlot` 原来看"这个连接存不存在"，现在还要看"干不干得了这活"：关键字槽只认 ES（Qdrant 没有全文检索），向量槽 ES 与 Qdrant 都行，原文槽非空即拒。界面下拉已按用途过滤，这道闸拦的是**手工构造的请求**——绑错了要一路走到开通道才炸，那时的报错既晚又难懂。
3. **原文槽画成只读**。它当前没有可绑的连接（原文走内置 BlobStore），原来给一个列出全部连接的下拉，等于让人选一个必然被拒的选项。
4. **存储集槽位右侧不再重复连接名**（下拉里已经有了），改成显示该连接的地址；**关键字与向量落在同一台实例时直接点出"与关键字同一实例 · 只写一份"**——这正是第 3 条决策的行为，页面自己说出来比让用户比对两行地址好。顺带把 Redis 卡片头上一直空着的徽章接上状态（已生效 / 未配置）。

新增测试：`InfraSettingsConnectionsTest` 追加 3 例（Qdrant 绑关键字槽被拒 / ES 绑向量槽合法 / 原文槽绑定被拒）。

### 6.7 存储集 → 知识体：单一用途 + 域自绑不继承（2026-10-31，后端语义重做）

> 「一体一用途」这条已被 §6.8 推翻（改为一个体装关键字 / 向量两路，各可选）。本节保留作演化记录，"不继承"等结论继续有效。

§6.6 的 `sets`（一个集三个槽）**已被本节取代**。§6.6 里除"集合形态"以外的结论（连接具名化、后端 id 即连接 id、按物理地址合并、注册表整份替换、多客户端池、合并口径单向、整份覆盖保存、口令按 id 补齐）全部继续有效。

**难点**：存储集是"平台级的一套"，三个槽绑在一起，于是三个问题都被它挡死。① 某个域只要关键字、不要向量，做不到——集是整体的，挂就得三个槽一起挂。② 两个域要落在不同集群（不同租户、不同环境）做不到——只有一个默认集，所有域继承它。③ 原文槽其实没有可绑的连接（原文走内置 BlobStore），它挂在集里只是个永远填不上的空格，校验还得专门为它开例外。根子在"域继承平台默认"这个假设：它让"给某一个域换个库"变成"给全体换库"。

**决策**（用户拍板：一个知识体只配三种存储方式中的一种；知识体不继承，自己绑自己的）：

1. **存储集拆成知识体**。`InfraSettings.KnowledgeBody` = `id` / `name` / `kind`(`keyword|vector|text`) / `connection`。一个体只干一件事，多个体才能覆盖多种用途。`kind` 不是标签而是**能力声明**：`searchable()`、`kindSupported()`、`effectiveKind()` 都由它决定，页面下拉也按它过滤。
2. **域 → 体的绑定存进 `DomainStore`**（`Map<String,String> bodies`，域 id → 体 id），与域配置同版本、同回滚。它不进 `InfraSettings`——那里是"平台有哪些体"，"哪个域用哪个体"是域自己的事实。
3. **不继承，一层都不借**。`RetrievalPlan.BodyLookup.bodiesOf(domain)` 只返回该域自己的绑定；返回空就是"这个域不挂知识库"，**既不看父域，也不看平台默认**。这是整节的语义核心：查询链 `Domains.chainOf` 遍历的每个域各自解析自己的体，父域的知识库不会被借给子域。
4. **读写两侧的回退刻意不对称**。`writeStore(domain)` 无绑定直接抛；`writeStore()`（平台默认）按 kind 扇出；`readStore(domain)` 无绑定回落平台默认。写要严格——静默写到用户没预期的库里，是"文档上传成功但搜不到"这类故障的源头；读要宽松——历史数据（改造前写进平台默认库的）还得读得出来。
5. **原文体不许绑连接**。`checkBody` 对 `kind=text` 且 `connection` 非空直接拒（"原文体走内置 BlobStore，不需要绑连接"），而不是像 §6.6 那样在原文槽上开一个"非空即拒"的例外。能力校验按体判：关键字体只认 ES，向量体认 ES / Qdrant，text 只认 BlobStore。
6. **`KnowledgeBaseService` 从"平台一个 store"改成"按域解析"**。`stores()` 返回所有后端去重后的集合（按对象同一性），`existingIndices()` 取并集，计数与存在性判断按"取最大 / 任一存在"，删除类操作按"全删"。
7. **迁移幂等**。中间版 `{"sets":{id:{keyword,vector,text}}}` → 每个集拆成最多 3 个 id 形如 `集id-用途` 的体；已经是新格式时什么都不做。yaml 合成路径同样产出 `default-keyword` / `default-vector` 两个体。

**代价与坑**：

- **多后端下"计数"只能用最大值，不能相加**。改造后同一切片可能在两台库里各有一份（关键字在 ES、向量在 Qdrant，或换库期间双写），`countAll` 相加就是重复计数，用户看到索引量翻倍。`countByDocId` 同理取最大；`deleteByDocId` 反过来必须**全删**，否则删完还搜得到。
- **平台默认的 `writeStore()` 仍必须按 location 判同实例**（§6.6 决策 3 的结论在这里复活一次）：关键字体与向量体指向同一台 ES 时，两条体是两个对象、同一个索引，按引用比会扇出两路、同一批切片写两遍。
- **绑定要跟域配置一起版本化，包括回滚**。`DomainStore.commitRollback` 因此多了一个参数（快照里的 `bodiesOf`）。漏掉这一步的后果是回滚后域指向一个已经不存在的体——不报错，只是静默变成"不挂知识库"，比报错难查得多。
- **页面上"体已失效"必须画出来**。体被删了但域还绑着它时，接口下发 `bodyMissing=true`，下拉里留一个「（已删除）」占位，而不是把它显示成"（不挂知识库）"——后者会让用户以为这个域本来就没用知识库，于是永远不会去修。
- **写侧抛异常是有意的**。未绑定就上传会得到明确的失败，而不是"上传成功、检索不到"。

相关类：`InfraSettings`（`KnowledgeBody` / `checkBody` / `SUPPORTED_KINDS` / `platformConnectionId` / `isKindUsable`）/ `InfraSettingsStore`（`migrateSetsToBodies`）/ `InfraSettingsHolder`（`synthesizeFromYaml` 产出两个体）/ `DomainStore`（`bodyOf` / `setBody` / `bodiesOf` / 四参 `commitRollback`）/ `RetrievalPlan`（`BodyLookup` / `BodyBinding` / `channels(domain)` / `readStore(domain)` / `writeStore(domain)`）/ `KnowledgeBodyResolver`（新，`@Component` 实现 `BodyLookup`）/ `KnowledgeBaseService`（`stores()` / `ownersByIndex()` / 跨后端 `rebuild*`、`purge*`、`reindex*`）/ `AdminController`（`/admin/infra` 收发 `bodies`、`/admin/domains` 下发 `body`/`bodyMissing`/`knowledgeBodies`）/ `AdminDomainController`（新 `PUT /admin/domains/{id}/body`）/ 前端 `frontend/src/pages/infra.js`、`domains.js`。

### 6.8 知识体改双路 + 检索工具按域动态注册（2026-10-31，推翻 §6.7 的两条前提）

§6.7 的两条前提（"一个体只装一种用途""检索工具挂根域全域可见"）**已被本节推翻**，其余结论（连接具名化、不继承、绑定进 `DomainStore` 同版本、读写侧回退不对称、计数取最大 / 删除取全删）继续有效。

**难点**：混合召回要求同一批文档既有关键字索引又有向量索引，而 §6.7 的"一体一用途"逼着域绑两次。"绑了一个、忘了另一个"的表现是**静默退化成单路**——召回到了，只是少一半，没人会去查。另一处是检索工具：它挂根域，于是每个域、包括根本没有知识库的域都能看到一个 `searchKnowledge`；模型对着空库调它，用户得到的是"未检索到相关内容"，看起来像知识库没数据，实际是这个域压根没配。

**决策**：

1. **一个体装两路，各可选**。`KnowledgeBody` = `id` / `name` / `keyword`（连接 id，可为空）/ `vector`（同上）。`configured()`（至少一路）、`modes()`、`hybrid()`、`keywordId()` / `vectorId()` 都由两槽直接回答。**原文退出知识体**——它一律写平台内置 `BlobStore`（换模型要能从原文重灌），没有"配到哪台机器"这回事；`KIND_TEXT` / `SUPPORTED_KINDS` / `searchable()` / `effectiveKind()` 一并删掉，`kind` 不再存在于模型里。
2. **"这个域走几路"由体回答，不由部署方配置**。`KnowledgeBodyResolver.bodiesOf(domain)` 逐槽产出 **0~2 条** `BodyBinding`（向量在前、关键字在后，与 `RetrievalPlan.fixed()` 一致）；只配一路就是单路召回，两路都配就是混合。融合策略仍是 `CompositeRetriever` 那边的事，这里不改。
3. **逐槽判可用，不整块失效**。某一路的连接被清空/删掉时只跳过那一路：关键字体那台 ES 停了，向量路不该跟着消失。`usableBody(id)` = 体存在 ∧ 配了至少一路 ∧ 那一（些）路的连接可用；`usableConnection(id)` 只判"存在且填了地址"，不测连通性。
4. **检索工具改成域相关、运行期声明**。`KnowledgeSearchTool` 的注解写 `domains = ToolDescriptor.UNBOUND_DOMAIN`（新哨兵），启动即"对任何域都不可见"；由 `KnowledgeToolBinder` 在**三个时点**重算并整体覆盖声明：① `@PostConstruct` 首次；② `DomainStore.onChange`（绑定 / 解绑 / 删域 / 回滚都走落盘，一处就够）；③ `InfraSwappable.swap`（存储配置保存，体或连接被改都可能让一批域从"有"变"没有"）。判定口径：域 d 有工具 ⟺ d 绑了体 ∧ `usableBody` 非空。声明写在域自己身上，子域靠 `visibleIn` 的累加语义自动可见（子域确实查得到父域数据）。
5. **迁移**：中间版 `sets`（一个集三槽）→ 一个集合成一个双槽体，原文槽丢弃；§6.7 的单用途体（`kind=keyword|vector`）→ 映射到对应槽，`kind=text` 或没配连接的直接丢；yaml 合成路径产出一个 `default` 双槽体。

**代价与坑**：

- **哨兵不能是空串或纯空白**。`declaredDomains()` 会把空白项滤掉，滤完是空列表，而空列表按累加语义是"挂根域"——正好把"谁都不能用"变成"全域可见"。故用 `<unbound>`（非空白、`trim` 不改动、尖括号不在域字符集里）。而 `AnnotatedToolScanner.resolveDomains` 会拿声明去跑 `Domains.validatePath`，`<unbound>` 会被拒 → 扫描器必须对哨兵**跳过校验**，否则启动即失败。
- **`ToolDomainRegistry.remember` 必须同时过滤两个哨兵**（`<revoked>` / `<unbound>`）。漏一个就会把哨兵当域建进域树：每次启动刷一条"新域"，`knownDomains()` 里多出一个 `<unbound>`，管控台域列表跟着脏。
- **`declareDomains` 刻意不碰 `ToolDomainRegistry`**。传进来的域来自业务配置（域已存在），不需要"沿链派生进域树"；顺手 remember 会把域树与业务配置混成两份来源。
- **声明是"整体覆盖"不是增量**。三个时点里任何一次都可能同时影响一批域；增量要算 diff，多算一次则无害，所以 `refresh()` 每次重算全集再一次性写回。
- **空壳体必须在保存时就被拒**。两槽都空的体在页面上能建出来，绑到域上后行为与"没绑"完全一样却不报错，用户会以为配了。`validate()` / `checkBody` 对此直接拒（`!configured()` → 报错）。
- **`KnowledgeSearchToolTest` 里"根域必须可见"是旧设计的钉子**，必须改成断言 `declaredDomains() == [<unbound>]` + 任何域都不可见，否则它会替旧语义守着门。
- **`DomainStore.onChange` 已于 2026-11-01 改成监听器列表**（`CopyOnWriteArrayList`，逐个回调、逐个隔离异常）。历史坑：它原本是单监听位（`changeListener` 一个字段），第二个消费者（`KnowledgeStatsService` 的知识库统计缓存）挂上去会把 `KnowledgeToolBinder` 的悄悄顶掉，现象是"绑/解绑知识体后检索工具可见性僵住"且无任何报错。现在多挂是安全的，但**仍然只能做幂等的派生状态重算**。

相关类：`InfraSettings`（`KnowledgeBody` 双槽 / `usableBody` / `usableConnection` / `checkBody`+`checkSlot`）/ `InfraSettingsHolder`（`synthesizeFromYaml` 产一个双槽体）/ `InfraSettingsStore`（`migrateSetsToBodies` / 新 `migrateKindBodies`）/ `KnowledgeBodyResolver`（逐槽 0~2 条绑定）/ `ToolDescriptor`（新 `UNBOUND_DOMAIN` + `isSentinel`）/ `ToolDomainRegistry`（两哨兵都过滤）/ `AnnotatedToolScanner`（哨兵跳过域校验）/ `ToolRegistry.declareDomains` / `KnowledgeToolBinder`（新）/ `DomainStore.onChange` / `AdminController`（`bodyBody` 下发两槽 + `domains()` 的 `bodyModes`/`bodyDead` + `knowledgeBodies` 按 `configured()` 过滤）/ `AdminDomainController`（改用 `configured()` + `usableBody`）/ 前端 `infra.js`（两路各一个下拉、去掉用途下拉与原文弹窗）、`domains.js`（下拉显示"关键字+向量"、体死标记）。

测试：`InfraSettingsConnectionsTest` 按双槽整体重写为 12 例（双槽混合 / 仅关键字 / 平台 ES 回落 / 同实例两槽同 location / 不同端口 / 悬空槽被拒 / 空体被拒 / 类型不支持 / Qdrant 填关键字槽被拒 / ES 填向量槽合法 / 空地址槽不可用 / 一路坏一路好仍可用），`KnowledgeBodyResolverTest` 重写为 10 例（两路两条绑定且向量在前 / 一路坏只跳过该路 / 两路都坏为空 / 不继承 / 未绑定为空 / 体被删绑定保留 / `platformBody` 按槽取 / 绑定跨重载存活），新增 `KnowledgeToolBinderTest` 5 例（未绑定全不可见 / 绑了只在该域与子域可见 / 解绑消失 / 连接被清空后随保存消失 / 一路好一路坏仍可见）。全模块 573 例绿。

## 7. 对后续改动的约束

1. 新接口优先选 A（纯 `code`）或 D（裸对象）；不要新增 B（双写）。
2. 页面逻辑只写 `frontend/src/pages/*.js`，不碰 `static/console/assets/page-*.js`（那是产物）。
3. 改完必须 `cd domainplane-server/frontend && npm run build`，且源码与产物同一次提交。
4. 页面里不写 `code !== 0` / `!r.success` 判断，一律走 `api.get/post/put/del`。
5. 不引 `tabler.min.css`；需要 Tabler 组件时加类，不加样式表。
