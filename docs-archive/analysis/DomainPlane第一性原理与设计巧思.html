DomainPlane 第一性原理与设计巧思

这个系统在为谁解决什么不可回避的问题，以及代码里 12 处把它焊死的设计

根本问题 · 不可靠的模型 + 多业务场景基本事实 · 4 条巧思 · 12 项，覆盖 6 层
结论先行：根本问题只有一句话：要把"会撒谎、会超时、会中断"的模型，装进"多业务场景共用一套能力"的容器里，且任何一次越权、静默降级、状态撒谎都不能发生。四条不可再分的事实决定了四类必然设计（域链装配、失败可区分、状态可恢复且不撒谎、进程内状态必须显式化）。代码里 12 处设计之所以精妙，是因为它们不是"最佳实践"，而是这四条事实的直接推论——换成别的写法，故障会以"看起来正常"的方式出现。

1根本问题

一句话：在一个进程里，让多个业务场景共用同一套 Agent 能力，而每次调用的能力边界、数据边界、失败语义都必须由业务结构决定，不能由代码分支决定。

拆开看，这个容器要同时容纳四种矛盾：

  • 模型不可信（会编、会超时、会被提示词注入带走）；
  • 检索不可靠（外部存储会挂、会慢、会在换了嵌入模型后全废）；
  • 交互是长事务（一轮几十秒、可能人工审批挂起数小时、可能被用户中途停止）；
  • 部署是单机的（没有分布式事务，没有跨节点状态，没有一致性协议可用）。

2四条不可再分的基本事实

事实一（本体论）：业务边界先于调用存在，而且是一棵树

一个客服场景、一个工单场景、一个内网运维场景，它们的边界不是"调用时才决定"的——它在上线时就以组织结构存在，并且有公共父级（公司级政策、通用话术）。所以"能力如何装配"只能有一个答案：沿一棵已存在的树继承，而不是在调用处拼 if-else。

它推翻了什么表面答案：配置项 + 开关。"给每个场景加一堆 xxx.enabled"在场景数到 3 之后必然失控，因为公共部分会被复制三遍。

事实二（认识论）：模型和检索的输出不可信，但"没命中"与"链路坏了"必须可区分

对模型而言，"我不知道"和"我出错了"是两种完全不同的回答；对检索而言，"库里没有"和"库连不上"也是。如果系统把两者揉成同一个空结果，用户会得到一个看起来正常、实际错误的答案，而且没有人会去查配置——这是最贵的一类故障：不报错、不留痕、只让人做错事。

它推翻了什么表面答案：把所有异常 catch 住返回空列表（"优雅降级"）。

事实三（工程论）：长事务必须可恢复，且恢复时的状态不能撒谎

一轮对话跨几十秒到几小时，中间可能人工审批、可能断连、可能被停止。可恢复意味着状态要落盘；而不撒谎意味着：落盘失败必须让这一轮失败，不能假装成功。半截回答被当成完整回答、被清空的断点被当成"没有会话"，都是状态撒谎。

它推翻了什么表面答案：失败即吞、下次重试。

事实四（运维论）：单进程内存是唯一不需要一致性的存储，多实例之前任何跨节点状态都是假承诺

停止标志、SSE 连接、远程工具实例在线表，全在 JVM 堆里。这不是疏忽，是当前部署形态的直接结果。若假装它们能跨实例，得到的是"偶尔停不掉、偶尔路由到已死实例"——比诚实地只支持单实例更糟。

它推翻了什么表面答案：先上 Redis 把状态"分布式化"，再考虑一致性。

4巧思全景

以下 12 项按"防住了什么不可靠性"排列，覆盖存储层、会话层、编排层、工具体系、模型层、鉴权层六个层次。

1越权边界写在"查哪些索引"上KbIndexes.java / DomainChannelProvider.java+

检索域 D 时，通道集合 = D 自身 + 全部祖先域，每个域各召回关键词与向量两路。文档归属由"上传到哪个域的索引"决定，metadata.domain 只用于管控台展示，不参与过滤。

server/knowledge/DomainChannelProvider.java
// 通道 = 域链 × 2 路；不在链上的索引根本不会被构造出来
List<Channel> channels() { /* 沿域链向上，逐域产出 keyword + vector */ }
为什么必然：事实一要求边界随业务结构走。用过滤条件（WHERE domain IN (...)）意味着每次新增字段、每次改 SQL 都有一次漏写的机会；用索引选择意味着漏写不可能——不存在的通道不会返回结果。
2全部通道失败 ≠ 没有相关内容CompositeRetriever.java:206-211+
java
if (succeeded == 0) {
    // 全部通道失败 ≠ 没有相关内容：这里若返回空列表，
    // "检索链路坏了"会和"真没命中"长得一模一样
    throw new IllegalStateException("知识库检索全部通道失败（通道数 " + channels.size() + "）");
}
为什么必然：事实二。这条 if 是整个 RAG 链路上最便宜的一行代码，也是唯一能把"配置错了"和"库里是空的"分开的地方。
3检查点读失败必须炸，不能当空列表RedisCheckpointSaver.java:253-270+

断点写入是"读全部 → 加一条 → 写回整份"。如果读失败被当成空列表，下一次写入就会把整段会话历史覆盖成一条，全程无异常，用户收到的是"会话不存在，请新建会话"。

java
private CheckpointCorruptedException corrupt(String key, Exception cause) {
    // fail-closed 与记忆侧一致：数据存疑时宁可不提供，
    // 也不能提供一份被清空过的"正确答案"
    return new CheckpointCorruptedException("检查点数据损坏，已中止本轮读写…", cause);
}
为什么必然：事实三。可恢复性的前提是"状态没被悄悄改过"。降级成空在这里不是容错，是数据销毁。
4写扇出、读只走 primaryFanOutStore.java:67-113+

多后端时写入扇出到全部 target（任一失败即整体失败），去重只问 primary，capabilities()、documents()、readByDocId() 全部以 primary 为准。删集合尤其严格：任一后端删不掉即整体失败，因为集合名是域路径哈希，域重建后同名集合会把旧知识原样复活。

为什么必然：事实二 + 事实一。"多副本"最容易犯的错是把读也摊开——副本落后就会让同一个域在不同请求里看到不同的知识，而这种不一致没有任何报错。
5切片原文剥离向量后当权威源ChunkArchive.java:70-94+

归档时把 vector 置空再落 JSON（768 维 ≈ 6KB/条，而重灌反正要重新 embed），载体是 BlobStore，键 kb/chunks/{index}/{docId}.json。归档失败只告警 + 打指标，由对账补写。

为什么必然：事实二。换嵌入模型 = 索引全废，此时"能不能取回原文"决定了这件事是一次重灌还是一次数据迁移。存向量等于存一份注定作废的复印件。
6撤销先于清除：心跳加不回来ToolDomainRegistry.java:97-113+
java
public void forget(Collection<String> domains) {
    synchronized (lock) {
        revoked.addAll(...);      // 先记撤销
        declared.removeAll(domains); // 再清声明
    }
}
为什么必然：事实一。顺序反过来的话，"剥离完成"到"记下撤销"之间的一次心跳就能把域加回来，删域当场失效——而且失败方式是"偶尔删不掉"，不报错、不留痕。
7可调用性：写入存意图，读取算生效DomainRegistry.java:436-446+
java
public boolean isCallable(String domainId) {
    Domain domain = domains.get(Domains.normalize(domainId));
    return domain != null && isEffectiveCallable(domain);
}
/** 生效的可调用性 = 显式标记 ∧ 无子域。读取侧一律走这里 */
private boolean isEffectiveCallable(Domain domain) {
    return domain.callable() && !hasChildren(domain.id());
}

落盘文件里只有"意图"（显式标记），"现在能不能当入口"是读取时派生的。写盘时反向写回生效值，保证文件、管控台展示、入口判据三者一致。

为什么必然：事实一。状态一旦有两个来源（标记 + 子域列表），就必须选一个作为唯一判据；把派生值也落盘，等于给自己留了一条"文件与内存不一致"的暗道。
8改密即吊销：密钥 = HMAC(主密钥, 密码哈希)CredentialService.java:102-105+
java
private byte[] deriveKey(AccountSettings account) {
    byte[] master = Base64.getDecoder().decode(account.getSigningKey());
    return hmac(master, account.getPasswordHash());
}

凭证本身无状态、不设有效期（payload = {sub, iat}），但签名密钥由密码哈希派生——改一次密码，全部旧凭证立刻失效，不需要任何吊销表。

为什么必然：事实四。单机部署不需要 token 存储；而"无状态"最容易变成"永远有效"，把吊销成本转移给运维。用密码哈希参与派生，等于把"改密"这个已有动作免费升级成全局吊销。
9单实例守卫：把进程内状态变成启动期契约SingleInstanceGuard.java:86-107+

启动时抢 Redis 租约，抢不到直接抛异常中断启动。理由写在代码注释里："多实例的失败方式是不报错的错误结果"。

为什么必然：事实四。既然停止标志、SSE、实例在线表都在堆里，多实例就会表现为"偶尔停不掉、偶尔路由到死实例"。与其让人在事故里发现，不如让第二个进程起不来。
10一轮一次 embed，全部向量通道复用CompositeRetriever.java:149-166+
java
if (queryVectorResolver != null && hasVectorChannel(channels)) {
    try { embedded = queryVectorResolver.embed(query.text()); }
    catch (Exception e) { failed = true; /* 向量通道降级，关键词照常 */ }
}

embed 失败时本轮向量通道全部标记失败、关键词通道继续，且整轮共享一个 deadline（域链深 5 = 10 条通道，按通道各等 5s 会拖到 50s）。

为什么必然：事实二 + 工程成本。一次 embed 失败不该让整轮检索抛异常（那会与"没命中"再次同形），但也不该每条通道各 embed 一遍。这里同时修掉了"失败语义"和"成本"两个问题。
11硬删级联：中止点必须落在还没有东西被删的位置DomainPurgeService.java:138-232+

顺序是：停/强杀在飞会话 → 清 Redis（记忆/检查点/归档/倒排/摘要）→ 删知识索引（同时 evict 检索器缓存）→ 清域属性（提示词/模型绑定/MCP 绑定/工具声明）→ 才删注册表条目 → 清软删标记并落盘。

为什么必然：事实三。级联删除失败后的重试必须安全，所以第一个可能失败的点必须出现在"什么都没删"的位置。反过来先删注册表，一次失败就留下"域已删、知识还在"的孤儿，而孤儿无人认领。
12适配三级降级 + id 字典序，确定性优先ModelAdapterRegistry.java:35-41+

模型名精确 → 模型名正则（全串匹配）→ 服务商 host；同级多个命中按 id 字典序取第一个，不依赖文件列举顺序。坏文件只记 ERROR 并跳过，不影响启动与其余文件。

为什么必然：事实二 + 可运维性。适配文件是 curated 数据，一个手误不该让服务起不来；但匹配结果必须确定，否则同一个模型在两台机器上可能套用不同参数，故障无法复现。

6代价与边界

代价一：一致性靠"人读懂注释"，不靠编译期

上面 12 项里有 6 项的成立条件是"调用方按约定走"：ChunkArchive 归档失败只告警（靠对账兜底）、ToolDomainRegistry.forget 的顺序、isEffectiveCallable 是唯一判据、FanOutStore 读只走 primary、KnowledgeStore 各方法的 fail-closed 姿态、SessionKeys 的键拼法。这些约定没有类型系统保护，写在新代码里的偏离不会被编译捕获。

代价二：fail-closed 的可用性账单

"读失败就抛"在测试环境很好看，在生产是一张账单：Redis 抖动一次，所有进行中的会话一起报 70004（检查点错误），而不是静默降级。项目用"单实例 + Redis RDB+AOF"作为对冲，但这意味着部署方必须把 Redis 当一级依赖维护。

代价三：抽象密度高，学习曲线陡

域的语义（沿链累加 / 就近覆盖 / 只有叶子可调用 / 软删宽限期 / 撤销态）分布在 DomainStore、DomainRegistry、ToolDomainRegistry、DomainPurgeService 四处，新人要同时读四个文件才能回答"删了这个域会怎样"。抽象省掉了租户表，但把复杂度转移到了概念数量上。

边界：多实例之前，这些巧思有一半要重写

CancellationRegistry、StreamSinkRegistry、InstanceRegistry 是纯内存态；SingleInstanceGuard 只是把这条限制显式化，并没有解决它。真要水平扩展，停止语义、SSE 续传、实例路由三处都得改成"跨节点可寻址"，而不是把 Map 换成 Redis 就完事——因为"等它真的停下"这类操作在分布式下需要的是协调，不是共享存储。

7结论

这个项目的设计密度不在"用了 LangGraph4j"或"上了虚拟线程"，而在于它把四个很朴素的事实各自推出了必然结论，并且愿意为结论付代价：

  1. 边界是结构，不是参数——所以有域树、一域一索引、(域, sessionId) 会话键。
  2. "不知道"和"出错了"必须分开——所以有一整套 fail-closed 姿态、全通道失败抛异常、错误码 11 个段位。
  3. 状态可以丢，但不能撒谎——所以检查点读失败要炸、记忆先记锚点再写、SSE 关掉容器超时并校验终止事件。
  4. 没做到的事要显式承认——所以有单实例守卫：第二个进程起不来，而不是起来后偶尔出错。

反过来说，这套设计最脆弱的地方也在这里：它的正确性依赖"后来的人继续按约定走"。12 项巧思中，注释承担了 6 项的约束力——这是这个项目最值得补的一件事，比再拆一个类更重要。
