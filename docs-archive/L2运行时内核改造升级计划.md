##### 1. 约束与难点

**难点一 · 2,544 行不是"堆出来的"，是 5 类职责被一条主流程串住。** 拆不动的真正原因是**跨职责共享局部变量**——`memorySizeBefore` / `turnId` / `graphStarted` / `StreamContext` 四个量贯穿全程，且必须在 `try` 之外声明（`catch` 要靠它们收尾）。按方法归类的现状切面：

| 切面 | 代表方法 | 约行 | 去向 |
| --- | --- | --- | --- |
| 构造器阶梯 | 8 个 `AgentOrchestrationService`（最长 16 参） | 195 | 第 3 步消掉 |
| 图（构建/节点/路由/等模型/解模型） | `buildGraph` `messagesSchema` `syncNode` `agentNode` `awaitAiMessage` `toolsNode` `routeAfterAgent` `resolveModel` | 424 | `AgentGraphFactory` |

| 本轮上下文胶水 | `systemMessageOf` `windowOf` `buildSummarySegment` `buildCardsSegment` `assemblerFor` | 170 | `TurnContextFactory` |

切面按方法归类、区间相互交错（收尾与失败矩阵都散在 1827–2527），**切分必须按方法搬，不能按行块切**。

**难点二 · 最大的一条误判：它其实已经可测。** 设计文档 7.13 写"依赖 Redis/ES/模型三件外部设施，只能端到端验"——这条现在是错的，而正是它让 P0 一直显得做不动。实测可测性：

- 构造器只强制三项非空（`promptResolver` / `executor` / `stateSerializer`），其余可传 `null`；
- `executor` 可传 `Runnable::run` → 同步执行，`Flux.create` 直接推完，不需要线程池与 Reactor 调度；
- **langgraph4j-core 1.8.17 自带 `org.bsc.langgraph4j.checkpoint.MemorySaver`**（已核对 jar 条目）→ 断点存内存，`interruptBefore` 与 `resume` 能在纯 JVM 里完整跑；
- 可选依赖（归档 / 摘要 / 检索 / 媒体暂存 / 装配清单 / 模型解析）**全部有判空**（`conversationArchive` 6 处、`rollingSummaryService`、`historySearch`、`modelResolver`、`mediaAttachmentStore`）→ 传 null 即退化为"不摘要、不归档、不检索"的旧行为；
- **先例已经在**：`AgentChatPendingDeleteGateTest`（144 行）就是这么 new 出 Service 的，它跑的是 `chat()` 的前两道闸门。

**难点三 · 拆分的前置不是"先补单测"，是先消构造器阶梯。** 8 个构造器、最长 16 参、25 个字段。不先把装配收成一个对象就开拆，每个新类都要把 16 个参数再传一遍——拆完只是把 2,544 行挪成 5 个文件，耦合原样保留。

**难点四 · 虚拟线程不是"换个 Executor"就完。** 现在 core=8 的平台池同时承担了**并发闸门**职责（池满 → `RejectedExecutionException` → `SYSTEM_BUSY`）。虚拟线程没有队列上限，不加显式闸门等于把背压交给内存。

##### 2. 决策一：四步拆分（前三步零行为变化）

1. **建测试台 `OrchestrationHarness`（runtime 测试域，非生产代码）**：`ScriptedStreamingChatModel`（在 `chat(ChatRequest, StreamingResponseHandler)` 里同步回调 `onPartialResponse` / `onCompleteResponse`，脚本可编排"吐 token → 带工具调用 → 终结"多段）+ `MemorySaver` + 内存 `ChatMemoryProvider` + `Runnable::run`，其余依赖传 `null`。**先钉现状行为，再动结构**——这一步不碰生产代码。
2. **抽执行模板 `runTurn(...)`**：`runOrchestrate`（310 行）与 `runResume`（127 行）的"门禁（`tryMarkRunning` → `SESSION_BUSY` 且先注销后 complete）+ `TraceId.begin/end` + `TokenUsageRecorder` + `finally` 三件套（`clear` / `unmarkRunning` / `unregister`）"完全相同，差异只在 body。抽成模板后两个入口各留一个 body。**这是拆分里唯一可以闭眼做的一步**：零行为变化，且把"两处改一处漏一处"的风险一次消掉。
3. **装配收 `OrchestrationDeps`**：不可变载体（record）+ 单个主构造器；旧 7 个构造器先保留为委托并标 `@Deprecated`，核完引用再删（server `GraphConfiguration` 与既有测试是主要调用方）。消掉 195 行机械代码，同时给后续拆分一个可整体传递的依赖包。
4. **切 4 个协作者**（同包 `runtime.orchestration`，先包私有、需要时再提接口）：
   - `AgentGraphFactory` — 图构建 + 三个节点 + 条件边 + `awaitAiMessage` + `resolveModel`
   - `TurnLifecycle` — 9 个 `*Quietly` + `rememberFinalAnswer` + `restoreMemory` + `finalizeTurnOnFailure`
   - `TurnContextFactory` — `assemblerFor` + 系统提示 + 窗口 + 摘要段 + 卡片段（**装配胶水，不改 `ContextAssembler` 的纯函数边界**）
   - `TurnInputFactory` — 多模态入参：内容块校验 / 视觉路由 / 暂存 / notice 拼装

   留在 Service 里的只剩：入口（`chat` / `orchestrate` / `resume` / `stop`）+ 执行模板 + 失败矩阵分派。

##### 3. 决策二：虚拟线程与并发闸门

- 编排执行器换成 `Executors.newVirtualThreadPerTaskExecutor()`（每轮一个虚拟线程），`AgentProperties` 的 core/max/queue 保留为**兜底配置**（切回平台池的开关），不再承担并发上限语义。
- **补显式并发闸门**：信号量（默认取 CPU 与配置的较小值，建议初值 200）+ 有界等待队列；超限时仍发 `SYSTEM_BUSY`（码与文案不变）。没有它，"服务过载"会从快速失败变成 OOM。
- 结构化并发**不做**（Java 21 preview）。现有"分片等待 + 总 deadline"已经覆盖了它想解决的"子任务泄漏"问题：一轮就是一个虚拟线程，跑完即终。

##### 4. 决策三：与 F13 的边界

F07 侧只做**收敛**，不做外置：把所有会话运行态限制在 `CancellationRegistry`（停止标志 / 执行中标记）与 `StreamSinkRegistry`（SSE 上下文）两个出口，**不再新增第三处进程内状态**。外置方案（Redis + 发布订阅，stop 广播到持有会话的节点）与 F13 同波设计。F07 提前要定的一件事：跨节点后 stop 从"内存可见"变成"至少一次投递"，**命中不到任何本地会话时的返回语义**要先定（建议仍返回 `true` 并 WARN，否则前端会把"打到别的节点"当成停止失败）。

##### 5. 代价与坑

- **节点与外层的耦合点在 `RunnableConfig.metadata(CTX_METADATA_KEY)`**：`StreamContext` 经它跨节点传递（`GraphContextCarryingTest` 钉着）。拆 `AgentGraphFactory` 时必须把这个隐式契约显式化（方法参数或显式的 context 解析函数），**不能变成"两个类都去读 metadata"**——否则拆完耦合更隐蔽。
- **拆分的验收不是"行数变小"，是"行为零变化"**：以测试台用例为准逐个重跑，另做一次真实环境冒烟（chat / 1 秒内 stop / 审批中断 + resume 批准与拒绝）。
- **`awaitAiMessage` 的 200ms 分片等待在虚拟线程下照样是阻塞**（会被卸载、不占载体线程，这是好事），但**绝不能顺手改成 `future.join()`**——那样停止标志再也没机会被读到，会话会被永久占住（设计文档 7.3 那条）。
- **`CancellationRegistry.prepareNewRound` 是 `synchronized`**：JDK 21 虚拟线程在 synchronized 内阻塞会 pin 载体线程；它本身不阻塞所以无害，但**绝不能往里面加任何 IO**。
- **停止检查共 5 处**（三处模型回调 + `awaitAiMessage` 分片 + `toolsNode`），比设计文档记的"三处"多两处；拆分时漏搬任何一处，现象都只是"停止偶尔不灵"。
- **超时配置化牵三个时钟**：`MODEL_WAIT_LIMIT` 与 F04 检查点 TTL、F03 软删宽限期同族（都是"这一轮能活多久"），改一个要评估另外两个。
- **不要动 `AgentService` 接口签名**：chat-client 的 `AgentServiceClient` 是第二个实现（设计文档待办 #5），改签名要同步两处 SDK。
- `releaseCheckpointQuietly` 对 `checkpointSaver == null` 没有判空，靠外层 `catch (Exception)` 兜住（不炸、只刷 warn）。拆分时补判空，别把"静默警告"带进新类。

#### F10 附注：从"替用户声明"改成"用户声明、我透传"

**约束与难点**——为什么放弃"每家写一份适配"：

厂商的参数面一直在变（新参数、旧参数改名、同名不同义），而我们既没有足够的人去逐个实测，也没有办法保证写进去的 `min/max/step/options` 是对的——**27 份文件被刻意禁用，本身就是这条路线做不动的证据**。继续往里加只会得到更多"看起来配了、实际没人验证过"的声明，这比没有更糟（F05 定的纪律：配了像没配是绝对禁止的）。

第二个难点是**透传的边界**：参数面交给用户，不等于请求体的每一处都交给用户。模型名、地址、协议、凭证必须仍由平台掌握——一旦用户能塞 `model` 或覆盖鉴权头，"档案"就不再是可信的配置单元，删域/审计/热替换全部失据。

第三个难点是**标准参数会"发两遍"**：`temperature` / `max_tokens` 这类标准参数走 builder setter（构建期），而 `customParameters` 是请求体另一条路；用户在文本框里填 `temperature`，两条路同时发同一个字段——现有注释已明确警告这种情况。

**决策**：

1. **只留一个 DeepSeek 适配**，它的定位不是产品能力，是**活样板 + 回归样本**：三级降级匹配、`enabledWhen` 条件参数、`wireWrap` 包装（`response_format: {type: ...}`）、`display: bar` 这些 schema 能力都要有地方被测试和演示。其余 29 个移入 `adapters/disabled/`（保留作为将来官方适配的素材，不删、不启用）。
2. **加载器 fail-loud**：统计"扫到 / 成功 / 跳过"，扫到 0 个打 WARN。只剩一个文件的状态下，这条日志是唯一的保险丝。
3. **放开透传**：未命中适配的档案允许 `params` 非空（现在拒绝），`effectiveParams()` 的未命中分支原样下发即可——**服务端几乎不用改，主要工作在校验与前端**。
4. **透传的四道闸门**：① 黑名单——禁止 `model` / `messages` / `stream` / 鉴权相关键 / 与地址协议相关的键；② 类型——只收标量、字符串数组与一层简单对象，拒绝嵌套结构与超长字符串；③ 量——键数上限（建议 32）与整体体积上限（建议 4KB）；④ **标准参数冲突即拒绝**——文本框里出现 `temperature` / `top_p` / `max_tokens` / `presence_penalty` / `frequency_penalty` / `seed` / `stop` / `response_format` 等标准键时，保存报错并提示"请用上面的标准字段"。理由：与其让两条路静默发两遍，不如在保存时把话说清楚。
5. **协议先 OpenAI、后 Anthropic**：档案加 `protocol` 字段（下拉二选一，默认 openai），`ModelClientFactory` 按协议分派到 `OpenAiChatModel` 或 `AnthropicChatModel`；`langchain4j-anthropic` 依赖已就绪，这一步是"接线"不是"引依赖"。切换协议时**清空或提示重填自定义参数**——同一个 `max_tokens` 在两种协议下语义与必填性都不同。
6. **自定义请求头**：档案加 `customHeaders`（键值表，值按敏感字段处理），发请求时拼上；先验证 LC4j 1.18.1 两侧 builder 是否都支持 `customHeaders`，不支持就走 HTTP client 层补。

**代价与坑**：

- **"未命中适配"从此是常态，不再是异常**。当前代码注释写"正常应为空、保存时已被拒绝非空"，把它当异常路径；新路线下 30 个模型里 29 个走这条。它的测试从"没有"变成"必须有"。
- **错误要原样回传**：用户参数填错时，服务商返回的 400 必须原样（含厂商原始文案）回到管控台，不要包装成"平台错误"——包装了用户就不知道是自己填错，会当成平台 bug 报过来。
- **自定义字段是新的敏感面**：用户很可能把 API Key 塞进自定义 header 或参数值。展示、日志、导出全部要掩码（与 blob 的 AK/SK、`accounts.json` 同族），`InputSanitizer` 那一套在配置侧要同样对待。
- **协议切换会让自定义参数失效**：OpenAI 的 `max_tokens` 可选、Anthropic 的 `max_tokens` 必填，字段名相同语义不同。切换时若不清空，用户会看到一个"我明明填了却不生效/报错"的黑盒。
- **只留一个 adapter 后，匹配命中面极小**：`match.hosts` 只有 `api.deepseek.com`，其余全部走未命中分支。别把这个样板反过来当成"DeepSeek 之外的服务商都不支持"——它们支持，只是参数由用户自己填。
- **`.json.txt` 归档进 `disabled/` 后要确保不被扫到**：`classpath:adapters/*.json` 只扫当前目录，子目录天然不进；但如果哪天改成递归 glob，`disabled/` 会被重新扫进来。**加载计数这条断言要钉住"29 个归档文件不参与加载"**。

**实施步骤**：

1. 建 `adapters/disabled/`，把 29 个文件移进去（保留 deepseek-flash.json 在原位）；`git mv` 留痕，不删历史。
2. 加载器加"扫到 / 成功 / 跳过"计数与空列表 WARN。

4. 前端模型卡片加「自定义参数（JSON）」文本框（含解析错误提示、上限提示、标准键冲突提示）。
5. `protocol` 字段回归（默认 openai）+ 下拉；`ModelClientFactory` 按协议分派；切协议时清空自定义参数并提示重填。

#### 横切附注：特殊格式文件的存储抽象（本地默认 + 可选远程）

**落地状态（2026-10-24）**：第一波（媒体侧拆弹）已完工——`BlobStore` SPI（runtime.storage）、`LocalBlobStore`（server.storage，默认，根目录走 `StorageLocations.blobDir()` / `domainplane.storage.path`）、`BlobMediaAttachmentStore`（登记表留 Redis + 字节进 blob，老格式存量回退读）、`MediaBlobSweeper`（孤儿回收，默认 5 分钟间隔 + 5 分钟竞态护栏）、`MetricsRegistry` 四个回收计数（blobSweeps / blobsScanned / blobsReclaimed / blobSweepFailures）。新增测试 46 例全过（LocalBlobStoreTest 8 / BlobMediaAttachmentStoreTest 19 / MediaBlobSweeperTest 8 / RedisMediaAttachmentStoreTest 11）。第二波（`S3CompatibleBlobStore` + 管控台"存储配置"页）仍随 F13，未动。

**本轮范围**：对话媒体（图/音/视）暂存区。文档原文（决策 3 及约束段中的知识库部分）保留至知识库波次（F05/F06）再施工，本轮不展开、也不删除。

**约束与难点**——为什么图片/视频/各种文档要单独抽一层存储：

特殊格式文件现在有两个互不相干的落点，且都不合适。**对话媒体（图/音/视）在 Redis 里存 base64 大 value**——上传上限 5MB，base64 后约 6.7MB 一条，Redis 单线程被大 value 卡住时所有命令一起等，这是生产隐患，现在靠 30 分钟 TTL + 活动续期兜着而已。**知识库文档上传后原文直接丢弃**（`KnowledgeBaseService.upload` 收 byte[]，ingest 完只留 ES 切片文本和切片预览 txt）——OCR（F06 P0）、换向量模型重建（现有"捞回原文"捞的其实是切片文本，不是原文件）、语义分块（F05）全部卡在"没有原文"上。

与 F03 是同一种哲学的两个面：F03 回答了"配置类小文件本地权威、不引外部存储"，本条要回答镜像问题——**二进制大对象默认本地零依赖，用户显式配置 OSS/COS 才走远程**。多实例（F13）下本地磁盘不共享，远程存储与 F03 的版本信号共同构成多实例前置。

还有一组容易混的生命周期：**媒体附件是暂存区**（分钟级，可过期，本来就不是记忆），**文档原文是档案**（与"原始记忆不主动删除"同族，不主动删）。同一套 SPI，两套保留策略。

**决策**：

1. **SPI 形态**：runtime 定义 `BlobStore`（put/get/delete/exists + 流式读写），server 出两个实现——`LocalBlobStore`（默认，落 `StorageLocations` 下按用途分目录）与 `S3CompatibleBlobStore`（OSS/COS/MinIO 全部 S3 兼容，**一个实现覆盖三家，不按厂商各写一个**）。`MediaAttachmentStore` 接口不动，新实现 `BlobMediaAttachmentStore` 内置存量回退读（先查登记表，未命中再查旧格式 key），单 bean 注入——编排层与 `VisionConfiguration` 接线无感，旧 `RedisMediaAttachmentStore` 退位为只读兼容路径，新写入走 BlobStore。
2. **登记表与字节分离**：暂存区对象键沿用现有内容哈希引用名规则（`img_xxx`），但**只有字节搬去 BlobStore，登记表留在 Redis**（引用名 → kind/mime/blobKey/expiresAt，小 value）。TTL 与 touch 续期继续吃 Redis 原生能力，编排层 `renewActiveAttachments`（每轮按近况窗口给活跃引用续期）零改动——迁出 Redis 的只是大 value 这个生产隐患，不是整套暂存机制。**反直觉点：远程模式下"续期"不是一条 EXPIRE，S3 改对象元数据要整对象重新拷贝一遍**；拆开之后续期只动登记表，字节一次写入不再回头。代价是两份数据要对齐：登记表一过期字节就成孤儿，回收扫描从"可选优化"变成"正确性必需"（见代价段）。
3. **文档原文保留**：ingest 成功后原文进 blob（键 = docId + 原始文件名），ES 切片 metadata 记原文键，管控台文档列表提供"下载原文"。F05/F06 的 OCR、语义分块、向量重建全部改为从原文取。
4. **管控台新开"存储配置"页**（F14）：provider 单选（本地 / OSS / COS / S3 兼容）+ endpoint/bucket/region/AK/SK + **连通性测试**（写入-读回-删除一个小对象）+ 密钥落盘加密、界面只显掩码、日志禁打（与 `accounts.json` 同族的敏感配置）。
5. **切换语义**：配置切换只影响新写入，旧数据留在原处——明确告知用户，不假装无缝；"存量迁移工具"列为后续项，不进第一版。

**代价与坑**：

- **孤儿回收是本次交付物，不是附属优化**：字节侧没有原生过期，登记表一过期 blob 就成孤儿——本地烧磁盘、远程烧钱，且都是静默的。兜底扫描（以登记表为权威，回收"无登记对应关系"的 blob；本地按目录列举、远程按前缀 LIST）随 `BlobMediaAttachmentStore` 一起交付，不等 F13；必须可观测（扫了多少、删了多少、失败多少），漏跑一天就多烧一天。事件驱动（Redis 过期键通知）只能当快车道——丢事件、副本不发射过期事件决定了扫描才是保底，列为后续优化。
- **双倍磁盘峰值**：远程模式下"落地再传"让上传峰值翻倍；第一版接受（流式直传/multipart 拆后续），但大文件场景必须在文档里写明，别让用户以为配置了 OSS 就没有本地磁盘压力。
- **密钥是新敏感面**：AK/SK 加密落盘 + 掩码显示 + 日志禁打；输入侧已有 `InputSanitizer`，配置侧要同样对待，不能只防用户消息不防运维配置。
- **别把 `domains.json` 塞进来**：它是权威配置不是二进制大对象，归 F03 的本地文件 + 版本库管。两条线各管各的——混用会让"权威"变成"可能存在于远端的一份额本"，F03 的三级恢复链全部失效。
- **分两波落地，别整捆绑死**：媒体侧拆弹（登记表留 Redis + `LocalBlobStore` + 孤儿回收）不依赖任何远程服务、也不依赖多实例，先落地先拆雷；S3 兼容 provider + 管控台"存储配置"页与 F13 同波——远程存储的价值全在多实例（本地盘不共享），单机部署下本地零依赖够用。与 F03 附注同款结论：远程那半波提前单独做收益有限，本地那半波没有等的理由。
