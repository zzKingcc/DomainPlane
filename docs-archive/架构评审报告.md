## 1. 方案概述

### 1.1 背景

问题不是"做一个 Agent"，是**多个业务场景要不要各部署一套 Agent 服务**。

走"一场景一服务"的老路，代价是：每套都要重复实现工具体系、知识检索、会话记忆、模型接入、多模态、管控台；且这些能力的实现会各自漂移，半年后就变成六个互不兼容的 Agent 服务。走"一个大而全的 Agent 服务 + 租户表"的老路，代价是租户维度要渗透进每一个查询、每一次装配，以及所有历史数据都要带上租户键做清理。

DomainPlane 选的是第三条：**把"域"做成一个点分路径字符串，用它同时承载归属、继承、权限和状态键**，服务端在一个进程里跑，每轮对话带域进来，服务端沿域链实时把工具 / 知识索引 / 提示词 / 模型四维能力装配到这一轮。

### 1.2 目标

由代码可验证的四条：

1. **一实例多场景**：同一进程服务多个业务场景，隔离靠域，不靠部署。
2. **装配而非配置**：能力按"本轮域"裁剪，改域即改行为，不重启、不改代码。
3. **能力缺失显式失败**：越权、模型不具备视觉、依赖未配置，一律报错码，不静默降级。
4. **后端可替换**：换向量库 / 存储不触碰编排内核。

第 1、2、3 条已达成；第 4 条**达成了一半**（见 3.2 关注点 1）。

### 1.3 方案架构

实测模块依赖（口径：各模块 `pom.xml` 的内部 `<dependency>`）：

```text
domainplane-api             → 无内部依赖
domainplane-common          → api
domainplane-domain          → common
domainplane-infrastructure  → common + domain
domainplane-runtime         → api + common + domain      ← 与 infrastructure 并列
domainplane-server          → api + common + domain + infrastructure + runtime
sdk-core                    → api + common
client-core                 → sdk-core
chat-client / kb-client     → client-core
tool-provider               → sdk-core
```

真实形状是：

```text
api ← common ← domain ← { infrastructure , runtime } ← server
```

三个 SDK 自成一支，只走 HTTP，从不接触 runtime / server。

### 2.1 技术架构

| `domainplane-common` | 16 | 1,327 | 异常体系、输入清洗、CJK 度量、指标、原子落盘 |
| `domainplane-domain` | 32 | 2,347 | 纯领域算法与 SPI：记忆双约束、检索编排、融合、存储契约 |
| `domainplane-infrastructure` | 60 | 8,667 | 对外部世界的全部实现：ES / Qdrant / Redis / 8 种格式摄取 |
| `domainplane-runtime` | 46 | 8,134 | 编排引擎、工具体系、上下文装配、取消与流 |
| `domainplane-server` | 149 | 26,264 | 装配 + 管控台 + 鉴权 + 模型层 + MCP + 知识库服务 |
| SDK 五模块 | 27 | 2,646 | 只走 HTTP 的消费侧 |

### 2.2 部署架构

| 维度 | 现状 | 约束来源 |
| --- | --- | --- |
| 实例数 | **强制单实例** | `SingleInstanceGuard` 启动期抢 Redis 租约（TTL 90s），抢不到即中断启动 |
| 外部依赖 | Redis（必需）、Elasticsearch（知识库必需） | 均可在管控台热切换，不重启 |
| 落盘 | `settings.path` 下 8 份 JSON | 账号 / 模型 / 域 / 提示词 / MCP / 存储连接 |
| 对外 | HTTP + SSE，15 个 Controller / 89 处方法级 Mapping | 无 OpenAPI |
| 定时任务 | 6 个 `@Scheduled`（指标采样 / 实例心跳 / MCP 对账 / 域清理 / 版本巡检 / chunk 归档对账） | 全仓 grep |
| 配置面 | `application.yaml` 301 行 / 约 114 个叶子键 | 无统一全量表、无 `configuration-metadata` |

单实例不是"还没做"，是**当前设计的一部分**：`CancellationRegistry`、`StreamSinkRegistry`、`InstanceRegistry` 三个注册表全部住在 JVM 堆里，一轮对话的"停止"和"推流"都靠本进程内存指针。守卫的作用是把这条隐含约束显式化——宁可在启动期炸，也不要在多实例下"停止只停了一半"这种不报错的错误结果。

### 2.3 数据架构

按生命周期分三类，这条分类是整个项目最值钱的一条工程判断：

| 类别 | 承载 | 生命周期 | 可重建 |
| --- | --- | --- | --- |
| **真相** | 会话记忆（`domainplane:chat:memory:*`）、按轮归档（`domainplane:chat:archive:*`）、切片原文（`kb/chunks/{domainHash}/{docId}.json` → BlobStore） | 只增不减，**无 TTL** | 否，删即丢 |
| **派生** | 倒排索引（30 天 TTL）、向量索引、摘要 | 可重算 | 是，换后端/换模型 = 一次重灌 |
| **暂存** | 媒体引用（30 分钟 TTL）、检查点（24h TTL） | 到期自清 | 否，但丢了只坏一轮 |

这个划分决定了"换向量库"是**一次重灌**而不是**一次数据迁移**——前提是切片原文落在权威源里，而它确实落了（`ChunkArchive` → `BlobStore`）。这是本次升级里做得最对的一件事。

## 3. 评审意见

### 3.1 优势

**一、越权边界是结构性的，不靠过滤条件。**

检索域 D 时只查 D 自身与祖先链上的索引（通道 = 域链 × 2 路），文档归属由"上传到哪个域的索引"决定，`metadata.domain` 不参与过滤。含义是：**漏写一个 `WHERE domain = ?` 不会造成越权**——越权需要"查错索引"，而索引名由域路径确定性派生。同理，工具可见性在装配期按域裁剪、执行前再复核一次。

代价是放弃了"一条索引查所有域再过滤"的灵活性（跨域统计、全局搜索都得遍历索引），换来的是权限 Bug 的失效模式从"静默泄露"变成"查不到"。对一个多业务共用实例的中间件，这个交换是值的。

**二、内核不认识外部世界。**

`domain` 只有 32 个类，全是纯算法与 SPI；`runtime` 全文没有 `infrastructure` 依赖。所以"ES → Qdrant"这件事在代码里表现为"新增 `kb/qdrant` 包 + 注册一个 backend"，编排内核零改动。**副作用是这条约束可以被机器验证**——`pom.xml` 里没有这条依赖，谁想破坏它都要显式加一行，review 时看得见。

**三、"失败"与"空结果"永不混淆。**

凡是二者会长得一样的路径，一律抛异常而不是返回空：检索全部通道失败 → 抛（否则调用方会换个问法反复试，而不是去查配置）；`KnowledgeStore.exists/delete/write` 全 fail-closed；检查点读失败 → `CheckpointCorruptedException`；域配置损坏时禁止覆盖写（写回等于抹掉全部人工域）。

这是整个代码库最一致的一条工程纪律，也是它跟"能跑起来的 demo"最大的区别。

**四、存储真相与呈现预算解耦。**

记忆只追加、不淘汰（默认永久），"这轮给模型看多少"完全由装配预算决定（24k token，近况 8 轮 / 摘要 2k / 卡片 5 张，逐级降级，**永不拒绝开轮**）。

老做法是在写入侧做窗口截断，代价是"昨天说过的话"永久消失且不可追溯；这里的做法是**写入侧不裁剪，读取侧按预算裁剪**，模型看到的是投影，归档里是全量。这让"回溯历史"和"扩大上下文"都变成可配置项，而不是数据恢复问题。

**五、升级路径留下了可验证的测试台。**

`OrchestrationHarness` + `ScriptedStreamingChatModel` + `MapChatMemoryStore` 让编排能在纯内存里跑完整轮次（含审批中断与 resume）。这一条的价值不在于覆盖率，而在于把"编排只能端到端验"这句原本成立的判断变成了不成立——1,203 行的核心类现在可以被单测逼着改。

### 3.2 关注点

| # | 问题 | 严重度 | 证据 | 建议 |
| --- | --- | --- | --- | --- |
| 1 | **外壳偏胖且开始回吸**："存储后端可替换"只兑现一半 | 高 | `server` 占主代码 50.3%（149 类 / 26,264 行）；**7 个 server 文件直连 `co.elastic.clients`**：`knowledge/ChunkExporter`(5 处，绕过 `KnowledgeStore` 直接 search)、`controller/AdminController`、`config/EsClientConfiguration`、`config/SwappableElasticsearchTransport`、`knowledge/KnowledgeBackendsConfiguration`、`settings/InfraSettingsHolder`、`advice/ServerGlobalExceptionHandler` | 换后端时这 7 处要单独改，SPI 之上又长了一条旁路。把 `ChunkExporter` 改成走 `KnowledgeStore`，ES 专属能力收进 `capabilities` 或 `EsKnowledgeStore` 内部 |
| 2 | **接口下沉、实现上浮（分层方向反了）** | 中 | `BlobStore` 接口定义在 `runtime/storage/BlobStore.java`，唯一实现在 `server/storage/LocalBlobStore.java` | 内核定义存储接口、外壳提供实现——依赖方向反了。接口应落 `api` 或 `domain`，实现落 `infrastructure`；否则 `runtime` 无法自测，`infrastructure` 也无法提供第二实现 |
| 3 | **单实例是硬约束，且不是配置项** | 高 | `CancellationRegistry` / `StreamSinkRegistry` / `InstanceRegistry` 均在 `runtime` 内存；`SingleInstanceGuard` 启动期租约拦截 | 多实例化 = 重写这三处状态出口（转 Redis pub/sub 或 DB 游标），不是加个开关。当前 `single-instance-guard: false` 可绕过守卫，但绕过后的行为是**未定义的**——建议把该开关的更名或加注释，明确它只用于"临时接管"，不是"支持多实例" |
| 4 | **域语义分散三处，靠装配顺序与注释维系** | 中 | 声明在 `DomainStore`、生效判据在 `DomainRegistry.isEffectiveCallable`、工具声明史在 `ToolDomainRegistry` | 三者一致没有编译期约束，改错一处不报错，只在边角暴露（例如心跳把撤销的域加回来）。至少补一个跨三者的不变量测试 |
| 5 | **并发正确性缺口：软删标记表是裸容器** | 高 | `DomainStore.pendingDeletes` 为 `LinkedHashMap`，全类零 `synchronized`；写侧在 `markPendingDelete` / `commitRollback` / `restore`，读侧正是**开轮软删闸门** `isPendingDelete` | 写时读会抛 `ConcurrentModificationException` 或读到半更新状态，表现为"偶发的域被误判"。换 `ConcurrentHashMap`（`Map.copyOf` 已是快照语义）成本极低，收益是把一个不可复现的偶发问题降级为不存在 |
| 6 | **巨型类 + 单块端点面** | 中 | `AdminController` 1,512 行 / `AdminModelProfileController` 1,381 行 / `AgentOrchestrationService` 1,203 行；15 Controller、89 处方法级 Mapping | 编排侧已拆出 7 个协作者（65–504 行量级），再往下切只剩"掏空编排"或"删兼容构造器（破坏性）"两条路，**需要拍板**；管控台侧建议按资源拆 Controller，顺带出 OpenAPI |
| 7 | **契约只存在于 Java 侧** | 中 | 60 个 `ErrorCode`、8 种 `AgentEvent` 只有 Java 枚举；无 OpenAPI / 无 SSE schema / 无错误码字典 | 非 Java 接入方（Node / Python / Go）无入口，只能读源码猜报文。这是"生态形态"问题，不是"文档"问题——契约文件（`domainplane-wire`）是唯一可自动化的出口 |
| 8 | **可观测性几乎为零** | 中 | `MetricsRegistry` 是自研内存计数（进程内、重启即清零、无导出端点以外的形态）；6 个定时任务；SDK 无 trace 透传 | 跨进程排障只能靠日志时间拼接。Micrometer + OTel 是 F07/F08 可观测项的前置，也是"多实例后仍能定位一条会话"的前置 |
| 9 | **版本与发布形态** | 中 | Maven `version` 为 `v1.0-beta.2`（**带 `v` 前缀**，Maven 版本比较会退化成字符串序，`v1.0-beta.10` < `v1.0-beta.2`）；未发 Maven Central，接入方必须自建 | 去掉 `v` 前缀、改用 `1.0.0-beta.2`；发布仓库缺失要么补，要么在 README 明确"只支持源码内构建"（README 已写，但版本号仍会误导） |
| 10 | **测试结构偏斜 + 4 个测试被停用** | 中 | 测试 179 类 / 25,228 行，但 `server` 与 `infrastructure` 占 66%；`controller/AdminModelAdapterControllerTest.java.txt`、`AdminModelProfileAdapterTest.java.txt`、`model/ModelAdapterRegistryTest.java.txt`、`ModelClientFactoryAdapterTest.java.txt` **被改名为 `.java.txt` 以跳过编译** | 改名的 4 个测试正好覆盖"模型适配"这条刚改过的路径，等于把回归网开了口子。要么修好启用，要么在文档里登记为已知缺口（不能只靠文件名藏起来） |
| 11 | **仓库卫生** | 低 | 根目录 50+ 个 `mvn-*.log|txt`（最大 586 KB）全部未跟踪、未 ignore；`tools/` 下 80+ 临时 `.txt`；`.dockerignore` 为 0 字节 | 一次 `git add -A` 就会把 3 MB 日志提交进去。补 `.gitignore` 规则即可 |

### 3.3 风险评估

| 风险 | 影响 | 概率 | 应对 |
| --- | --- | --- | --- |
| 业务上量后要求多实例 | 高（不是扩容问题，是"停止/推流"语义要重写） | 高 | 提前把三个内存态注册表收敛到两个明确出口（现在已收敛），再评估 Redis pub/sub 化 |

## 4. 可调整优化建议

按"改完之后能删掉多少后续麻烦"排序，不按工作量排序。

### P0 · 结构性（不改会持续产生新的债）

| 项 | 动作 | 落点 | 判据 |
| --- | --- | --- | --- |
| 存储收口 | `ChunkExporter` 改走 `KnowledgeStore`；ES 专属查询收进 `EsKnowledgeStore` 或 `capabilities` 分支 | `server/knowledge/ChunkExporter` | server 里 `co.elastic.clients` 的 import 从 7 个文件降到 3 个以内（连接/交换/异常映射属合法） |
| 分层归位 | `BlobStore` 接口搬到 `api` 或 `domain`，`LocalBlobStore` 落 `infrastructure` | `runtime/storage` → `api.storage` | `runtime` 不再持有存储接口；`infrastructure` 可提供第二个实现 |
| 并发修正 | `DomainStore.pendingDeletes` 换并发容器 | `server/settings/DomainStore:87` | 开轮闸门读路径无锁安全 |
| 状态出口文档化 | 把三个内存态注册表 + 单实例守卫写成一张"多实例改造前置清单" | 设计文档 F13 | 后来者能一眼看出多实例化要动哪几处 |

### P1 · 一致性（成本低、消除隐性分叉）

| 项 | 动作 |
| --- | --- |
| 域三处不变量 | 补一个测试：`DomainStore` 声明 → `DomainRegistry.isEffectiveCallable` → `ToolDomainRegistry` 三者在删域/撤销/心跳三种操作后的期望态 |
| 注册 Controller | `AdminController` 按资源拆（settings / models / infra / prompts / kb 已具备边界），顺带产出 OpenAPI |
| 恢复被停用的 4 个测试 | 修 `AdminModel*AdapterTest` / `ModelAdapterRegistryTest` / `ModelClientFactoryAdapterTest`；短期未修则在文档登记为已知缺口 |
| 版本号规范化 | `v1.0-beta.2` → `1.0.0-beta.2`，同步 README / Dockerfile 标签 |

### P2 · 工程化（补齐"生产可用"的地基）

| 项 | 动作 |
| --- | --- |
| 可观测性 | Micrometer + OTel 三支柱；至少先做"一轮对话的 span"（chat → 装配 → 检索 → 模型 → 工具） |

### P3 · 演进方向（需单独拍板，不建议顺手做）

| 项 | 说明 |
| --- | --- |
| Wire 契约流出 | `domainplane-wire`（OpenAPI 3.1 + SSE schema + 错误码字典）。这是非 Java 生态的唯一入口，也是兼容线 SDK 的生成源 |

## 5. 评审结论

| 结论 | 勾选 | 说明 |
| --- | --- | --- |
| 通过 | ☐ | — |
| **有条件通过** | ☑ | 架构判断成立、工程纪律罕见地一致；存在 1 处结构性未收口（存储后端）与 1 处并发正确性缺口，需在下一轮升级前关闭 |
| 拒绝 | ☐ | — |

### 修改要求（按优先级，不含排期）

1. **`ChunkExporter` 收回 `KnowledgeStore`**，把"可替换后端"从"实现了 SPI"推进到"没有旁路"。
2. **`DomainStore.pendingDeletes` 换并发容器**——这是一处能在线上表现为"偶发误判"的缺口，修复成本以分钟计。
3. **`BlobStore` 分层归位**，否则 `runtime` 永远无法在不启动 Spring 的情况下自测存储路径。
4. **给"多实例"写一张前置清单**，明确它不是配置项；同时把 `single-instance-guard: false` 的语义从"可绕过"改成"仅用于人工接管"。
5. **分批提交工作区积压的改动**——这是当前最高风险项，与架构无关但与结果有关。

### 不必改的（避免过度设计）

- 不要为了"优雅"去删 `AgentOrchestrationService` 的兼容构造器：那是对外部使用方的破坏性变更，收益只有行数好看。
- 不要给 `CompositeRetriever` 的串行模式引入共享线程池：临时单线程池是为了让通道可被 `cancel(true)` 打断，这是有意为之，不是疏漏。
- 不要在单实例前提下补分布式锁：租约已经解决了它要解决的问题。
