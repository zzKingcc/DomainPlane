# 知识库页面重设计（待审）

> 触发：存储配置已改为「连接（命名实例）+ 知识体（关键字/向量两槽）」模型，知识库页仍按「一台 ES + 一域一索引」的老假设编排。
> 本文只给设计与改动清单，不含代码改动。

## 0. 结论

页面的核心问题从「有哪些文档、要不要重建」变成**「哪个知识体装了什么、这批域挂在哪台机器上、我要动的到底是哪一份」**。所以重设计的落点是三件事：

1. **把知识体提为页面第一等对象**——它才是存储配置里的组织单位，域只是它的使用者；
2. **把落点（域 → 体 → 槽 → 连接 → 后端）做成可见数据**，而不是让用户上传失败后猜；
3. **把破坏性操作按作用域分级**（体 / 域 / 全平台），并在弹窗里说清「动哪几台、几个索引、保不保留原文」。

现有页面里「ES 索引」卡、「触发重建」、「重灌到新后端」三处的语义都已失效或不准确，属于必须改而不是可选优化。

## 1. 约束：页面逻辑必须服从的九条事实

| # | 事实 | 代码位置 | 对页面的含义 |
|---|---|---|---|
| 1 | 索引名只由**域**派生（`domainplane_kb_{域}_{hash}`），体不参与命名 | `KbIndexes.nameOf` | 索引归属是域；**同名索引可以在多台后端各存在一份**（换过体的域） |
| 2 | 知识体 = 两槽（keyword / vector），每槽引**恰好一条**连接 | `InfraSettings.KnowledgeBody`（keyword/vector/id/name） | 页面上每个体必须显示两行落点，不能只显示一个"后端" |
| 3 | 连接 id 同时就是知识库后端 id；后端自描述能力 `keyword/vector/wildcard/storesText/reindexInPlace` | `InfraSettings.Connection`、`KnowledgeBackend.capabilities()` | 目标/落点下拉要按能力位判，不能按"是不是 ES"判 |
| 4 | 域 → 体是**单值绑定且不继承**（没绑就真的没有） | `DomainStore.bodyOf`、`KnowledgeBodyResolver.bodiesOf` | 不能出现"继承自父域"的绑定展示（与模型/MCP 绑定不同） |
| 5 | 召回沿域链**向上累加、不向下**；只对"自己绑了体"的域开通道 | `RetrievalPlan.channels`、`KnowledgeStatsService.retrievableBy` | 「归属本域」和「本域可检索」是两个数，位置不能混用 |
| 6 | 写入必须带域；域没绑体**直接抛**，不回落平台默认 | `RetrievalPlan.writeStore(String)` | 上传前必须能判"能不能传"，而不是传完报 60007 |
| 7 | 原文在平台 BlobStore（`ChunkArchive`），索引是可重建派生数据 | `ChunkArchive`、`VectorReindexer` | 「重建」与「重灌」都从 archive 出发，是两件不同的事 |
| 8 | 换过知识体的域，旧机器上会留同名 collection；删除是**逐台删**同名 | `deleteIndices`、`deleteByDocId`、`mergeDocuments` | 页面必须能表达"这份数据在两台都有"，以及淘汰残留 |
| 9 | 统计是 60s TTL + 300s 失败冷却的缓存快照，且 ES 侧 fail-open | `KnowledgeStatsService` | 数字必须能标「旧数据」；"索引为空"≠"没有数据" |
| 10 | **全局召回策略**是 yaml 配置（`domainplane.knowledge.strategy`，默认 HYBRID），在通道层做闸门：KEYWORD 时向量通道**根本不开**（不是开了不用），VECTOR 同理 | `KnowledgeProperties.Strategy`、`RetrievalPlan.addVectorChannel/addKeywordChannel` | 体的「召回模式」必须按 **体两槽 × 全局策略** 算"生效模式"——混合体在 KEYWORD 策略下实际只走关键字；页面只按体配槽显示"混合"就是在骗人 |

还有三条口径事实：

- `KnowledgeStatsService.byBody` 是**按当前绑定**把文档归到体名下的（`domainStore.bodyOf(domain)`），所以"换过体的域，旧文档会算在新体上"。页面上凡是按体汇总的数字，都要按这个口径解释，别顺手写成"文档存在这个体里"。**连带推论**：解绑了体的域、绑定悬空的域，它们的文档不进任何体（byDomain 里有、byBody 里没有）——**体视图各行之和 ≠ 顶部平台总数**，这个差是"没有体可归"的文档，不是算错。
- 上传链路的拒绝点不止"域没绑体"一个：文件扩展名白名单、大小上限、**域必须已登记**（`domainRegistry.contains`，否则凭空造索引）、同名文档拒绝（不区分大小写，除非 `replace=true`，且这个判定发生在**拿到导入锁之后**的异步任务里）。预检接口只查"绑体"是漏的，见 §3.4。
- 上传与重灌共用**同一把串行导入锁**（`ingestPermit`，1 个许可 + 有界队列 + 超时拒绝）：重建/重灌执行期间上传会被拒（`KNOWLEDGE_UPLOAD_REJECTED`），反之亦然。页面要把"忙"当成正常态提示，而不是当失败报错。

## 2. 现页面的 8 处不适配

| # | 今天的行为 | 冲突的事实 | 后果 |
|---|---|---|---|
| 1 | 顶部第 3 卡叫「ES 索引」，取 `/kb/status.indexCount` | 该值是**全部后端**的域名索引并集，与 ES 无关；纯 Qdrant 或无关键字体时也会是 0 | 用户以为"ES 没配好"，其实数据在 Qdrant 上 |
| 2 | 页面层级只有「域 + 文档」 | 体才是配置单位，域只是使用者 | 改完存储配置无法在这页确认"哪个体吃了我这批文件" |
| 3 | 上传只传 `domain`，落点由后端解析 | 落点 = 域 → 体 → 两槽 → 连接；域没绑体直接抛 | 上传到一半才报错；扇出写入（关键字/向量在两台）时用户完全不知道写了两份 |
| 4 | 文档表列：docId / 文件名 / 域 / 切片数 / 预览路径 | `DocumentItem` 不含体与后端；`list()` 跨全部后端合并 | 混合部署下答不出"这份文件在哪台机器"；删除实际是"所有后端上该 docId 全删"，页面无法解释 |
| 5 | 「触发重建」= `POST /kb/rebuild` 无作用域 | `rebuildAll` 删**全部已存在索引**并在其所在后端重建 | 只想修某个体的向量槽，结果把别的体的数据一起清了 |
| 6 | 「重灌到新后端」= `reindexToBackend(target)` | 该操作**不改任何绑定**，只把 archive 重灌到目标后端 | 用户以为"换后端成功"，实际是造了一份副本，检索仍走原体 |
| 7 | 无异常态展示位 | 体被删（绑定悬空）、槽连接被停用、有绑定无索引、孤儿索引都存在且都是静默的 | 这正是"看着空其实有 / 以为删了其实还在"两个经典坑的源头 |
| 8 | 卡片数字用 `/kb/status`（现扫，不走缓存），域空间页用 `/kb/stats`（可检索口径） | 两套算法、两种口径 | 同一份数据两页数字对不上；`/kb/status` 还会在 ES 黑洞时每次烧一个 connectTimeout |
| 9 | 页面对全局召回策略零感知 | `domainplane.knowledge.strategy`（KEYWORD/VECTOR/HYBRID）在通道层闸门 | 用户在存储配置里给体配了两路，页面上显示"混合"，实际 yaml 关了向量路——又一处"配置看着对、运行静默缺一路" |

## 3. 新页面结构

### 3.1 顶部四卡（替换现有四卡）

| 卡片 | 内容 | 来源 | 口径（放 tooltip，不上页面正文） |
|---|---|---|---|
| 已入库文档 | 全平台文档数 | `/kb/overview.platform.documents` | 所有体所有域的归属文档合计 |
| 总切片数 | 全平台切片数 | 同上 `.chunks` | 跨后端取最大值，不重复计扇出 |
| 知识体 | `N 个 · M 个在用` | `.platform.bodies` / `.bodies[*].domainCount>0` 计数 | 在用 = 至少一个域绑了它 |
| 向量模型 | 已就绪 / 未配置 | `/admin/settings`（现有逻辑不动） | 全局唯一 |

「ES 索引」卡删除。索引数量下沉到体视图的每行（"3 个索引"），因为它只对具体某个体有意义。

### 3.2 主体：知识体视图（新，页面第一屏）

一张表，一行一个体：

| 列 | 内容示例 | 说明 |
|---|---|---|
| 知识体 | `kb-sales`（`销售知识`） | id + 展示名 |
| 关键字落点 | `es-main · Elasticsearch` / `未配` / `es-main（不可用）` | 槽位为空、连接被删、连接被停用三种态要分开 |
| 向量落点 | `qdrant-a · Qdrant` / `es-main · Elasticsearch` | 两槽指同一台时合并显示一次 `es-main（两路同机）` |
| 召回模式 | `混合` / `仅关键字` / `仅向量` / `空壳` | **生效模式 = 体两槽 × 全局策略**（策略 KEYWORD 时混合体也显示"仅关键字"或标"混合·向量被全局策略关闭"）；空壳 = 两槽都没配（域绑它等于没绑） |
| 绑定域 | `3 个`（可展开） | 展开后每行：域路径 → 索引名 → 文档/切片 |
| 文档 / 切片 | `128 / 1,204` | 按体汇总（当前绑定口径，见 §1 尾注）。**不显示合计行**：解绑/悬空域的文档不进任何体，合计会显得数字凭空丢失 |
| 状态 | `正常` / `连接不可用` / `有绑定无索引` / `体已删除` | chip。**词与域空间页对齐**：`体已删除` = 域空间页的 `bodyMissing`，`连接不可用` = `bodyDead`，两页同一个状态一个词；判据见 §6 |
| 操作 | `重建` `重灌` `看文档` | 「看文档」= 给下方文档表加 `body=xxx` 筛选 |

空态：一个体都没有时，整块显示「还没有知识体」+ 一个指向「存储配置」的按钮（页面上不写解释文）。

### 3.3 文档表（在现有表上改）

- **新增两列**：`知识体`、`落点`（后端 id，多台时逗号并列，如 `es-main, qdrant-a`）。**落点是推算口径**：按文档归属域**当前绑定**的体两槽连接显示，不逐台查物理位置（`DocumentItem` 没有后端信息，逐台查 containsByDocId 是 O(文档×后端) 的远程调用，不值得）。代价要接受：换过体的域，老文档实际躺在旧机器上，落点列显示的是新体那台——列名就叫"落点（当前绑定）"，不冒充物理事实。文档表自己不承担"找出旧机器残留"的职责，那是孤儿清理的事。
- **新增筛选行**：域 / 知识体 / 后端三个下拉，默认全选。
- 保留：docId、文件名、切片数、切片预览路径（点击复制）、删除。
- 高度与空态沿用上一轮的固定表（420px 无限滚动、表体内空态），避免尺寸跳变。
- 删除弹窗要写清范围：`将删除该 docId 在所有后端上的全部切片（当前：es-main, qdrant-a）`。

### 3.4 上传区（在现有基础上加落点预检）

```
[选择文件]                     [上传]
归属域 [ default.sales ▾ ]   覆盖更新 ☐
落点：kb-sales · 关键字 es-main + 向量 qdrant-a（写两份）
```

- 域选中后立刻请求预检，落点行实时更新（chip 表达，不写解释句）。
- **预检的判据必须覆盖上传链路全部拒绝点**（与 `upload()` 的抛错顺序对齐，缺一条就是"界面放行、后端拒绝"）：
  1. `domainExists`：域是否已登记（`domainRegistry.contains`，未登记后端直接 INVALID_PARAMETER）；
  2. `writable`：绑体判定，与 `writeStore(domain)` 抛错条件逐字一致——含**绑的体是原文体**这个分支（`RetrievalPlan` 的报错原文是"未绑定知识体（或绑的知识体是原文体）"，预检漏了这个分支就会放行）；
  3. `duplicate`：目标索引内是否已有同名文档（不区分大小写）。有同名 → 上传按钮不置灰，但**把"覆盖更新"勾选框点亮并提示"已存在同名，将覆盖"**——这个冲突今天要到拿到导入锁之后才炸，是最值得提前的一条；
  4. `limits`：扩展名白名单（`allowedExtensions`）与大小上限（`maxFileSize`）由接口带回，前端不硬编码（现在页面 `accept` 属性是手抄的，服务端改白名单就漂移）。
- 预检结论 `writable=false` 时：上传按钮置灰，右侧给一句原因 + 跳转（`去域空间绑体` / `去存储配置`）。
- 扇出写入（两槽不同后端）显示 `写两份`；两槽同机只显示一次。
- 上传是**同步阻塞**请求（后端 `future.get()`），执行期间按钮必须防重复点击；返回"导入繁忙/队列已满"时提示稍后重试，不当失败报错。

### 3.5 维护区（低频高危，独立分区，默认收起）

按「作用域 × 动作」分级，每个动作的确认弹窗必须写清三件事：**会动哪几台后端、影响几个索引、保不保留文档**。

| 动作 | 作用域 | 后端行为 | 使用场景 |
|---|---|---|---|
| 重建（保留原文） | 体 / 域 / 全平台 | archive 读原文 → 新维度重建 → 重灌（`rebuildPreservingText`/`VectorReindexer`） | 换向量模型、换体的向量槽 |
| 重建（丢弃内容） | 体 / 全平台 | 删索引 → 按当前维度建空索引（`rebuildAll`） | 确实要清空重来。**空库特例**：一个索引都没有时 `rebuildAll` 会凭空建出根域 `default` 的空索引——确认弹窗要写明"当前无索引，重建将创建 default 域的空索引" |
| 重灌到该体的当前槽 | 体 | 从 archive 重灌到当前连接 | 换连接后恢复（页面写清这是**改完绑定后的第二步**） |
| 重灌到指定后端 | 体 / 全平台 | 现状 `reindexToBackend`，**不改变检索落点**，只生成副本 | 迁移前预置数据 |
| 清孤儿索引 | 全平台 | 列出不属于任何现存域的 `domainplane_kb_*` 并提供删除 | 删域残留、换体残留 |

页面常驻文字只留动作名与作用域；语义全进弹窗与本文档。

三条边界纪律：

- **`purgeAll()` 不清编**：`KnowledgeBaseService` 里还有第三个破坏动作 `purgeAll`（删索引不重建，连空索引都不留），它是换向量模型流程在「模型设置」页的两个选项之一（保留重建 / 丢弃重建）。知识库页的"重建（丢弃内容）"用 `rebuildAll` 就好，不把 purge 收编进来——否则两个语义相近的清空按钮分居两页，用户永远记不住哪个是哪个。
- **导入锁互斥提示**：重建/重灌与上传共用一把串行锁，任一方执行中另一方被拒。维护操作执行期间页面给"执行中"态（按钮禁用 + 上传按钮同步禁用），收到 `KNOWLEDGE_UPLOAD_REJECTED` 提示"稍后重试"。

## 4. 接口改动清单

| 接口 | 现状 | 目标 | 备注 |
|---|---|---|---|
| `GET /admin/kb/overview` | 无 | **新增**。一次给全：`strategy`（全局召回策略，生效模式判定用）、`limits{allowedExtensions[],maxFileSize}`（上传预检判据）、`bodies[{id,name,slots{keyword:{connectionId,type,usable},vector:{...}},effectiveModes,domainCount,documents,chunks,indices[{name,domain,documents,chunks,backends[]}]}]`、`orphans[{name,backends[]}]`、`platform{documents,chunks,bodies,backends[]}`、`stale`、`generatedAt` | 索引→后端映射只能靠逐台 `listCollections()`，必须复用 `KnowledgeStatsService` 的快照（见 §6）。孤儿**判定判据**：索引名不匹配任何**现存域**的 `KbIndexes.nameOf`（按索引名反推，不按切片 metadata.domain——孤儿索引里的老文档 metadata 还带着已删的域，按 metadata 判会漏） |
| `GET /admin/kb/target?domain=` | 无 | **新增**。上传前预检：`{domainExists, bound, bodyId, bodyName, modes, slots[], writable, reason, fanOut, duplicate, limits}`；`reason` 枚举覆盖：域未登记 / 未绑体 / 绑的体是原文体 / 体两路连接全不可用 | 纯读配置 + 连接可用性；`duplicate` 需查目标索引的文档登记（走统计快照，不现扫） |
| `POST /admin/kb/rebuild` | 无作用域，删全部 | 加 `scope=body\|domain\|all` + `bodyId`/`domain` + `preserveText` | **scope 必填**，缺省不推断为 all（防误触） |
| `POST /admin/kb/reindex` | 只有 `targetBackendId` | 加 `scope=body\|all` + `bodyId`；响应与文档同步标注「不改变检索落点」 | **`scope=body` 有个语义坑**：`VectorReindexer` 现在以"整台 store 的 collection 清单"为源，按体过滤只能按"该体**当前绑定域**派生的索引名"圈定 archive 条目——换过体的域，旧域的 archive 条目不在过滤集里，重灌不会跟着走。要么接受这个语义（页面写明"重灌只覆盖该体当前绑定的域"），要么做"该体历史写过的索引"（从配置推不出来，得逐索引查归属，代价大）。见 §7 待拍板。若要"换后端"，页面走引导：先改体槽连接（存储配置页）→ 再重灌 |
| `DELETE /admin/kb/orphans` | 无 | **新增**（或 `POST /kb/orphans/clean`）：按索引名清单删除，逐台、fail-closed | 防误删：只接受 `overview.orphans[].name` 里的名字 |
| `GET /admin/kb/documents` | 6 字段，无过滤 | 增 `bodyId`、`backends[]`；支持 `?body=`、`?domain=`、`?backend=` | `DocumentItem` 扩展；过滤可先在前端做（数据量不大），接口字段必加 |
| `GET /admin/kb/status` | 全平台现扫 | 保留兼容，页面改用 `overview` | 后续可下线，避免两套口径并存 |

## 5. 分期建议

| 期 | 内容 | 是否要动后端语义 |
|---|---|---|
| P0 | `/kb/overview` + `/kb/target` 两个读接口；四卡替换；知识体视图；文档表加列与筛选；上传落点预检 | 否（只读聚合） |
| P1 | 重建/重灌加 `scope`；页面维护区改成作用域分级；确认弹窗写清影响范围 | 是（参数与校验） |
| P2 | 孤儿索引检测与清理；"有绑定无索引"一键补建 | 是（要枚举并逐台判定） |

P0 就能解决"页面逻辑不适配"的 6 条中的 5 条（第 5、6 条属于破坏性动作语义，落在 P1）。

## 6. 代价与坑

**成本上限在哪**：`/kb/overview` 的明细（索引 → 后端）只能靠逐台 `store.listCollections()` 拼出来，这是 O(后端数) 的远程调用；再乘上"每个索引都要 `documents()` + `count()`"就是现扫。所以这把明细必须**并入 `KnowledgeStatsService` 的同一份快照**，一次算完、60s 内复用。若让页面并发打三个接口各扫一遍，等于把刚拆掉的域空间页性能问题原样搬到这页。

**fail-open 会被页面当成事实**：ES 的 `listCollections()` 失败返回空列表，统计层拿不到异常。于是"存储不可达"在数据上长得像"一个索引都没有"。页面必须能区分这两者（快照里带 `reachable` 或复用 `stale`），否则用户会去点"重建"——在不可达的后端上，这是最坏的误操作。

**配置态不是错误态**：体被删、槽悬空、有绑定无索引，都是"当前配置的样子"，不是系统报错。不要红屏、不要 toast，按行标灰 + 一句原因 + 修复跳转即可。这与"页面干爽"一致：状态用 chip 表达，原因放 tooltip。**状态判据**（与域空间页 `bodyMissing`/`bodyDead` 同词同义）：`体已删除` = 有域绑着这个 id 但 `infra.body(id)=null`；`连接不可用` = 体在但两路的连接缺失/未填地址（`usableBody` 的判法：至少一路可用才算正常）；`有绑定无索引` = 体可用但其绑定域的 `nameOf` 不在快照 `indices` 里——**受快照 fail-open 影响，"存储不可达"与"真的没索引"在数据上同形，必须先看 `stale`/`reachable` 再给这个状态，否则会引导用户去点重建**。

**破坏性动作的 fail-closed 纪律要带进页面**：`assertStoreReachable()` 的语义是"任一台不可达就整体拒绝"。页面不能做成"跳过不可达那台继续删"，也不能在预检里把"某台不可达"降级成警告。

**口径统一**：一个位置上只能有一种数。域空间页、知识库页、删域预演三处的数字必须同源（`KnowledgeStatsService`），且各自标注是「归属」还是「可检索」。混用的代价是用户会拿两个不可比的数字做决策。**还有两个必然出现的"对不上"，页面要提前承认而不是让人当 bug 报**：① 体视图各行之和 < 平台总数（解绑/悬空域的文档没有体可归）；② 文档表"落点"列与真实物理位置可能不符（按当前绑定推算，换过体的老文档在旧机器上）。

### 8.3 与原计划的偏差（都是有意的）

1. **同名冲突改在前端判**，不进 `/kb/target`。预检的价值是"选域立即反馈"，一旦掺入远程查询就会变慢；而文档表本来就拿着全量文件名与归属域。判到同名时**自动勾上「覆盖更新」**并提示，不静默覆盖。
2. **文件白名单 / 大小上限由接口带回**（`limits`），前端不再硬编码 `accept` 之外的第二份判据。
3. **文档表的"落点"列不显示物理位置**，只显示"当前绑定的两槽"，列名与 tooltip 都写明口径。物理残留归孤儿清理（P2）。
4. **体视图不显示合计行**——解绑/悬空域的文档没有体可归，合计必然小于平台总数，写出来只会被当成 bug。
5. **`/kb/status` 保留但页面不再调用**（P0 不动它，避免影响其它潜在消费者）；等到 P1 再决定下线。
6. **「总切片数」口径变了**：旧 `/kb/status` 用 `store.count(index)` 跨后端取最大值（精确计数）；新 `overview()` 用"按 docId 聚合的切片数之和"（与域空间页 byDomain 同源）。两者在单索引文档数 ≤ 1000（列表聚合上限）时相等，超过时新口径只算聚合到的部分。换来的是三处数字终于同源——这是要的，不是回归。
7. **槽位能力位进了预检**（复核补充）：`slotView` 现在查后端 `capabilities`，关键字槽指到 Qdrant 显示"能力不匹配"而不是"可用"——否则预检放行一个运行期会静默跳过的召回路，正好复刻"配置看着对、运行少一路"。`writable` 仍与 `writeStore` 同源（它本来就不查能力位），两者职责不同：`writable` 答"上传会不会被拒"，槽位 chip 答"这一路活着吗"。

### 8.5 复核修正（2026-11-01 夜，第二遍代码审查）

| # | 问题 | 修法 |
|---|---|---|
| 1 | `slotView` 只判连接注册、不判能力位：关键字槽指 Qdrant 显示"可用"，运行期该路静默跳过 | 加 `incapable` 状态（查 `capabilities`），前端同款 chip + 原因 |
