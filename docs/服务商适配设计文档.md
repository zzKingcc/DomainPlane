# 服务商适配设计文档

面向开发 / 维护者。规定「OpenAI 兼容基底 + 声明式服务商适配」的完整设计：未适配的服务商走纯 OpenAI 直连且不提供参数调优，已适配的服务商按适配文件暴露调优参数。
形态与部署见 `架构设计文档.md`；模型配置基线见 `详细设计文档.md` §7；本文件落地后，§7 相关章节以本文件为准同步修订。

## 1 背景与目标

### 1.1 现状（代码事实基线，2026-10-13 核对）

| 事实 | 位置 |
| --- | --- |
| 连接基底已统一为 OpenAI 兼容一种格式，协议分派（Anthropic / Ollama / DashScope 分支）已整体移除 | `domainplane-server/.../server/model/ModelClientFactory.java` |
| 模型档案 `ModelProfile` 为 13 字段 record：`alias` / `endpoints` / `input` / `output` / `baseUrl` / `apiKey` / `modelName` / `temperature` / `maxTokens` / `thinking` / `returnThinking` / `dimensions` / `fallbacks` | 同目录 `ModelProfile.java` |
| 客户端按档案指纹缓存，指纹 = `baseUrl + modelName + temperature + maxTokens + thinking + returnThinking + SHA-256(apiKey)` | `ModelProfile#fingerprint()` |

| 内置预设只承担「填默认地址」，不携带任何协议与元数据 | `ModelPresets.java` |
| 多模态四族端点（生图 / 重排 / TTS / ASR）由 `ModelEndpointClient` 直接走 JDK HttpClient 拼 OpenAI 兼容路径 | `ModelEndpointClient.java` |

### 1.2 技术前提（已实地验证，非推测）

对本地 Maven 仓库 `dev/langchain4j/langchain4j-open-ai/1.18.1/langchain4j-open-ai-1.18.1.jar` 逐类解包核对：

| 验证点 | 结论 |
| --- | --- |
| `OpenAiChatModel$OpenAiChatModelBuilder` | 同时具备 `defaultRequestParameters` 与 `customParameters` |
| `OpenAiStreamingChatModel$OpenAiStreamingChatModelBuilder` | 同上 |
| `OpenAiChatRequestParameters$Builder` | 具备 `customParameters` |
| `dev.langchain4j.model.openai.internal.chat.ChatCompletionRequest`（真正序列化为请求体的 DTO） | 字段含 `model / messages / temperature / topP / maxTokens / maxCompletionTokens / seed / reasoningEffort / … / customParameters`，私有字段与标准字段并列合并进同一请求体 JSON |

**结论：厂商私有请求字段（如 `enable_thinking`）无需任何协议分支，经 `customParameters` 声明即注入；标准字段 langchain4j 原生支持。** 这是整套方案成立的技术基础。

### 1.3 目标

1. 用户配置**未适配**的服务商时：默认走 OpenAI 规范直连，**不提供参数调优工具栏**（工具栏不渲染，非置灰）。
2. 用户配置**已适配**的服务商 + 模型时：按适配文件提供参数调优工具栏，参数范围 / 默认值 / 语义以**官方文档**为出处（适配文件内登记 `docUrl` 与 `note`）。
3. 新增一家服务商的适配 = 新增一个 JSON 文件，**零 Java 改动**；新增一个可调参数 = 改 JSON 一个条目。
4. 存量档案（`models.json`）零迁移，行为不变。

### 1.4 非目标

- 不做非 OpenAI 兼容协议的接入（那是另一个决策，本方案明确不回头）。
- 不做参数条件显隐（如「思考开启后才显示 budget」）——留待有真实需求（P2）。
- 不改动多模态端点的请求构造逻辑（P1 只让它们消费 params 默认值，不改路径与结构）。

## 2 总体方案

```
用户填写 服务商地址(baseUrl) + 模型名
        │
        ▼
┌─────────────────────────────┐
│ 适配匹配引擎（后端权威）       │  ① models 精确 → ② modelPatterns 正则 → ③ hosts 服务商
└─────────────────────────────┘
     │命中                              │未命中
     ▼                                  ▼
渲染调优工具栏                     纯 OpenAI 直连
（schema 驱动：number/int/         （工具栏不渲染；
 bool/enum/string）                 params 恒空）
     │                                  │
     ▼                                  ▼
保存档案：                          （无调优数据）
标准参数 → 老字段                   │
私有参数 → params map               │
     │                                  │
     ▼                                  ▼
┌──────────────────────────────────────────────────┐
│ ModelClientFactory 构建客户端（按指纹缓存）          │
│   temperature/maxTokens/returnThinking → builder  │
│   setter（内部即 defaultRequestParameters 通道）     │
│   params → customParameters                       │
└──────────────────────────────────────────────────┘
     │
     ▼
OpenAI 兼容请求体 JSON
```

核心决策一览：

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 适配的载体 | 项目内 JSON 文件（`resources/adapters/*.json`） | 参数调优本质是「官方文档约定的数据」，不是逻辑；数据与代码解耦，改参数不发版 |
| 匹配权威 | 后端 | host 归一、正则语义只实现一份，杜绝「前端画出工具栏、后端不认」 |
| 参数存储 | 标准参数复用 `ModelProfile` 老字段；私有参数进新增 `params` map | 存量档案零迁移；加参数不改 record 结构 |
| 注入通道 | 模型 builder setter（`temperature` / `maxTokens` / `returnThinking`）+ `customParameters` | §1.2 已验证；不开协议分支 |
| 未适配的约束 | 前端不渲染 + 后端拒绝非空 params | UI 与 API 双层成立，绕过无效 |

## 3 适配文件规范

### 3.1 位置与加载

| 项 | 规定 |
| --- | --- |
| 目录 | `domainplane-server/src/main/resources/adapters/`，**一服务商一文件**，文件名即建议的 adapter id 前缀 |
| 加载时机 | 应用启动时全量扫描，解析进内存注册表（`ModelAdapterRegistry`，单例 Bean） |
| 加载顺序 | 按文件名排序，**与文件系统 / jar 内目录顺序无关**（保证匹配优先级确定） |
| 坏文件 | 单个文件解析失败或 schema 校验不过 → 记 ERROR 日志并跳过该文件，**不影响启动与其余文件** |
| 外部覆盖 | P1 增加 `config/adapters/`（运行时）覆盖同名内置文件；P0 只内置 |

### 3.2 文件结构（JSON Schema 语义）

```json
{
  "id": "dashscope-qwq",
  "provider": "dashscope",
  "label": "阿里云百炼 QwQ（思考模型）",
  "docUrl": "https://help.aliyun.com/zh/model-studio/developer-reference/…",
  "input": ["text"],
  "output": ["text"],
  "match": {
    "hosts": ["dashscope.aliyuncs.com"],
    "models": ["qwq-plus", "qwq-32b"],
    "modelPatterns": ["^qwq-.*$"]
  },
  "families": {
    "chat": {
      "params": [
        {
          "key": "temperature", "label": "温度", "type": "number",
          "min": 0, "max": 2, "step": 0.1, "wire": "temperature", "std": true
        },
        {
          "key": "maxTokens", "label": "单次最大输出", "type": "int",
          "min": 1, "max": 8192, "wire": "max_tokens", "std": true
        },
        {
          "key": "thinking", "label": "思考模式", "type": "bool", "default": true,
          "wire": "enable_thinking", "std": false
        }
      ]
    }
  }
}
```

### 3.3 字段定义

| 字段 | 必填 | 语义 |
| --- | --- | --- |
| `id` | 是 | 适配唯一键；档案可回记 `adapterId` 供排障（P0 只记日志，不落档） |
| `provider` | 是 | 服务商标识（小写短名，如 `deepseek` / `moonshot`） |
| `label` | 是 | 适配显示名（如「DeepSeek Flash（V4.1）」）。随 `/admin/model-profiles` 的 `adapter` 摘要下发，便于识别命中哪家；P0 界面不再单列一行展示（绿框出现即已命中） |
| `docUrl` | 否 | 官方文档链接；**参数语义的可追溯出处**。随摘要下发，P0 界面不再单列外链入口 |
| `input` / `output` | 否 | 该模型的输入 / 输出模态（词表 `text` / `image` / `audio` / `video` / `file` / `embedding` / `score`，写错一个词加载失败）。空 = **没登记**（不是"只能吃文本"） |
| `match.hosts` | 否 | 服务商 host 列表（归一化口径见 §4.2） |
| `match.models` | 否 | 模型名精确列表 |
| `match.modelPatterns` | 否 | 模型名正则列表 |
| `families.<族>.params` | 是（至少一个族一段） | 该端点族暴露的调优参数；族 ∈ `chat` / `embedding` / `images` / `rerank` / `tts` / `asr`，P0 只消费 `chat` |

`match` 三项至少填一项；三项全空 = 该文件永远不命中，加载时记 WARN。

### 3.4 参数字段（`families.<族>.params[]`）

| 字段 | 必填 | 语义 |
| --- | --- | --- |
| `key` | 是 | 档案 `params` map 的键（同一 adapter 内唯一） |
| `label` | 是 | 控件显示名 |
| `type` | 是 | `number` / `int` / `bool` / `enum` / `string` / `stringList` |
| `wire` | 是 | 注入 OpenAI 请求体的字段名（同一 adapter 内唯一） |
| `wireWrap` | 否 | 非空时注入的值要包一层单键对象 `{wireWrap: value}`（如 `response_format` 的 `{type: "json_object"}`）。只对 `std=false` 成立 —— 标准参数的值形状由框架定，没法再套一层 |
| `std` | 是 | `true` = 标准参数，wire 限 `temperature` / `max_tokens`，值存 `ModelProfile` 老字段；`false` = 私有参数，值存 `params`，注入走 `customParameters` |
| `min` / `max` / `step` | 否 | `number` / `int` 的取值范围与步长；在 `stringList` 上 `min` / `max` 是**元素条数**区间（如 `stop` 最多 16 条）。前端控件属性 + 后端校验双端执行 |
| `default` | 否 | 官方文档写明的默认值。它同时管两件事：① **控件初始值** —— 初始接入（模态）与卡片回填时，控件直接落在这个值上，用户一眼看到的就是"不填会按什么走"；② **注入补缺** —— 无 default 且用户未填 = 不发送该字段，沿用平台「不注入自造默认值」的哲学。没有 default 的控件才留空、空态显示「服务商默认」（前端不本地复刻任何厂商默认值）。条件参数也可以声明 default（§3.4.1）；标准参数（`std=true`）的 default **只用于 ①**，不参与注入 —— 标准参数的值走 `ModelProfile` 老字段，注入由 `allowedStdWires` + setter 单独一条路负责 |
| `enabledWhen` | 否 | 条件可用性：非空时本参数只在被依赖参数取到指定值时才可填（§3.4.1） |
| `options` | `enum` 必填 | 枚举候选 `[{"value": "…", "label": "…"}]` |
| `display` | 否 | 控件呈现方式，仅 `enum` 可用。`bar` = 分档进度条（§3.4.2）。只是呈现提示，不参与取值与注入 —— 值仍是 `options` 里那个枚举字符串 |

`std=false` 的 wire **禁止**取 `temperature` / `max_tokens`（与老字段绑定冲突），schema 校验时拒绝。

> **为什么 top_p 这类标准字段也归 `std=false`**：`customParameters` 与 `defaultRequestParameters` 注入的是同一个请求体，key 不重叠即无歧义；`top_p` 没有老字段承载，走 params + `customParameters` 与走框架 setter 的请求体结果完全一致，且加参数零代码。

#### 3.4.1 条件可用性（`enabledWhen`）

有些参数**填了不生效**，取决于另一个参数。DeepSeek 的思考模式是最典型的一例：非思考模式下 `top_p` 固定 1.0、传值被忽略；思考模式下 `temperature` 无效。与其让用户填一个服务商根本不看的字段，不如把控件灰掉并说清为什么 —— `enabledWhen` 就是把这件事声明出来：

```json
"enabledWhen": {
  "key": "reasoningEffort",
  "values": ["low", "high", "max"],
  "missing": "high"
}
```

| 字段 | 必填 | 语义 |
| --- | --- | --- |
| `key` | 是 | 被依赖参数的 `key`：同族、`std=false`、且自身无条件的参数 |
| `values` | 是 | 允许值集合；取值必须落在被依赖参数自己的取值域内（`enum` 必须是它的合法选项之一 —— 写错一个字母就永远灰着的框，加载期拦下） |
| `missing` | 否 | 被依赖参数**未填**时按这个值参与判定；缺省 = 未填即不命中（默认关） |

判定式：`values[key] ∈ values`，其中 `values[key]` 缺失时取 `missing`，`missing` 也为空则视为不命中。两端同一套语义，后端为权威：

| 端 | 行为 |
| --- | --- |
| 前端 | 条件不成立的控件 `disabled` 并**清空**该控件的读数 —— 界面上看到的必须等于保存后会生效的；留着旧值就成了"界面上有、实际发不出去"，正是这套机制要消灭的东西。控件不附任何解释文案：能填就填，不能填就是灰的 |
| 后端校验 | 条件不成立却带了值 → 400 拒绝（**不静默丢弃**：丢弃会让用户以为"保存成功了、填的值在生效"），文案带参数 key 与它依赖的参数 |
| 注入层 | 同样按条件过滤（兜住绕过控制器写入的档案：改配置文件、旧版本残留）—— 未命中的字段不发射；标准参数走的是框架 setter，不经 `customParameters`，故单独算一遍 |
| 条件不成立却带了值 | 保存时 400 拒绝（文案带 key 与被依赖的参数）；注入层同样按条件过滤，兜住绕过控制器的档案（改配置文件、旧版本残留） |

三条禁令（加载期校验）：不得指向自己（条件恒不成立）、不得指向另一个条件参数（链式依赖会叠出两级禁用态，用户无从判断到底缺哪个）、不得指向标准参数（标准参数不在 `params` map 里，判定会飘）。

条件参数**可以**声明 `default`：它同样要过上面那道条件门 —— 条件不成立时控件被清空、值也不发射，两者不会打架。允许它，是为了让"官方写明默认值、但只在特定档位生效"的参数（如 DeepSeek 的 `temperature`，默认 1、仅非思考模式生效）在可用档位上也能把默认值体现出来。

#### 3.4.2 分档进度条（`display: "bar"`）

「思考强度」这类参数是**有序档位**（`none` → `low` → `high` → `max`）：下拉框把顺序藏进展开列表里，用户得点开才知道一共几档、自己在哪一档。`display: "bar"` 把 `options` 按数组顺序铺成一排可选档位，当前档实绿加重、其左侧各档浅绿（"已点亮到这一档"），当前档说明再另起一行：

```json
{ "key": "reasoningEffort", "label": "思考强度", "type": "enum", "wire": "reasoning_effort",
  "std": false, "display": "bar", "default": "high",
  "options": [ {"value": "none", "label": "none"},
               {"value": "low", "label": "low"},
               {"value": "high", "label": "high"},
               {"value": "max", "label": "max"} ] }
```

| 点 | 说明 |
| --- | --- |
| 只对 `enum` 成立 | 分档的前提是取值有序，只有枚举自带这个顺序（`options` 数组顺序 = 档位顺序）。`type` 非 `enum` 而带 `display` 的，加载期拒绝 |
| 取值不变 | 值域仍是 `options` 里的枚举字符串：`none` 是 DeepSeek 的"非思考模式"入口，**不是**"未选"，照样占一段可点档位 |
| 控件协议不变 | 值仍由一个**隐藏 `input`** 承载，id 与其它控件同构 —— `collectTuning` / `tuneSignature` / `tuneValuesNow` / `syncTuneEnabled` 全部零改动复用；进度条只是"往同一个槽里写值的又一种控件" |
| 清空语义 | 再点**同一档** = 取消 → 回未选态（说明回落到 schema 默认：写了 `default` 显示「默认 X」，没写才「服务商默认」），与下拉里选回空项等价（否则选了就再也清不掉） |
| 置灰 | 条件不成立（§3.4.1）时整条锁死且不点亮任何档 —— 灰条不该看起来像已经选中了某一档 |

`display` 取值走白名单（当前仅 `bar`）：适配文件是 curated 数据，写错一个词应当在加载期炸出来，而不是静默退化成一个普通下拉。

### 3.5 参数值的存储分岔（核心存储规则）

| 参数类别 | 存储位置 | 注入通道 | 说明 |
| --- | --- | --- | --- |
| `std=true`（temperature / max_tokens） | `ModelProfile.temperature` / `.maxTokens` 老字段 | 模型 builder 的 `temperature` / `maxTokens` setter（内部即 `defaultRequestParameters` 通道） | 存量档案无缝；编辑时工具栏控件回显老字段值 |
| `std=false`（enable_thinking / top_p / …） | `ModelProfile.params`（`Map<String,Object>`，新增） | 模型 builder 的 `customParameters` | 新扩展的唯一入口 |

## 4 匹配引擎

### 4.1 算法（后端权威，前端只消费结果）

匹配输入：档案的 `baseUrl` 与 `modelName`。逐级降级，取第一个命中的 adapter：

| 级别 | 规则 | 说明 |
| --- | --- | --- |
| ① models 精确 | trim 后**忽略大小写**相等 | 优先级最高，模型个体差异（同名模型不同参数面）在此层表达 |
| ② modelPatterns 正则 | **全串匹配**（语义等同 Java `Pattern.matches`；书写 `^qwq-.*$` 与 `qwq-.*` 等价，两端行为一致） | 系列模型（如 `^qwq-`）在此层表达 |
| ③ hosts 服务商 | baseUrl 归一化后的 host 在 `hosts` 列表内（忽略大小写） | 服务商级兜底 |

同级多个 adapter 命中 → 按 `id` 字典序取第一个（确定性，不依赖文件列举顺序）。三级全不中 → **未适配**。

### 4.2 host 归一化

| 步骤 | 规则 |
| --- | --- |
| scheme | baseUrl 无 scheme 时补 `https://` 再解析；解析失败 → 视为无 host（不可能命中 ③） |
| 大小写 | 转小写 |
| 端口 | 去掉默认端口 `:80` / `:443` |
| 尾点 | 去掉末尾 `.`（FQDN 根点） |
| 路径 | 忽略（host 匹配不看了路径） |

### 4.3 匹配接口（新增）

```

请求：{"baseUrl": "https://dashscope.aliyuncs.com/compatible-mode/v1", "modelName": "qwq-plus"}
响应（命中）：
{
  "code": 0,

  }
}
响应（未命中）：{"code": 0, "matched": false, "adapter": null}
```

接口只做匹配与 schema 下发，**不落盘、不依赖已存档案**；`GET /admin/model-adapters` 返回全量适配清单（排障用，管控台不展示）。

### 4.4 端点族与模态：适配文件优先于检测

保存档案时端点族为空（表单不采集），按两级取：

| 级 | 来源 | 何时命中 | 结果 |
| --- | --- | --- | --- |
| ① | **适配文件** | `match` 按**模型名**命中（① 精确 / ② 正则） | 端点族 = 登记了参数的族名（`families` 的键）；输入 / 输出模态 = 文件里的 `input` / `output`。**不发任何上游请求** |
| ② | 服务商元数据 | 上一级没中 | `GET /models` 识别链（`architecture` → `?sub_type=` → 留空，见 `接口文档.md` 的模型档案约定），只发 GET、零 token |

为什么需要 ①：只有 OpenRouter 那类综合提供商才会在接口里说明模型吃什么、产出什么；OpenAI / DeepSeek 官方的清单只有 `id/object/created/owned_by`。而这些内置模型本来就是**按官方文档登记过**的 —— 端点族与模态在同一个人工维护的文件里，一次请求都不用发。

**host 兜底命中（③）不给声明**：那只说明"这家服务商我们登记过"，说明不了"这个模型是什么"。照抄同 host 另一个模型的声明会把 `api.openai.com` 上的 `text-embedding-3-*` 说成 `text → text`（`ModelAdapterRegistry#declaration` 因此在 `MatchLevel.HOST` 上返回空）。参数调优的绿框仍按 ③ 兜底显示（P0 既有口径），两者判据不同、互不影响。

## 5 档案存储扩展

### 5.1 `ModelProfile` 变更

| 项 | 现状 | 目标 |
| --- | --- | --- |
| 字段 | 13 字段 | 新增 `Map<String,Object> params`（可空，空 = 未适配或无调优值） |
| 构造归一 | `endpoints` 等 List 拷贝 | `params` 同样归一为不可变 map；**归一前先剔除 value 为 null 的条目**（`Map.copyOf` 遇 null 直接 NPE；调用方传 `{"top_p": null}` 是合法输入，语义＝不发送） |
| `fingerprint()` | 不含 params | **必须纳入**：params 排序后稳定序列化（`TreeMap` + Jackson）拼入 raw。漏纳入的后果：改调优值后指纹不变 → 客户端缓存不失效 → 「保存成功、行为没变」且无任何提示 |
| `thinking` / `returnThinking` | 存档案 + 进指纹，但客户端已不注入 | **保持现状不动**（P0 不迁移、不自动改写）；适配文件的思考类参数以新 `params` 键表达（如 `enable_thinking`）。遗留双轨在 P1 评估清理 |

### 5.2 `ModelProfileSettings.ProfileData` 变更

| 项 | 规定 |
| --- | --- |
| 新增字段 | `private Map<String,Object> params;`（`toProfile` / `from` 同步） |
| 读盘兼容 | 类上已有 `@JsonIgnoreProperties(ignoreUnknown = true)`；老文件无 `params` → 反序列化为 null → `ModelProfile` 归一为空 map，**行为零变化** |
| 写盘 | `from()` 时 params 为空的档案写 `null`/缺省，不在文件里留 `{}` 噪声 |

### 5.3 保存校验（`AdminModelProfileController.save` / `updateTuning`，后端复核）

| 场景 | 规则 |
| --- | --- |
| 匹配命中 | 调优值逐 key 对照 schema：**未知 key 拒绝**（`INVALID_PARAMETER`，文案列出合法键）；`type` 校验（number/int 接受 JSON number 或可解析数字字符串；bool 接受 `true`/`false`/`"true"`/`"false"`）；`min`/`max` 越界拒绝 |
| 标准参数一并复核 | 校验前先把 `temperature` / `maxTokens` 老字段**摊平进同一份 key→value map**（键 = schema 里的 `key`）再走上面的 schema 校验。不摊平就漏过 `min`/`max` —— 前端 number 控件的 `min`/`max` 只是填表便利，直接调 API 一样能提交越界值 |
| 匹配未命中 | `params` 非空 → **拒绝**（文案：「该服务商 / 模型未做适配，不支持参数调优」）；`temperature` / `maxTokens` 老字段**宽容接受**（存量 API 兼容），记 INFO 日志 |
| `PUT /tuning` 额外约束 | 只收 `alias` + `params` + `temperature` + `maxTokens`；连接信息 / 端点族 / 模态从既有档案带过，**接口没有入口可以改**（不是"前端不发"）。未命中适配 → 直接拒绝（绿框也只长在命中适配的卡片上） |
| 参数可空 | 任何参数缺省 = 不发送；有 `default` 的缺省 = 注入 default。**不引入必填参数概念**；`PUT /tuning` 的 `null` / `{}` 是"清除"，见 §7.2 |

> 前端可被绕过（直接调 API），所以「未适配不能调优」必须在保存复核层成立，而不是只靠 UI 隐藏。

## 6 请求注入（`ModelClientFactory` 改造）

注入点选在**模型 builder** 上（而非另建 `OpenAiChatRequestParameters`）：`OpenAiChatModel.Builder` / `OpenAiStreamingChatModel.Builder` 三者齐备——`temperature` / `maxTokens` / `returnThinking` setter（现行代码即用法），外加 `customParameters`（§1.2 已验证）。改动因此最小：每个 builder 只加一个 if 块。

```java
private StreamingChatModel buildStreaming(ModelProfile profile) {
    var b = OpenAiStreamingChatModel.builder()
            .baseUrl(profile.baseUrl())
            .apiKey(profile.apiKey())
            .modelName(profile.modelName());
    applyTemperature(b::temperature, profile);      // 老字段，非空才设（现状不变）
    applyMaxTokens(b::maxTokens, profile);          // 老字段，非空才设（现状不变）
    applyReturnThinking(b::returnThinking, profile);
    applyCustomParameters(b::customParameters, profile);   // 私有参数：key→wire 翻译 + default 补缺
    return b.build();
}
```

`buildChat` 同构。规则：

1. `applyTemperature` / `applyMaxTokens` / `applyReturnThinking` 语义不变（留空不发送）。
2. 私有参数**不是**把 `params` 原样扔进请求体：档案 `params` 的键是适配 `key`（UI 侧标识，如 `reasoningEffort`），请求体要的是 `wire`（OpenAI 字段名，如 `reasoning_effort`）——注入前按命中适配的 schema 逐个翻译（§3.2 示例里 `thinking` → `enable_thinking` 正是这个关系）。翻译只发生在注入点，存储 / 校验 / 视图全用 `key`。
3. 适配 schema 声明了 `default` 而用户没填的键，注入时补缺（§3.4）；没登记 default 又不填 = 不发送。条件参数的补缺值同样要过 `enabledWhen` 那道门。**标准参数（`std=true`）不走这条**：它的 default 只用于界面空态提示，注入由 `allowedStdWires` + setter 单独一条路负责，否则同一个 `temperature` 会被发两遍。
4. 冲突规避靠 schema 约束（`std=false` 禁设 `temperature`/`max_tokens`，见 §3.4），运行时不依赖合并语义。
5. **实施时一次实测确认**：P0 用可拦截 HTTP 的手段（JDK HttpServer 桩或等价探针）抓一次请求体，断言 `customParameters` 的 key 与标准字段并列出现在顶层 JSON——把 §1.2 的静态验证补成动态验证，防版本行为变化。

### 7.2 卡片右侧的绿色调优框

档案列表里的**对话档案卡片**，命中适配时在 `.card-body` 右侧空白区多出一块绿框（`.card-tune`），

| 项 | 规定 |
| --- | --- |
| 数据来源 | `GET /admin/model-profiles` 的 `profiles[].adapter` = `{id, label, docUrl, params[schema], items[有值的项]}`；`params` 与 match 接口同形状（卡片要能渲染**可编辑**控件，只有"键 = 值"文字不够） |

| 可点条件 | 任一控件与**框里初始显示的值**（已保存值 + 缺位补的 default）不同即变可点（"有改动就变可点"，含"清空"这种改动）；比较走规范化签名，`0.7` 与 `0.70` 视为无改动，否则按钮会一直亮着 |
| 保存 | `PUT /admin/model-profiles/tuning`，body `{alias, params, temperature, maxTokens}`；三项**整份替换**：`null` / `{}` = 清除（回到服务商默认）。若按"空 = 不动"处理，用户会发现温度清不掉 |
| 不改动的东西 | 连接信息（地址 / Key / 模型名）、端点族、模态 —— 接口不收这些字段，卡片上也没有入口。**不是"前端不发"，而是"后端无从改动"** |
| 反馈 | 就地回「已保存」/ 错误原因；成功不重拉整张列表（卡片上没有别处显示调优值，重拉反而冲掉提示） |
| 条件参数 | 启停按**已保存的**依赖值算；用户在卡片上改依赖值则立即重算启停并清空被锁项，「更新」按钮随之变可点 —— 那笔改动确实会清掉服务端上的旧值，得由用户确认 |
| 与只读 chip 行 | 原先 meta 里那行「参数调优：思考强度 = high」已撤掉 —— 绿框既显示当前值又可改，两者并存等于同一件事说两遍；卡片头部「已适配」徽标保留（一眼可知这份档案有适配） |
| 框内标题行 | 绿框内不再有「已适配 + 服务商名 + 官方文档」那一行（模态与卡片一致）：框出现即已命中，是哪家服务商看参数本身即可 |
| 标签与空态 | 每个参数的中文名后挂上英文 `wire`（如「思考强度 `reasoning_effort`」），填表时能直接对上官方文档；不写「（温度）」这类中文括号注解。控件初始值取 schema 的 `default` —— 写了就落在那个值上（用户看得见当前就是官方默认），没写才留空、空态显示「服务商默认」（§3.4）。两侧都不写任何解释性小字：参数名 + 控件就是全部 |
| 多行输入框 | `stringList`（停止序列）补上边框与内边距，与页面其它输入框同形 —— 不吃浏览器默认样式（否则文字贴着边框） |
| 密度 | 绿框是**网格**（`auto-fit` + `minmax(176px, 1fr)`）：一框横排 3 个上下参数，分档进度条（`display:"bar"`）独占一整行以免档名被截断。框内控件比页面其它表单再小一档（内边距 5/8、字号 12），整框上下留白压到 8px |

## 8 已登记的适配（P0，共 9 个模型文件）

参数范围 / 默认值**以官方文档为准**，下表只列「登记了哪些键」，各文件里带 `min/max/step/docUrl`：

> 9 个文件一律声明 `"input": ["text"]` / `"output": ["text"]`（端点族即 `families.chat`）：
> 它们登记的调优面全是文本对话参数（`reasoning_effort` / `temperature` / `max_tokens` / `verbosity` …），
> 没有任何图像 / 音频入口。这样 OpenAI / DeepSeek 官方（清单读不出类型）也能在卡片上如实显示「文本 → 文本」，
> 且保存时一次上游请求都不发。**模型将来支持多模态输入时，改这个文件即可** —— 它是 curated 声明，
> 与参数面同源同维护。

| 文件 | provider | 匹配 | 登记的调优参数（wire） |
| --- | --- | --- | --- |
| `deepseek-flash.json`、`deepseek-v4-pro.json` | deepseek | host `api.deepseek.com`；models 同名 | `reasoning_effort`、`temperature`(std，条件)、`max_tokens`(std)、`top_p`(条件)、`stop`、`response_format`、`logprobs`、`top_logprobs`(条件) |
| `openai-gpt-5.6-terra.json`、`openai-gpt-5.6-luna.json` | openai | host `api.openai.com`；models 同名 | `reasoning_effort`、`verbosity`、`temperature`(std)、`max_tokens`(std) |
| `openai-gpt-5.6-sol.json` | openai | host `api.openai.com`；models `gpt-5.6-sol` + 别名 `gpt-5.6` | 同上一行 |
| `openai-gpt-6-sol.json`、`openai-gpt-6-luna.json` | openai | host `api.openai.com`；models 同名 | `reasoning_effort`、`temperature`(std)、`max_tokens`(std) |
| `openai-gpt-6-astra.json` | openai | host `api.openai.com`；models `gpt-6-astra` | `reasoning_effort`、`verbosity` |
| `openai-gpt-6.1-sol.json` | openai | host `api.openai.com`；models `gpt-6.1-sol` | `reasoning_effort` |

> `temperature` / `max_tokens` 是**标准参数**（`std=true`）：值落 `ModelProfile` 老字段（`temperature` / `maxTokens`），不进 `params`（§3.5）。登记它们，绿框里才会出现「温度」「单次最大输出」两个控件 —— 此前这两个字段在管控台上没有任何入口，等于无从设置。
>
> Astra / 6.1-Sol 刻意**不登记**温度与最大输出：官方明确它们的 Chat Completions 不接受 `temperature`，且本代无 `none` 档（思考恒开）。登记一个填了就报错、永远不生效的控件，只会让用户以为是自己填错了。
>
> **DeepSeek 一家登记 8 个**（官方 `/chat/completions` 里对调优有意义、且填了必生效的全部）：除上面三个，还补了 `top_p`、`stop`、`response_format`（JSON 模式，`wireWrap: "type"`）、`logprobs` 与 `top_logprobs`。其中三个带条件 —— `temperature` 仅非思考模式可填，`top_p` 仅思考模式可调，`top_logprobs` 依赖 `logprobs` 打开（§3.4.1）。**官方的 `frequency_penalty` / `presence_penalty` 已废弃，一个字都不登记**：传了不生效，登记等于骗用户。
>
> 各家参数面按官方文档分化（`max` 档 Responses 专属不登记、`verbosity` 仅确认支持的登记等），完整口径见 `ModelAdapterRegistryTest#生产适配文件全部加载且按id排序` 的 `expectedWires`。拿不准的一律不登记（未登记 = 不暴露，不会误导用户）。
>
> GPT 系列暂未登记条件：OpenAI 侧"思考开启时温度是否生效"的口径没有逐代确认过，按上面同一条原则先不写 —— 拿不准的条件规则与拿不准的参数一样，写错的代价是用户对着一个灰得没道理的控件。
>
> 「思考强度」(`reasoning_effort`) 在 9 个文件里一律标 `display: "bar"`（§3.4.2）：它是典型的有序档位（DeepSeek `none`→`low`→`high`→`max`；GPT-5.6/6 多数 `none`→`low`→`medium`→`high`→`xhigh`；Astra / 6.1-Sol 无 `none`，`low`→`xhigh` 四档），分档进度条比下拉框更能一次说清"有几档、现在在哪一档"。档位数与档名一律由各文件自己的 `options` 给出（4 档 / 5 档并存），前端不做任何假设。

## 9 错误处理与边界

| 边界 | 行为 |
| --- | --- |
| 适配文件 JSON 坏 / schema 不过 | 启动记 ERROR 跳过该文件，其余正常 |
| `id` 跨文件重复 | 启动记 ERROR，后加载者跳过（先到先得，文件名序确定） |
| baseUrl 不是合法 URL | host 归一失败 → 不命中 ③；精确 / 正则仍可命中（modelName 侧独立判定） |
| modelName 为空 | 只可能命中 ③；①② 不参与 |
| params 值类型与 schema 不符 | 保存时 400 拒绝（§5.3） |
| 条件不成立却带了值 | 保存时 400 拒绝（文案带 key 与 reason）；注入层同样按条件过滤，兜住绕过控制器的档案（改配置文件、旧版本残留） |
| 条件声明本身写坏（指向不存在的参数 / 自己 / 条件参数 / 标准参数，或取值不在被依赖参数的取值域内） | 启动记 ERROR 跳过该文件（加载期校验，同 §9 首行） |
| `display` 写坏（用在非 `enum` 上，或取值不在白名单） | 启动记 ERROR 跳过该文件（curated 文件，不静默退化成一个普通下拉） |
| `customParameters` 与标准字段 key 重叠 | schema 层禁止（§3.4），运行时不赌合并语义 |
| 客户端指纹碰撞 | params 稳定序列化后入指纹（§5.1），不改缓存结构 |

## 10 测试计划

| 前端 | match 命中/未命中绿框显隐（含"三项填全"这道门）；debounce；schema 驱动渲染（含 stringList 多行框、`display:"bar"` 分档进度条：档位顺序 / 点亮到当前档 / 当前档说明 / 未选回落默认 / 点击写值 / 再点同一档取消 / 置灰整条锁死）；**参数名后挂英文 `wire`**；**空态文案「默认 X」/「服务商默认」由 `default` 决定**；**绿框不再有标题行**；受条件门禁的私有 / 标准参数都不发射；条件参数启停 + 禁用即清空 + 禁用项不进报文；卡片回填当前值；**卡片头部「更新」在「删除」左侧**且无改动灰 / 有改动亮；`save` 与 `saveTuning` 报文形状（沿用 DOM 桩 + 报文模拟手法） |
