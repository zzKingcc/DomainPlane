# 对话编排

一轮对话进来之后会发生什么：进哪张图、走哪条边、什么时候停、停下来之后怎么接回去。

---

## 1. 入口链路

```
POST /api/agent/chat
  → AgentOrchestrationService.chat
      · 域校验（存在 / 可调用 / 未软删）
      · 输入清洗（注入拦截、长度）
      · cancellationRegistry.prepareNewRound  （清上一轮的停止标志）
  → orchestrate
      · 注册 StreamContext（SSE 出口）
      · ConcurrencyGate.tryAcquire            （拿不到 → 20002）
      · agentExecutor 提交（虚拟线程）
  → runOrchestrate
      · tryMarkRunning(会话键)                 （占不到 → 30003）
  → runOrchestrateBody
      · 装配上下文（见 05）
      · 写用户消息进记忆
      · TurnPlanner（可选，见 §6）
      · compiledGraph.stream(...)
  → agent ⇄ tools 循环
  → rememberFinalAnswer + DONE
```

入口处三道闸的顺序不能换：先域、再容量、最后会话。反过来会在"域根本不可用"时白占一个并发位。

---

## 2. 状态图

三个节点，两条环：

```
START → agent ──(无工具调用)──────────────→ END
              └─(有工具调用且需审批)──→ review ──→ tools ──→ agent
              └─(有工具调用且免审批)──────────────────→ tools
```

| 节点 | 干什么 | 备注 |
| --- | --- | --- |
| `agent` | 调模型，收集本次响应里的工具调用；吐 TOKEN / THINKING | 停止标志就在这一层检查 |
| `review` | **空节点**，只是中断锚点 | `interruptBefore("review")` 让图停在这里 |
| `tools` | 逐个执行工具调用，回填结果 | 执行前逐次检查停止标志 |

两个实现细节值得记住：

- `review` 里没有一行业务代码。它的存在只是为了让 LangGraph4j 有一个"可以停"的位置——审批中断本质上是"图停在某个节点之前"，不是抛异常。
- `releaseThread(true)`：模型调用期间释放执行线程，否则一个慢模型会永久占住池里的线程。

路由在 `routeAfterAgent`：调 `toolRouter.toolsRequiringApproval(domain)`，有需要审批的工具就走 `review`，否则直接 `tools`。这个判断发生在**工具调用产生之后**，不是提前按域把所有工具都拦一遍。

## 3. 九种事件

| 事件 | 何时发 | 携带 |
| --- | --- | --- |
| `TOKEN` | 模型流式吐字 | 增量文本 |
| `THINKING` | 模型吐思考过程（档案开了 `returnThinking`） | 思考文本 |
| `PLAN` | 本轮规划完成，**恒先于第一个 TOKEN** | 计划文本 |
| `TOOL_CALL` | 决定调用某工具 | 工具名 + 参数（**已掩码**） |
| `TOOL_RESULT` | 工具返回 | 工具名 + 结果 |
| `INTERRUPT` | 图停在审批点 | `ToolCallPayload{tools:[{name,arguments,requireApproval}]}` |
| `STOPPED` | 用户主动停止 | — |
| `ERROR` | 任何失败出口 | `code` / `codeName` / `retryable` |
| `DONE` | 正常结束 | — |

终止事件只有三个：`DONE`、`STOPPED`、`ERROR`。SDK 侧靠这个判"流是不是被掐断了"——只收到 TOKEN 就断流的，会报 `STREAM_TRUNCATED` 而不是当正常结束。

`PLAN` 先于 `TOKEN` 靠的是**发送时序**（规划在进图之前完成并发出），不是运行时校验。所以任何"把规划挪到图里"的改动都会破坏这个约定，而且不会有测试报错。

## 4. 审批中断与恢复

### 产生

工具声明了 `approval != NONE`（远程/MCP 工具则按 `requiresApproval` 或 `effect != READ` 推导）→ 图停在 `review` 前 → 发 `INTERRUPT`。

payload 里的参数**已经掩码**：敏感参数在进事件体之前就换成了 `***`，工具下线的情况整个参数体换成 `[参数无法解析，已整体屏蔽]`。所以前端展示的、用户审批看到的，和模型实际发出的可能不一样——这是有意的，审批看的是"这件事"，不是"这个密钥"。

### 恢复

```
POST /api/agent/resume?sessionId=…&approved=true|false&domain=…
```

| 情形 | 行为 |
| --- | --- |
| 断点不存在 | `30001 SESSION_NOT_FOUND` |
| 图没停在 `review` | `30002 SESSION_STATE_INVALID` |
| `approved=true` | `GraphInput.resume()`，从断点继续 |
| `approved=false` | 用 `updateState` 往 `tools` 注入一条"用户拒绝"的工具结果，让图继续走，而不是把图丢掉 |

`approved=false` 走"注入拒绝结果"而不是"直接结束"，是因为模型需要知道自己被拒了才能改口——直接砍断会让用户看到半截回答。

断点存在 Redis：`domainplane:graph:checkpoint:{域}|{sessionId}`。`memory.checkpoint-ttl` 默认 24h；置 0 或负数表示永不过期（重启后仍可 `resume`）。

## 5. 停止：一个布尔值，不是线程中断

`stop` 的实现只有一步：`compareAndSet(false, true)`。

| 性质 | 行为 |
| --- | --- |
| 幂等 | 第二次调用返回 `false`，不报错 |
| 不可恢复 | 标志只在新一轮入口 `prepareNewRound` 时清除；本轮内不清 |
| 不碰线程 | 不 `interrupt()`，纯协作式：模型等待每 200ms 醒一次看标志，工具循环每次执行前看标志 |
| 半截文本 | 已经吐出去的保留，事件流以 `STOPPED` 收尾 |
| 记忆回滚 | 本轮写进去的提问被撤销（`truncateTo`），避免留下"有问无答" |

为什么不用线程中断：虚拟线程池里的线程会被复用，`interrupt` 留下的标记可能漂到下一个任务上，症状是"莫名其妙的任务被中断"。协作式标志的代价是响应延迟等于分片大小（默认 200ms），换来的是行为可预测。

"不可恢复"也是刻意的：允许"停完继续"就要保存运行时状态的中间态，而中间态没有定义（模型可能已经吐了一半、工具可能执行到一半）。要接着聊就发新一轮，历史还在。

## 6. 规划前置

每轮进图之前，可以先用主模型做一次规划调用，由模型自判 `direct`（直接答）还是 `plan`（先出计划）。

| 项 | 值 |
| --- | --- |
| 开关（做不做） | `domainplane.planning.enabled`，默认 `false` |
| 开关（发不发） | 域级 `planDisplay`，默认 `false`；关着就只是不把 PLAN 事件发给前端 |
| 上限 | `domainplane.timeout.planner-wait-ms`，默认 60s，分片同 `model-wait-slice-ms` |
| 失败 | 除取消外的所有异常一律吞掉，降级为直进图；超时同样降级 |
| 产物去向 | 以 `SystemMessage` 插在**最后一条 UserMessage 之前**，只进本次请求，不写记忆 |
| 恢复轮次 | `resume` 不重新规划（断点里已有完整状态） |

两颗开关互不约束：全局关 = 不做；全局开 + 域级关 = 做了但不给前端看（计划只作为系统消息引导模型）。

为什么插在最后一条用户消息之前而不是系统提示词里：系统提示词是"长期人设"，会进每一轮；计划是"这一轮的做法"，插进历史会污染后续轮次，模型会在下一轮继续执行已经过期的计划。

失败静默降级而不是报错，是因为规划本身是增强项：规划调用失败就说明"这轮不规划"，用户的提问并没有失败。

## 7. 并发与容量

| 闸门 | 实现 | 饱和时 |
| --- | --- | --- |
| 全局并发 | `ConcurrencyGate`：`Semaphore` + `tryAcquire`，**不排队** | `20002 SYSTEM_BUSY` |
| 执行器 | `agentExecutor`：虚拟线程，每任务一条 | `20002 SYSTEM_BUSY` |
| 同会话串行 | `tryMarkRunning(会话键)` | `30003 SESSION_BUSY` |
| 单轮工具并发 | 有界池（8 起），零队列，满即拒 | 工具层返回失败结果给模型 |

为什么闸门不排队：排队会让"系统忙"表现为"卡住不动"，客户端超时后重发，队列更长。直接拒绝至少让调用方立刻知道该退避。容量由 `domainplane.agent.concurrency-limit` 控制，默认 200。

同会话串行与全局并发是两件事：前者防"同一段记忆被两个线程同时写"，后者防"整机被压垮"。前者命中是调用方的错（该等或该 stop），后者命中是平台的容量问题。

## 8. 超时总表

全平台"等多久算太长"只有一份定义（`runtime.config.Timeouts`）：

| 键 | 默认 | 用在哪 |
| --- | --- | --- |
| `model-wait-ms` | 600000 | 等模型终态的总上限，兜"既不吐字也不报错"的半开连接 |
| `model-wait-slice-ms` | 200 | 等模型的单次阻塞分片；决定"点停止"的响应延迟。**不得大于总上限** |
| `planner-wait-ms` | 60000 | 规划调用上限 |
| `tool-invoke-ms` | 30000 | 本地工具单次执行 |
| `vision-call-ms` | 60000 | 看图 |
| `capability-call-ms` | 120000 | 生图/生视频/语音（这类动辄 30–90s） |

两族"多久算过期"别混：上面是**单次调用上限**；`instance.timeout-seconds`（心跳 35s）、`memory.checkpoint-ttl`、`domain.delete-grace` 是**生命周期**，两者互不影响。

旧的 `domainplane.tool.invoke-timeout-ms` / `vision.timeout-ms` / `capability.timeout-ms` 已作废，统一到 `domainplane.timeout.*`。

## 9. 失败出口：三条，顺序固定

```
停止（用户主动） → 未配置（平台没配） → 通用失败
```

顺序错了的表现很隐蔽：用户点停止时如果先落到"通用失败"，流会以 `ORCHESTRATION_FAILED`（可重试）收尾，前端给个"重试"按钮——而用户要的是"它停下来了"。

| 出口 | 发什么 | 额外动作 |
| --- | --- | --- |
| 停止 | `STOPPED` | 回滚本轮记忆、清断点 |
| 未配置 | `90005`（对外只说"服务暂未就绪"） | 回滚本轮记忆、清断点；日志里写清缺什么、去哪个页面配 |
| 通用失败 | `ORCHESTRATION_FAILED` 或上游定性后的码 | 回滚本轮记忆 |

上游"明确拒绝"的三类会单独定性，不再一律报可重试：

| 上游情形 | 码 | 可重试 |
| --- | --- | --- |
| 余额/额度不足 | `90006 LLM_QUOTA_EXHAUSTED` | 否 |
| 凭证无效/未授权 | `90007 LLM_AUTH_FAILED` | 否 |
| 请求被上游拒绝 | `90008 LLM_REQUEST_REJECTED` | 否 |

这几类的上游原文会带进事件体（"（上游：Insufficient Balance）"），因为用户和运维都得靠它定位；可重试的几类（限流、超时、上游 5xx）不带原文——英文网络措辞不如错误码的对外文案好用。

## 10. 踩过的坑

**`resume` 带错 `domain` 会静默打到另一段会话。** 会话键是 `(域, sessionId)`，两个域下同名的 `sessionId` 互不相干。表现是 `30001`，不是"域不匹配"。

**审批中断不是异常。** 想用 `try/catch` 接住中断点会失败——图是正常返回的，只是停在 `review` 之前，靠 `isInterruptedBeforeReview` 判断。

**停止之后再发同一 `sessionId` 是允许的。** 停止只清本轮，不销毁会话；但顺序必须是"新请求进来时清标志"，所以不要在两个请求之间手动复位标志。

**`model-wait-slice-ms` 调大省 CPU，调小更跟手。** 它不影响总上限，只影响"停止"的响应延迟与唤醒频率。
