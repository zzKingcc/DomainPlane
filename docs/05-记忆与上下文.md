# 记忆与上下文

两件容易被混为一谈的事：**存多少**（记忆）与**这一轮给模型看多少**（装配）。这两个数字由不同机制控制，改错地方会得到完全相反的效果。

---

## 1. 一句话分工

| | 记忆 | 装配 |
| --- | --- | --- |
| 回答的问题 | 这段会话能存多久、存多少 | 这一轮往请求里塞多少 |
| 存储 | Redis，只追加 | 内存，每轮现算 |
| 上限 | **无**（只增不减；仅运维可人工清空整个会话） | 24,000 token 预算 |
| 超了怎么办 | 不存在"超"——永不拒绝开轮 | 逐级丢弃，永不拒绝 |
| 可恢复 | 是（永久保存） | 否（每轮重算） |

**记忆是档案，不是缓存。** 它的价值在于"半年后还能查到当时说过什么"，所以默认没有 TTL、不淘汰。代价是无限增长——这个代价被有意放在"存"这一侧承受，而不是用"悄悄删旧消息"来掩盖。

---

## 2. 记忆：只追加，不封顶

早期版本是"双约束"：`max-messages=100` / `max-tokens=30000`，超了就返回 `30004` **拒绝开新一轮**。这套语义已废止，原因很简单——**它约束的是一侧，却想解决另一侧的问题**：

- 封顶只能回答"会话有多大"，回答不了"这轮该给模型看多少"。
- 而真正会爆上下文的是后者。会话再长，只要装配层裁得住，模型调用就不会超限。
- 拒绝开轮却会让一个正常的长期会话**永久作废**（只增不减，只有运维能整会话清空），代价远大于收益。

现在 `DualConstraintChatMemory.add()` 是**纯追加**：不淘汰、不判上限、不拒开轮。类名和 `max-messages` / `max-tokens` 两个配置项保留（兼容既有配置与回归测试），但已**不参与任何行为判定**——`capacityFor(...)` 只剩内部自检与单测口径，主线零调用。

```
add(userMessage) → RPUSH，永远成功
```

- 平台不代为切换 `sessionId`。会话边界由调用方决定，不是平台偷偷开的。
- 已经写进去的消息永不删除，除非：用户停止（回滚本轮）、删域（级联清理）、手动清理 Redis。
- 保留期默认为空 = 永久。需要 TTL 时设 `DOMAINPLANE_MEMORY_TTL=30d`。

### 写入时机（顺序敏感）

| 时刻 | 写什么 | 为什么在这 |
| --- | --- | --- |
| 进图之前 | 用户提问 | 模型调用需要它已经在历史里 |
| 正常结束 | 最终回答 | 只有拿到完整回答才写，避免半截答案进档案 |
| 中断 | 不写 | 中断意味着"还没答完"，`resume` 后继续走同一轮 |
| 失败 / 停止 | 回滚提问（`truncateTo`） | 否则留下一条永久"有问无答" |

回滚这一条是踩过坑的：早期只在"回答写入失败"时回滚，用户点停止后档案里就多一条孤零零的提问，下次进这个会话模型会以为上次的问题没被回答，反复回答同一个问题。

### 键结构

| 用途 | Redis 前缀 |
| --- | --- |
| 会话记忆 | `domainplane:chat:memory:{域}\|{sessionId}` |
| 图检查点 | `domainplane:graph:checkpoint:{域}\|{sessionId}` |
| 归档轮次的检索索引 | `domainplane:chat:*` 下的旁路索引（关键词/向量） |
| 滚动摘要 | `domainplane:chat:*` 下的摘要键 |
| 媒体附件登记 | `domainplane:media:attachment:{内容哈希}` |

前缀后面都跟着 `(域, sessionId)` 的组合键，所以同一 `sessionId` 在不同域下是两套数据。

## 3. 装配：24k 预算怎么分

`ContextAssembler` 每轮现算，拼四块：

```
[系统提示词（沿域链拼）]
[历史摘要（若有）]
[知识卡片（上一轮工具带回的引用）]
[最近窗口（最近 N 轮原文）]
[本轮提问]
```

预算分配（默认）：

| 项 | 值 | 含义 |
| --- | --- | --- |
| 总预算 | 24,000 token | `assembly-budget` |
| 窗口份额 | 60%（14,400） | 给最近原文 |
| 摘要份额 | 2,000 | 给滚动摘要 |
| 卡片上限 | 5 张 | 给知识引用 |
| 窗口轮次 | 8 轮（16 条） | 优先取这么多，取不满不报错 |
| 摘要行数 | 40 行 | 超了丢最老的行 |

### 超预算时的降级顺序

```
摘要（从最老的行开始丢）
  → 卡片（从最后一张开始砍）
    → 窗口（从最老的整轮丢）
       → 底线：至少留 2 条、至少 512 token
```

顺序的道理：摘要是"压缩过的历史"，丢它损失最小；卡片是"上一轮的引用"，本轮基本用不上；窗口是"原文"，最贵。底线不破，是因为窗口清空等于让模型失忆，那比超预算更糟。

**装配是唯一的闸，且它永不拒绝开轮。** 输入再长也只降级，不报错——记忆侧已经没有第二个闸了（封顶语义移除后，这个平台不存在"这段会话还能不能继续"这个判断）。

### 模型窗口更小时

`TurnContextFactory.assemblerFor(sessionId, domainId)` 会按该域绑定的档案 `contextWindow` 经 `ContextBudget.effective` **收窄**预算（`min(配置预算, 窗口 − 输出预留 − 安全边距)`），只封顶、不放大；未声明窗口或解析失败就原样用配置值。否则换个小窗口模型就会直接撞上游 400。

## 4. 滚动摘要：默认关

`summary-enabled` 默认 `false`。关着的时候，历史压缩退化为"digest 拼接"——把老轮次拼成一段干巴巴的文本，信息不丢但不精炼。

开着的时候：

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `summary-min-new-turns` | `4` | 攒够几轮新对话才触发一次摘要 |
| `summary-max-material-turns` | `20` | 一次最多喂多少轮给摘要模型 |
| `summary-max-output-tokens` | `400` | 摘要输出上限（摘要段预算只有 ~2000） |
| `summary-workers` | `2` | 并发摘要的线程数（同会话由单飞保证串行，多线程只为不同会话互不阻塞） |

为什么默认关：摘要是一次**额外的模型调用**，会花钱、会增加延迟、会引入"摘要写错"的新故障面。默认关掉，让部署方自己决定值不值。

代价也要说清：摘要是**有损**的。它不设 TTL、不做版本、不可回溯——一旦摘要写歪，历史就永久歪了。所以它按"档案"对待，不按"缓存"对待。

## 5. 历史检索：让模型能翻旧账

窗口只有 8 轮，记忆里却可能已经积累了几百轮。中间那段怎么办？给模型两个工具去翻：

| 工具 | 干什么 | 声明方式 |
| --- | --- | --- |
| `read_history` | 按轮次顺序读一段 | 静态声明，不受域影响 |
| `recall_history` | 按语义/关键词检索归档轮次 | 静态声明，不受域影响 |

`recall_history` 有一路可选的语义检索：

| 开关 | 默认 | 行为 |
| --- | --- | --- |
| `history-vector-enabled` | `true` | 归档轮次做向量索引，检索时与关键词路 RRF 融合 |

未配向量模型时**静默退化为纯关键词**，检索行为与不开这一路一字不差——不是报错，也不是空结果。这条"静默"是刻意保留的：历史检索是增强项，不该因为没配向量模型就让整个对话不可用。

关键词路的打分权重是三项：

| 键 | 作用 |
| --- | --- |
| `recall-word-weight` | 完整词命中（中文按词，英文按词） |
| `recall-bigram-weight` | 二元组命中 |
| `recall-unigram-weight` | 单字命中 |
| `recall-extra-stop-words` | 追加停用词 |

停用词同时决定**写索引**与**查询**两侧的切词，改完必须重放归档重建索引；权重只在查询打分生效，改完即时生效。这一条不对称是必须记住的：改权重不用重建，改词表必须重建。

## 6. 检查点：断点不是记忆

| | 记忆 | 检查点 |
| --- | --- | --- |
| 内容 | 对话消息 | 图状态（停在哪个节点、有哪些待审批工具调用） |
| 生命周期 | 永久（默认） | `memory.checkpoint-ttl`，默认 24h |
| 谁写 | 每轮正常结束时 | 每次图状态推进时 |
| 丢了会怎样 | 接不上上文 | `resume` 报 `30001`，只能重发 |

检查点置 0 或负数表示持久化（永不过期），重启后仍可 `resume`。这条设置常被误用来"延长会话寿命"——它只延长"断点还能接回去"的窗口，不延长记忆。

---

## 7. 几个数字为什么是这些值

| 数字 | 值 | 依据 |
| --- | --- | --- |
| 装配预算 | 24k | 主流中文模型 32k–128k 窗口下，给工具定义与输出留出余量后的安全值 |
| 窗口份额 | 60% | 剩下 40% 给提示词、摘要、卡片与本轮输出 |
| 窗口轮次 | 8 | 超过 8 轮的指代（"刚才那个"）已经很难靠原文解决，该走 `recall_history` |
| 检查点 TTL | 24h | 与域删除宽限期对齐，两者是同一时钟 |

`memory.max-messages` / `max-tokens` 不在上表：它们已经不对应任何行为，改它们不会改变任何结果。

这些值都可以调，但**调之前先想清楚调的是哪一侧**：上表全是 `assembly-*`，影响的是"每轮塞多少"。**记忆侧没有可调上限**——存多少由保留期（`ttl`）决定，不设就是永久。

---

## 8. 踩过的坑

**窗口不是"最近 8 条消息"，是"最近 8 轮"。** 一轮 = 提问 + 回答（可能还有若干工具消息）。按条数理解会算出双倍。

**摘要开着但没配主模型，会在每轮多一次失败调用。** 摘要服务用的就是主模型，没有独立的"摘要模型"配置；主模型不可用时摘要会静默跳过并保留 digest 拼接。

**`read_history` / `recall_history` 不受域可见性影响。** 它们只看当前会话，不跨域。想跨会话检索是另一件事（知识库）。

**JSON 序列化走的是 `JsonContentSerializer`。** 多模态内容（文字 + 图片引用）在记忆里存的是结构化 JSON，不是拼好的字符串；手工改 Redis 里的记忆会让它读不出来。
