# md / docx / doc / pdf / excel 入库切片设计

> 状态：**md（①）、docx（②）、入口叉叉 + 白名单 + 切片上限（③）、pdf（④）、旧版 .doc（⑥）、Excel（⑦）已落地**（2026-10-02）；
> **pdf 字号推断标题（⑤）未做** —— 现在 pdf 按「页」叉节。
> 前置：`TXT-INGESTION-DESIGN.md`（txt 四步管线，已落地）
> 本文规则来自实测（Tika 3.2.3 + POI 5.4.1 + PDFBox 3.0.8，构造样例文件跑通），不采信文档与直觉。

---

## 一句话

txt 的管线是「**猜**结构」（靠正则认标题）；md/doc/pdf 的管线是「**读**结构」（格式里本来就有标题、表格、页边界）。
所以不是给白名单加几个扩展名，而是把现有四步拆成两层：

```
格式适配层（每种格式一套，产出统一的 Block 流）  →  通用切片层（全格式共用，一行不改）
```

**只有格式适配层是新的，切片规则（认标题之外的打包、重叠、去重、导出）全部复用 txt 那套。**

## 一、先说清：为什么不只是"加扩展名"

### 1.1 入口现在假设"输入是文本"

```
KnowledgeBaseService.upload()
  → TxtNormalizer.decode(bytes)        // BOM → 严格 UTF-8 → GB18030，判不出就拒
  → buildDocument(decoded.text(), ...) // Document.from(String)
```

docx / doc / pdf / xls / xlsx 都是**二进制**。走这条路的结果是：

| 情况 | 结果 |
|---|---|
| 二进制恰好能通过严格 UTF-8 | **乱码入库**（最糟：静默成功，检索出来全是垃圾） |
| 二进制过不了严格 UTF-8 与 GB18030 | 报"编码判不出" —— **错误的报错**，用户按提示换编码永远解决不了 |

→ **入口必须按类型叉叉**：文本类（txt/md）走"解码 → 文本"；二进制类（docx/doc/pdf/xls/xlsx）走"字节 → 解析器"。

### 1.2 与 txt 的本质差异

| | txt | md | docx | pdf |
|---|---|---|---|---|
| 结构 | **没有**，靠正则猜 | 显式（`#` 层级） | 显式（段落样式 Heading1-6） | **没有，只有坐标** |
| 标题层级 | 猜，只敢叉 2 级 | 确定，1~6 级 | 确定，1~6 级 | 要靠字号推断 |
| 表格 | 无 | 原生 md 表格 | 有结构（单元格） | **无法还原**（只有文本流） |
| 图片 | 无 | `![]()` 引用 | 内嵌二进制 | 内嵌或外链 |
| 页 | 无 | 无 | 有页眉页脚（**独立于正文**） | 有页眉页脚（**混在正文里**） |
| 码 | 无 | 有代码块，**不能切断** | 无 | 无 |
| 字符集 | 需探测 | 需探测 | 自带（无需探测） | 自带 |

这张表就是全部难点的来源。

后补的两种格式（⑥⑦）在同一套坐标里的位置：

| | doc（Word 97–2003） | xls / xlsx |
|---|---|---|
| 结构 | 显式（段落样式 + **大纲级别**） | 显式（工作表就是二维表） |
| 标题层级 | 样式名（**本地化，不可靠**）+ 大纲级别（可靠） | 无 |
| 表格 | 有结构（单元格） | **它本身就是表格** |
| 图片 | 内嵌二进制（不读） | 图表 / 图片（不读） |
| 页 | 正文里有叉页符 `\f`（不用它做页码锚点） | 无 |
| 字符集 | 自带 | 自带 |
| 额外难点 | 老文件**几乎没有标题样式** | 公式格 / 合并格 / 稀疏 used-range |

## 二、实测结论（决定了后面怎么设计）

以下结论来自构造样例的实测（带 Word 标题样式 + 表格的 docx、两页带页眉页脚的 PDF 等）。

### 2.1 Tika 的 XHTML 对 docx **丢掉了标题层级**

```xml
<body><p>第一章 会员规则</p>          <!-- Heading1 → 只是 <p> -->
<p>一、注册条件</p>                    <!-- Heading2 → 只是 <p> -->
<p>会员注册需提供手机号并完成实名认证。</p>
<table><tbody><tr><td><p>会员等级</p></td> ...   <!-- 表格结构 ✓ 保留 -->
```

**结论**：docx 的标题必须**用 POI 直接读**（`XWPFParagraph.getStyleID()`），指望 Tika 给的 XHTML 是拿不到层级的。

### 2.2 Tika 的 XHTML 对 pdf **页边界可靠，但标题、字号全丢**

```xml
<div class="page"><p />
<p>Internal Handbook - Confidential - Page 1</p>   <!-- 页眉，混在正文里 -->
<p>CHAPTER ONE MEMBERSHIP</p>                      <!-- 18pt 标题 → 只是 <p> -->
<p>1.1 Registration Steps</p>                      <!-- 13pt 小标题 → 只是 <p> -->
<p>Membership registration requires ... after delivery</p>   <!-- 句子在此被页截断 -->
<p>www.example.com/internal - do not distribute</p>          <!-- 页脚 -->
<p />
</div>
```

**结论**：
- ✅ `<div class="page">` 拿到了，**页边界可靠** —— 这是删页眉页脚的基础。
- ❌ 字号、字体、加粗**都没有** → 标题无法从 XHTML 区叉。
- ⚠️ **页眉里带页码**（`Page 1` / `Page 2`），两页文本**不相同** → 直接"文本相同就删"抓不到它，必须**先把数字归一化再比**。
- ⚠️ 段落跨页被切断（第一页末 `after delivery` 无句号，第二页首 `and must be...`）→ 需要跨页拼接。

### 2.3 Tika **没有 Markdown 解析器**

`tika-mimetypes.xml` 里 Markdown 只有一条 `*.markdown` 的 glob，**没有任何 markdown parser 模块**。
→ md 只能自己解析。**这反而是好事**：`#` 前缀是确定信息，比正则猜标题准得多。

### 2.4 依赖体量

| 方案 | 体积 |
|---|---|
| Tika 的 22 个 parser 模块全量 | **4.9 MB** |
| 只挑 core + pdf + microsoft | 3.2 MB |
| PDFBox（12 jar） | 7.8 MB |
| POI（8 jar）+ xmlbeans | 28.8 MB |
| **合计（全量含第三方）** | **≈ 41 MB** |

**瘦身挑模块只省 1.7 MB** —— 真正的重量是 PDFBox + POI（36 MB），而它们无论如何都要。
所以"引不引 Tika"**不该按体积决策，该按"它给不给我们要的结构"决策**。

**结论：不引 Tika。** 实测显示它对 docx 丢标题层级、对 pdf 丢字号 —— 它最有价值的"格式无关纯文本"恰恰不是这里要的"格式原生结构"。Tika 4.0 把默认输出换成了 Markdown，但 Markdown 语法里**没有"字号"这个维度**，对 pdf 标题判定毫无帮助。docx / doc / excel 用 POI，pdf 用 PDFBox。（唯一值得引它的场景是将来要支持一大堆杂格式，那就让它只做**兜底叉支**，不进主路径。）

## 三、架构：统一中间表示

### 3.1 引入 `Block`

现有 `OutlineReader.Section` 是 `(path, bodyLines)` —— 装不下"这是一张表"。加一层：

```java
record Block(Kind kind,     // TITLE / PARAGRAPH / LIST_ITEM / CODE / TABLE / IMAGE / QUOTE
             int    level,  // 仅 TITLE：1~6（0 = 无层级）
             String text,   // 正文；TABLE = markdown 表格文本；IMAGE = 占位描述
             int    pageNo) // PDF 用；其余 0
```

**格式适配层只做一件事：`文件字节 → List<Block>`**，标题层级由格式自己给出，不再"猜"。

### 3.2 通用切片层怎么吃 Block

```
List<Block>
   │
   ├─ TITLE ──────────→ 更新标题路径栈（层级来自 level，不用猜）   → 不产出正文
   │
   ├─ PARAGRAPH / LIST_ITEM / QUOTE ─→ 攒成"可切正文行" ─→ 交给现有 Chunker（原样复用）
   │
   ├─ CODE / TABLE ───→ 【不可切块】整块独占一片，块内按行切、不按句切、不加重叠
   │        └ TABLE 超长时按数据行切叉，且【每片重复表头行】
   │
   └─ IMAGE ──────────→ 占位文本，并入紧随其后的正文片；若后面没有正文则独立成小片
```

**关键点：`Chunker` 一行不改。** 新增的只是一个"叉派器"：可切块喂给现有 Chunker，不可切块自己成片。
txt 管线也完全不动 —— 它是"格式适配层退化成纯文本"的特例。

### 3.3 整条流水线

```
                     ┌──────────────── 格式适配层（新） ────────────────┐
bytes ─┬─ txt ───────→ 字符集统一 → 清洗 → 正则认标题 ────────────────┤
       ├─ md ────────→ 字符集统一 → md 解析（# 层级 / 代码块 / 表格）──┤
       ├─ docx ──────→ POI XWPF（段落样式层级 / 表格 / 图片）──────────┤→ List<Block>
       ├─ doc  ──────→ POI HWPF（样式名 + 大纲级别 / 表格）────────────┤
       ├─ pdf ───────→ PDFBox 抽行（页边界）→ 页眉页脚清洗 ────────────┤
       └─ xls/xlsx ──→ POI WorkbookFactory（工作表 → markdown 表）─────┘
                                                                      │
                     ┌──────────────── 通用切片层（复用） ──────────────┴──┐
                     │ 标题路径栈 → 叉派（可切/不可切）→ 句打包 + 重叠      │
                     │ → section_path 前置进正文 → content_hash → 去重      │
                     │ → 向量化 → 写 ES → 导出切片预览 txt                  │
                     └─────────────────────────────────────────────────────┘
```

## 四、各格式的适配规则

### 4.1 md（自研解析，最省事最准）

| 输入 | 处理 |
|---|---|
| `#` ~ `######` 标题 | → `TITLE(level=1..6)`；**`#` 后有空格才算**（`#tag` 不是标题） |
| ``` ``` 围栏代码块 | → `CODE`，**块内不解析任何标记**（`#` 在此不是标题） |
| 缩进 4 空格的代码块 | → `CODE`（老式写法，同样不解析） |
| `\| a \| b \|` 连续行 | → `TABLE`（含 `---` 叉隔行时确认为表头） |
| `- ` / `* ` / `1. ` / `> ` | → `LIST_ITEM` / `QUOTE`（保留标记，列表项语义对检索有帮助） |
| `![alt](url)` | → `IMAGE`，占位 `[图片: alt]`；**url 丢弃**（对检索是噪音） |
| `[文字](url)` | → 保留**文字**，丢掉 url（同上） |
| `<!-- 注释 -->` | 删除 |
| 行内 HTML 标签 | 剥标签留文字 |
| `---` 叉隔线 | 忽略（**注意：不能与表格叉隔行混淆**，只有紧跟在表头行后面的才算） |

md 里**不需要**"猜标题"，所以 txt 那套标题正则、`isNumericOrdinal` 这类硬约束在这里完全用不上。

### 4.2 docx（POI 直读）

| 来源 | 处理 |
|---|---|
| `XWPFParagraph.getStyleID()` 形如 `Heading1` / `标题 1` | → `TITLE(level=N)`；**样式名要做归一化**（中文版 Word 样式名带 `标题`，编号带空格） |
| `XWPFParagraph.getStyleID()` 的段落 `outlineLvl`（大纲级别） | → `TITLE(level=outlineLvl+1)`；**与样式名构成双路**：中文版 Word 的内置标题样式 ID 常常只是 `1` `2`（没有 heading 字样），这时只有 `outlineLvl` 能说明它是标题 |
| 其余段落 | → `PARAGRAPH` |
| `XWPFDocument.getTables()` | → `TABLE`，转 **markdown 表格**（表头取首行） |
| `getAllPictures()` | → `IMAGE`（占位；OCR 见 §五） |
| 页眉页脚 `getHeaderList()/getFooterList()` | **根本不读** —— 比事后删干净 |
| 脚注 / 批注 / 修订痕迹 | 不读（POI 默认给"接受修订后"的正文） |

认标题的**顺序不能反**：先试样式名（能给准层级），再用大纲级别兜底。反过来的话 `Heading 3` 会被大纲级别压成同一档，层级就丢了。

**表格必须与段落按顺序穿插**，不能"先全段落、后全部表格"。POI 提供 `getBodyElements()`（有序返回 `XWPFParagraph` / `XWPFTable`），用它遍历。

### 4.3 pdf（PDFBox 3.0.8 + 自定义 TextStripper）

PDF 没有结构，只有"文字 + 坐标 + 字号"。选 PDFBox 3.0.8（Apache-2.0）：它是唯一能同时拿到文本 + 字号 + 坐标 + 页码的成熟纯 Java 库。叉四件事：

**(1) 抽行**：自定义 `PDFTextStripper`（覆写 `writeString(String, List<TextPosition>)` 并**不调用 super**，
于是不再往字符串里写，只收行），逐行拿到 `文本 + y 坐标 + 主字号 + 页码`。

**(2) 删页眉页脚**（**必须有，否则每页噪音都进库**）：

判定条件（三条**同时**成立才删，误删正文的代价远大于留一行噪音）：
1. 是所在页**最前 / 最后的 1~2 行**（不依赖页面高度，比"离页边多少磅"更抗版式差异）；
2. 长度 < **120** 字、不以句末标点结尾、不是列表项；
3. **把数字归一化后**（`\d+` → `#`），该内容在**本文档 ≥ 2 个页面**的同一位置（上缘 / 下缘）出现。

> ⚠️ 第 3 条里的"数字归一化"是实测踩出来的：页眉 `... Page 1` / `... Page 2` 文本并不相同，不归一化就抓不到。
>
> 长度上限取 120 字而不是 txt 的 40 字：40 字会漏掉 pdf 常见的"产品名 - 机密 - 第 N 页"（实测样例就 41 字）。
> 敢放宽是因为位置 + 跨页重复这两条已经很硬；反过来，真有一整段正文挤在页面边缘、还每页一字不差地重复，那它就是版式噪音。

另有独立一条：**整行就是一个页码**（`第 X 页` / `Page X of Y` / `- X -`）时，哪怕只出现一次（单页 pdf）也删 ——
重复那条只管得住多页文档。

**(3) 叉段与跨页拼接**：

- 行内聚成段靠**行距**：先取全文"正常行距"参考值，超过它 **1.8 倍**就换段。
  参考值不能直接取中位数（页内夹着"页眉→正文""正文→页脚"几百磅的大跳变，页数少的文档能把中位数整个带偏），
  做法是**先用最小行距圈出候选区间（≤ 最小行距的 2.5 倍）再取中位数**。
- 行首出现列表标记（`- ` `1. ` `（1）` `第X章`）→ 换段。
- **跨页拼接**：上一页末行不以句末标点结尾 **且** 下一页首行够长（≥ 12 字，短行大概率是标题）→ 拼成一段。
  这是 PDF 最常见的断法（实测样例第一页末 `...after delivery` 就断在半句）。
  拼接后的段落**归属起始页** —— 页码锚点不能跟着挪到第二页。
- 拼回一行时的连接规则：上一行结尾是中文就直接接，否则补一个空格（英文换行断开的词靠它复原）。

**(4) 叉节 = 页**（当前落法，不做字号推断）：

`section_path = 文件名 > 第N页`（文件名一级、页码二级），切片同时带 `metadata.page_from`；
正文里也就带上了"出自哪份文档的哪一页"，可直接引用回原文。

> 为什么没有可信标题时选"页"而不是"整篇一节"：页是 pdf 天然的边界，也是唯一能对回原文的锚点。
> 代价是每页各自成节、不跨页打包（绝大多数切片本来也小于一页），以及**上传报告的 `sections` 会包含页数**
> （`1 + 页数`：文件名一级 + 每页一个）。

**PDF 明确不做的**：表格还原（只有文本流，硬做必然错）、双栏顺序还原（需坐标聚类，且失败是静默的）、
扫描件（无可抽文本 → **明确报错**，不给"导入成功、0 个切片"）。

### 4.4 旧版 doc（POI HWPF 直读）

`docx` 与 `doc` 是两套二进制格式（OOXML zip vs OLE2），标题层级的来源也不同，所以是**两个适配器**。
HWPF 的 API 面比 XWPF 窄得多，实测（8 个真实 .doc）把可用信号钉成三条：

| 来源 | 可靠性 | 处理 |
|---|---|---|
| `Paragraph.getStyleIndex()` → `StyleSheet.getStyleDescription(i).getName()` | **不可靠** | 名字是**本地化的**：俄文文档里 `Normal` 叫 `Базовый`、`Table Normal` 叫 `Содержимое таблицы`。只能当"能用就用"的**正向**信号（`Heading N` / `标题 N`） |
| **`Paragraph.getLvl()`（大纲级别）** | **可靠** | **语言无关**。实测 `Heading 1` 的段落 = `0`、正文 = `9`（Word 正文的默认值）。→ `0~5` 映射 `TITLE(level = lvl+1)` |
| `Range.getTable(p)` / `TableRow` / `TableCell` | 可靠 | → `TABLE`（markdown），表头取第一行 |

**顺序不能反**：先试样式名（能给准层级），再用大纲级别兜底。反过来的话 `Heading 3` 会被 `getLvl()`
压成同一档，层级就丢了。

**实测出来的三个坑**（都在测试资源目录的 README 里留了痕）：

1. `TableRow.isTableHeader()` 在真实表格里也返回 `false` → 表头只能按"第一行"。
2. 单元格文本以 `\u0007` 结尾，且**一个单元格内可以含多个 `\r`**（多段落）→ 必须折叠成空格。
3. 表格里每一行末尾还有一个"行结束段落"，它的文本是纯控制符。遍历时必须用 `Table.getEndOffset()`
   **把整张表一次跳过去**，否则单元格会被当正文再来一遍。

**代价（必须说清楚）**：老 `.doc` 绝大多数段落是 `Normal` —— **实测 7 个真实样例里只有 1 个带标题样式**。
这类文档整篇落进一个 `section_path`（= 文件名），靠 `chunk_seq` / `chunk_total` 保序，
与"没有标题的 docx"表现完全一致。

**明确不做**：Word 6 / Word 95（`OldWordFileFormatException`，另有一套 `HWPFOldDocument`，
**报错并提示另存为 .docx**）、文本框里的文字（`getMainTextboxRange()` 是另一个 story，与 docx 保持一致不读）、
正文里的叉页符 `\f`（不用它做页码锚点：同一个"Word 文档"在 `.doc` 与 `.docx` 两个格式下叉节语义会不一致，且 `\f` 在 Word 的文本模型里同时用于叉页与叉节，计数可能多算。宁可两个 Word 格式表现一致：叉节只认标题）。

### 4.5 excel（POI WorkbookFactory 直读）

表格是最接近"切片天生就该是表格"的格式 —— 没有结构可丢，所以适配层只做两件事：**取出每个工作表**、**渲染成 markdown 表格**。

- `.xls`（HSSF）与 `.xlsx`（XSSF）**同一个入口** `WorkbookFactory.create()`：它按文件头判类型，
  所以"`.xls` 改名成 `.xlsx`"也能正确打开，不必自己按扩展名叉叉 —— 也因此**一条策略覆盖两个扩展名**。
- **叉节 = 工作表**：`section_path = 文件名 > 工作表名`，与 pdf 的「文件名 > 第N页」同形。
- 每个工作表整体渲染成一张 `TABLE`；单表超长时由切片层按数据行切、**每片重复表头**（复用 §六规则）。

四处实测结论（都在探针里验过，别再靠推理改回去）：

| 坑 | 实测现象 | 处理 |
|---|---|---|
| **公式格** | 不传 `FormulaEvaluator` 时 `formatCellValue` 返回的是**公式文本** `C2*2`，不是值 | 传 evaluator 取真值；个别函数算不出来（外部引用 / 新函数）时**退回公式原文**，不让一格毁掉整张表 |
| **稀疏表** | `getFirstRowNum()..getLastRowNum()` 区间可以很大；`Sheet` 的迭代器只产出**真实存在的行** | 用 `for (Row row : sheet)` 遍历，不按区间 |
| **合并单元格** | 只有左上角有值，其余格子是空的 | 按合并区域**回填**，否则纵向合并的「类别」列只有第一行有值 |
| **远端杂散格** | 一个被误格式化的格子能让 `getLastCellNum()` 返回上万 | 单行取值列数**上限 256**（防脏数据的闸门，不是功能上限） |

取值统一走 `DataFormatter`：日期 / 数字按单元格自己的格式串出来（`2026-05-29`），而不是序列号。
全空的工作表跳过；**所有工作表都为空 → 明确报错**，不给"导入成功、0 个切片"。

## 五、图片怎么办

| 方案 | 成本 | 建议 |
|---|---|---|
| **A. 只留占位符**：`[图片: alt文字]`（docx 的 alt 常为空 → `[图片]`） | 零 | ✅ **默认** |
| B. OCR 抽文字：Tika OCR / Tesseract + 中文语言包 | 原生依赖 + 语言包 + 图像预处理；扫描件质量差、错误文本入库后无法区叉真假 | ❌ 不做 |
| C. 图片存对象存储 + 多模态向量 | 需要多模态 embedding 模型，与当前单向量模型架构冲突 | ❌ 不做，另一条路 |

**理由**：图片里有关键信息的场景（扫描件、图表）在 A 方案下就是抽不出内容 —— 但它本来也不该被悄悄灌进知识库。
宁可**明确不收录**，也不给一堆 OCR 错字。若将来要做，B 方案要单开配置开关 + 上传报告里明确标注"已 OCR / 未 OCR"。

**但必须有一条兜底**：整篇抽取出的文字几乎为空（扫描版 PDF 的典型特征）→
**报错"该文件没有可抽取的文本（可能是扫描件或纯图片），请提供文字版"**，
而不是"导入成功、0 个切片"。（这条比 OCR 重要得多。）

## 六、表格怎么办

**转换**：docx 表格 / doc 表格 / excel 工作表 / md 表格 → **markdown 表格**（`| 表头 | ... |` + `| --- |`）。

四个格式的表格**共用同一个渲染实现**（`MarkdownTable`）：列齐平、单元格转义、截断只写一份 ——
检索侧的表必须长得一样，不然 BM25 的字段权重就没法统一。各格式只在"格子从哪来"上不同
（docx 由 POI 直接给合并后的格子、excel 要自己按合并区域回填）。

**为什么是 markdown 而不是纯文本**：纯文本会丢掉"哪一列是哪一列"，表头与数据行的对应关系一断，这条知识就废了。markdown 表格同时让 BM25（表头词）和向量（表头 + 数据同现）都能吃到。

**切片规则**：
1. **整表独占切片**，不与前后段落合并（表格语义自足，混进段落反而两头不讨好）；
2. 表格**不加句子级重叠**（重叠对表格无意义）；
3. 超 `max-chars` 时**按数据行切**，**每一片都重复表头行**（否则第 2 片起就没有列名了）；
4. 单行仍然超长时，**整行随所在叉片保留，不硬切** —— 硬切出来的不再是合法表格行，
   与其灌一段残缺的行，不如让这一片超一点。

## 八、一份示例走完全程（md）

原文 `会员手册.md`：

````markdown
# 第一章 会员规则

会员体系叉为三个等级。

## 一、注册条件

会员注册需提供手机号。

> 注意：未成年人需监护人同意。

| 等级 | 折扣 |
| --- | --- |
| 黄金 | 9折 |
| 白金 | 8折 |

## 二、权益

```bash
curl -X POST /api/member/register
```

会员可享受专属客服。

# 第二章 退款政策

签收后七日内可申请退款。
````

**产出 5 片**：

| # | section_path | 正文 | 说明 |
|---|---|---|---|
| 1 | 第一章 会员规则 | 会员体系叉为三个等级。 | 章下开篇段落（短但**不合并到下一节**，因为跨标题） |
| 2 | 第一章 会员规则 > 一、注册条件 | 会员注册需提供手机号。\n> 注意：未成年人需监护人同意。 | 段落 + 引用同一节内打包 |
| 3 | 第一章 会员规则 > 一、注册条件 | \| 等级 \| 折扣 \| ... | **表格独占一片**，不并入上一片 |
| 4 | 第一章 会员规则 > 二、权益 | 代码块（`curl` 命令原样整块保留）+ 会员可享受专属客服。 | 代码块**不被切成两半**，其后段落可与其同片 |
| 5 | 第二章 退款政策 | 签收后七日内可申请退款。 | 撞标题即断 |

**与 txt 的差别一目了然**：标题层级是**读**出来的（3 级也认得出），章节边界**不可能**判错，表格和代码块**结构完整**。

## 九、配置

**不加新的切片参数。** 沿用现有三项（`max-chars` / `overlap-sentences` / `min-chars`）。
理由：表格 / 代码块的长切规则由 `max-chars` 直接复用；OCR 不做就不需要开关；标题层级来自格式自身，不需要阈值。

另有两项与格式无关、上传侧生效的：

| 配置 | 值 | 说明 |
|---|---|---|
| `domainplane.rag.allowed-extensions` | `[txt, md, markdown, docx, doc, pdf, xls, xlsx]` | 白名单 |
| `domainplane.rag.max-chunks-per-document` | `2000` | 单文件切片数上限，超限直接拒绝并提示拆叉。几百页的文档一次能产出几千片，一次上传就能堵死导入队列 |

## 十、怎么验证

复用现有机制，**不新增接口**：

1. **切片预览 txt**（已落地）—— 上传任意受支持格式后到 `%ProgramData%\DomainPlane\chunks` 看切片，这是最直接的验收方式；
2. **每种格式一份样例集**放测试资源，单测断言：md 的 6 级标题 / 代码块不被切断 / 表格整片；docx 的 Heading 层级 / 表格结构 / 页眉页脚不出现在正文；pdf 的页边界 / 页眉页脚被删 / 跨页句子被拼；doc 的表格 / 大纲级别认标题 / Word 6 报错话术；excel 的叉表叉节 / 公式取值 / 合并回填 / 全空报错。
3. **上传报告**（已有 `sections` / `droppedLines`）加上"页数 / 表格数 / 图片数"，让用户一眼看出解析到什么。

> **doc 与 excel 的样例性质不同**：excel 的样例在测试里现造（POI 可写，两种容器都能造）；
> **doc 的样例必须是真的**——HWPF 的样式表、表格遍历、控制符与实际二进制布局强相关，现造不出来，
> 靠推理也必错。所以引了 3 个 Apache-2.0 的真实 .doc 作为 fixture（来源与 SHA-256 见测试资源目录的 README）。

## 十一、明确不做

- 图片 OCR（默认不做，理由见 §五）
- PDF 表格还原、双栏顺序还原
- 扫描版 PDF（识别为"无文本"并报错，不静默成功）
- docx 的脚注 / 批注 / 修订痕迹 / 嵌入对象（Excel 表、Visio 图）
- md 的脚注、内嵌 HTML 块渲染（剥标签留文字）
- 目录页特判（交给 `min-chars` 合并，与 txt 同一处理）
- 跨格式的 `section_path` 统一编号（md 的 `#` 与 docx 的 `Heading 1` 直接当作层级，不做语义对齐）
- **Word 6 / Word 95 的 `.doc`**（另一套 `HWPFOldDocument` API，实测会抛 `OldWordFileFormatException` →
  报错并提示另存为 .docx）
- **`.doc` 文本框里的文字**（另一个 story；`getMainTextboxRange()`，与 docx 保持一致不读）
- **用 `.doc` 的叉页符 `\f` 做页码锚点**（刻意不用：同一个"Word 文档"在 `.doc` 与 `.docx` 两个格式下叉节语义会不一致，且 `\f` 在 Word 的文本模型里**同时用于叉页与叉节**，计数可能多算。宁可两个 Word 格式表现一致：**叉节只认标题**）
- **excel 的图表 / 图片 / 批注**（只取单元格；图表不是单元格，没有文本可供检索）
- **`xlsm` / `docm`（宏格式）**（技术上都已被读取器覆盖，只是没进白名单 —— 要支持就是白名单加一项）

## 十二、落地范围与失败兜底

| 部叉 | 状态 |
|---|---|
| `Block` + 叉派器 + md 解析器（纯自研） | 已落地 |
| docx（POI 直读：标题 + 表格） | 已落地 |
| 上传入口叉叉（二进制不解码）+ 白名单 + 切片上限 | 已落地 |
| pdf（PDFBox 抽行 + 页眉页脚清洗 + 跨页拼接） | 已落地 |
| 旧版 doc（HWPF：样式名 + 大纲级别 + 表格） | 已落地 |
| excel（`WorkbookFactory`：工作表 → markdown 表） | 已落地 |
| pdf 标题字号推断 | **未做** —— 现在 pdf 按「页」叉节 |

**依赖**：`.xls` 的 HSSF 在 `poi`、`.xlsx` 的 XSSF 在 `poi-ooxml`，都已在依赖树里；本设计唯一新增的构件是 `poi-scratchpad`（HWPF 只在它里面）与 PDFBox。

**失败兜底**（统一口径：不给"导入成功、0 个切片"）：

| 情况 | 行为 |
|---|---|
| docx 解析失败（加密 / 损坏 / 其实是 `.doc` 改了扩展名） | 直接报错 |
| 一个内容块都解析不出来（整篇图片） | 直接报错 |
| 加密 pdf | 直接报错 |
| 抽不出文字的 pdf（扫描件） | 直接报错，提示提供文字版 |
| Word 6 / Word 95 的 `.doc` | 报错并提示另存为 `.docx` |
| 所有工作表都为空 | 直接报错并说清怎么办 |

**一条一致性约定**："老 Word 文档"的两个格式（`.doc` / `.docx`）在切片语义上刻意保持一致 —— 都是"标题叉节，没有标题就整篇一节"。唯一的差别是 `.doc` 多了一路"大纲级别"兜底。
