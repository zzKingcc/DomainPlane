# 工具体系

工具是这个项目唯一能让模型"动手"的通道。它要同时满足三个互相拉扯的要求：写起来像普通 Java 方法、按域自动裁剪、远程实例也能挂进同一个目录。本文讲怎么声明、怎么被看见、怎么被执行、以及审批与掩码的边界在哪。

---

## 1. 声明：四条注解

```java
@Tool(
    desc = "按订单号查询订单状态",
    value = "queryOrder",                 // 可选，默认取方法名
    domains = {"default.customer"},       // 可见域
    effect = Tool.Effect.READ,            // READ | WRITE | DESTRUCTIVE
    approval = Tool.Approval.NONE,        // NONE | ALWAYS
    approvalReason = "会触发退款"          // 仅 approval=ALWAYS 时有意义
)
public String queryOrder(
        @ToolParam(value = "订单号", name = "orderNo", required = true) String orderNo) { … }
```

| 注解 | 位置 | 字段 | 说明 |
| --- | --- | --- | --- |
| `@Tool` | 方法 | `desc`（必填）、`value`、`domains`、`effect`、`approval`、`approvalReason` | `desc` 是给模型看的，缺失直接启动失败 |
| `@ToolParam` | 参数/字段/record 分量 | `value`（描述）、`name`（覆盖参数名）、`required` | 参数名解析不出来也启动失败 |
| `@ToolDomains` | 类 | `value` | 类级默认可见域，方法级 `domains` 优先 |
| `@ToolAdvanced` | 方法 | `example`、`allowValues`、`sensitive` | 给参数的补充元数据：示例、枚举白名单、敏感标记 |

三个"启动失败"都是刻意的：`desc` 缺失、`@Tool` 重名、参数名解析失败——这些错误在运行期会表现为"模型不知道怎么调"，排查成本远高于启动时报错。

### `effect` 与 `approval` 不是一回事

| 字段 | 表达 | 谁在用 |
| --- | --- | --- |
| `effect` | 这件事有多危险（READ / WRITE / DESTRUCTIVE） | 远程实例的默认审批推导、管控台展示、`@ToolAdvanced` 的策略 |
| `approval` | 这次调用要不要人工点确认 | 本地工具的审批判定 |

**本地工具只看 `approval`**：`approval = ALWAYS` 才走中断，`effect = DESTRUCTIVE` 但 `approval = NONE` 不会中断。远程工具（`tool-provider` / MCP）在未显式声明 `requiresApproval` 时，才按 `effect != READ` 推导。

这条不对称是历史造成的，但保留有理由：本地工具是"自己写的代码"，作者明确知道要不要审批；远程工具的清单来自别的进程，`effect` 是它能给出的最强信号。

## 2. 可见性：沿域链累加

### 域解析优先级

```
@Tool(domains = {...})           ← 方法级，最高
  ↓ 留空
类上 @ToolDomains({...})         ← 类级默认
  ↓ 留空
"default"                        ← 隐式根域
```

留空不是"不可见"，而是"挂在根域"——根域是全树的祖先，等于全域可见。这个默认值很容易误判，所以 `ToolDescriptor.declaredDomains()` 把这个解释集中在一处。

### 可见性算法

`ToolDescriptor.visibleIn(domain)`：域 D 能看到工具 T ⟺ T 的声明域是 D 或 D 的祖先。

```
T 声明在 default.customer
  default.customer            ✓ 可见
  default.customer.aftersale  ✓ 可见（祖先声明）
  default                     ✗ 不可见（子域声明，不向下）
  default.other               ✗ 不可见
```

### 两个哨兵值

| 哨兵 | 含义 | 什么时候出现 |
| --- | --- | --- |
| `<unbound>` | 全域不可见 | 动态绑定器算出来"没有任何域能用" |
| `<revoked>` | 已撤销 | 工具被下线/回收 |

`<unbound>` 必须用哨兵而不是空列表：空列表在注册表里按"累加语义"处理，等于挂到根域、全域可见——正好是相反的效果。这个坑踩过一次，现在 `AnnotatedToolScanner` 对哨兵跳过路径校验、`ToolDomainRegistry` 对哨兵不做累加，都是有意的补丁。

### 动态工具的可见域重算

两类工具的可见域不是注解写死的，而是算出来的：

| 工具 | 判据 | 重算时点 |
| --- | --- | --- |
| `searchKnowledge` | 该域（或其祖先）绑了知识体，且知识体至少一路可用 | 启动、域配置变更、存储配置热切换 |
| `generateImage` / `generateVideo` + `checkVideo` / `synthesizeSpeech` / `transcribeAudio` / `seeImage` | 该域能解析到满足端点族的模型档案 | 模型档案变更（`ModelProfileRegistry.onChange`） |

重算走 `declareDomains()` **整体覆盖**，不是增量追加。判据要改时必须改两处（这里与执行侧），否则会出现"看得见但调失败"或"能用但看不见"——后者更难查，因为用户以为平台没有这个能力。

## 3. 执行路径

```
模型返回 tool_calls
  → ToolRouter 解析（本地 Bean / 远程实例 / MCP）
  → 审批检查（需要则停在 review，见 04）
  → ToolExecutorService 执行（有界池，超时 30s）
  → 结果回填给模型
```

| 类型 | 执行方式 | 超时 |
| --- | --- | --- |
| 本地 Bean | 直接反射调用，线程来自 `toolExecutorService` | `tool-invoke-ms`（30s） |
| 远程实例 | 反向 HTTP POST 到实例的 `/domainplane/invoke` | `instance.invoke-timeout-ms`（30s） |
| MCP | 走 MCP 客户端调用 | `callTimeoutMs`（连接级配置） |

远程调用有两个策略值得记住：

- **副本轮换**：一个 `instance-id` 可以有多个副本，按轮换挑；`attempts = min(副本数, invoke-max-attempts)`。
- **非幂等不重试**：工具声明了 `idempotent = false` 时，超时/连接失败**不再重试**——重试一个已经执行的写操作比失败更危险。

### 执行过程要不要回写给模型

域级开关 `tool-call-echo`（管控台域卡片上的开关）：控制"工具调用与结果是否作为消息回写给模型看"。关掉时模型只拿到结果、看不到调用轨迹，省 token；开着时模型能看到自己调了什么，多轮纠错更容易。

## 4. 审批与掩码

### 审批的三段

| 阶段 | 行为 |
| --- | --- |
| 判定 | `toolsRequiringApproval(domain)` 有任何命中 → 图走 `review` |
| 中断 | 发 `INTERRUPT`，payload 是待审批调用清单（**参数已掩码**） |
| 恢复 | `resume(approved=true)` 继续；`false` 注入"用户拒绝"的工具结果 |

### 掩码规则

`SensitiveMasker` 按参数名递归替换：

| 情形 | 结果 |
| --- | --- |
| 参数名命中敏感词（`password` / `token` / `secret` / `apiKey` 等） | 值换成 `***` |
| JSON 解析失败 | 整段换成 `[参数无法解析，已整体屏蔽]` |
| 工具已下线 | 整段换成 `WITHHELD` |

为什么"解析失败就整体屏蔽"：宁可让审批者看不到参数，也不能让可能的密钥漏出去。代价是审批信息不全时用户可能直接点通过——所以敏感参数的工具最好自己保证参数格式稳定。

## 5. 远程工具实例

宿主应用引入 `domainplane-tool-provider` 后，启动即自动注册并保活。

```
宿主进程启动
  → 扫描 @Tool（含接口方法）
  → POST /api/agent/tools/register
        body: {instanceId, endpoint, manifest:[{name, description, category,
                version, domains, sideEffect, idempotent, toModel,
                requiresApproval, approvalMode, approvalReason, parameters}]}
  → 每 5s 心跳（同一个 register 接口）
  → 服务端调用时 POST {endpoint}  ← 宿主侧 /domainplane/invoke 执行并回结果
```

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `domainplane.tools` | `false` | 总开关，不开就不注册 |
| `domainplane.tool-instance.instance-id` | 无（必填） | 重连必须沿用同一个 |
| `domainplane.tool-instance.endpoint` | 按本进程端口推导 | 服务端可达的回流地址 |
| `heartbeat-interval-seconds` | 5 | 心跳间隔，失败指数退避（上限 20s） |
| `request-timeout-millis` | 10000 | 回调侧等业务执行的上限 |

判死窗是 35s（`instance.timeout-seconds`），配合 5s 扫描间隔，最晚约 40s 发现掉线。服务端返回 `410` 表示"强制下线"，客户端收到后停止心跳——不要自动重连，否则刚被踢下线就又爬回来。

### 回流地址的准入

`endpoint` 是"上报方决定请求打到哪"，所以有准入检查：

| 拦截项 | 说明 |
| --- | --- |
| 非 `http` / `https` | 拒绝 |
| 带 `user:pass` 的地址 | 拒绝 |
| 通配地址 `0.0.0.0` / `::` | 拒绝 |
| 链路本地（`169.254.0.0/16`、`fe80::/10`） | 拒绝 |
| 云元数据地址（含 `100.100.100.200`、`fd00:ec2::254`） | 拒绝 |

默认**不限制主机**——工具实例通常就在内网、甚至同机，限死内网反而会让正常部署失败。要收紧时配 `domainplane.tool.endpoint.allowed-hosts`（支持精确主机与 `*.后缀`）。

### 回调侧的安全性

`/domainplane/invoke` 不做鉴权，只在启动时打一条 INFO 告警。这是已知取舍：工具实例在内网，如果加鉴权就要引入一套密钥分发，收益与成本不匹配。部署到不可信网络时，靠网络层隔离而不是应用层。

## 6. 一轮里的工具预算

`RoundSearchBudget`：`read_history` + `recall_history` 两个工具**合计每轮最多 3 次**。超了工具返回"已达本轮检索上限"，让模型基于已有内容回答。

对象每轮新建、随调用上下文传到工具线程，`tryAcquire()` 是原子的——所以跨 `agent → tools` 多个循环扣的是同一个桶。

为什么单独给这两个工具设预算：它们最容易被当"抛球游戏"用（每轮先搜十次再答），而且每次都要打 Redis + 可能的向量检索。知识检索与能力工具不受此限，各自有别的约束（知识受 `inject-top-n`、能力受超时）。

## 7. 工具名冲突与命名

| 来源 | 命名 | 冲突处理 |
| --- | --- | --- |
| 本地 Bean | 方法名（或 `@Tool#value`） | 重名 → 启动失败 |
| 远程实例 | manifest 里的 `name` | 重名 → 注册被拒 |
| MCP | `mcp__<连接>__<原始名>`，非法字符换 `_`，超 64 字符截断加哈希 | 天然带前缀，不冲突 |

模型看到的是这个名字，调用时用的也是它。改名字等于换工具——历史记录里的旧调用记录会指向一个不存在的工具名。

## 8. 踩过的坑

**`effect` 不触发审批。** 只有 `approval = ALWAYS`（本地）或 `requiresApproval`（远程/MCP）才中断。

**`domains` 留空 = 全域可见，不是不可见。** 想"只给某个域用"，必须显式写该域路径；想"暂时不给任何域用"，用 `<unbound>` 哨兵（动态工具才有）。

**工具返回给模型的内容也会进事件流。** `TOOL_RESULT` 是给前端看的，同一份内容也会作为工具消息进模型上下文，长结果两边都吃 token。

**远程工具超时不重试是正确行为，不是缺陷。** `idempotent = false` 的工具超时后重试，可能把"已经成功的写操作"再执行一次。

**改了动态工具的判据，必须同步另一处。** 判据在 binder（决定可见性）与执行侧（决定能不能真跑）各有一份，只改一处就会出现"看得见、调不动"。
