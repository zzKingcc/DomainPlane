# 架构总览

要解决的问题只有一句话：**一个 jar 同时服务任意多个业务场景，场景之间不靠部署隔离、不靠字段过滤，而靠"域"这个请求维度实时装配能力**。

本文说清三件事：代码分成哪几块、为什么这么切、一块配置或一轮对话到底落在哪个模块里。

---

## 2. 依赖方向：分成两条不相交的线

```
                 ┌──────────── server（唯一可执行）
                 │
   api ← common ← domain ← { infrastructure , runtime }
                 │
                 └── sdk-core → client-core → { chat-client , kb-client }
                                sdk-core → tool-provider
```

两条线的交点只有一个：`api`。服务端线从 `api` 一路向上，SDK 线从 `api` 旁支出去，**两侧只通过 HTTP 报文耦合**——SDK 不依赖 `domain` / `runtime` 任何一行代码，服务端也不认识 SDK 的类。

### `infrastructure` 与 `runtime` 为什么是兄弟

两个模块都只依赖 `domain`，互相零依赖：

- `runtime` 只认识 `domain` 里声明的 SPI（`KnowledgeStore`、`BlobStore`、`MemoryStore` 之类），**不认识任何适配器实现**。
- `infrastructure` 提供这些 SPI 的实现，不知道编排的存在。

这条约束的收益是具体的：换掉 ES 走向量库时，编排内核一行不用改。代价也同样具体——SPI 的粒度必须由使用方（runtime）定，不能由实现方（infra）定，否则每加一个后端就要动内核。所以你会看到 `KeywordSearcher` 只收 `(collection, query, topK)` 三个参数、`VectorSearcher` 只收向量（不负责 embed），都是为了"实现方不反过来绑架调用方"。

### `domain` 不是纯 POJO

它依赖 `langchain4j-core`（`Content` / `ContentRetriever` 这些类型）和 `spring-context`（少量 `@Component`）。这是有意的取舍：`Content` 已经在 `api` 与 `server` 之间流通，为了"纯度"再包一层自己的 DTO，等于给每片切片做一次拷贝。

## 3. 一轮对话落在哪

```
HTTP POST /api/agent/chat
  │
  ├─ Controller（server）           取域、鉴权、参数校验
  ├─ AgentOrchestrationService（runtime）
  │    ├─ 域校验 / 软删校验 / 输入清洗
  │    ├─ 取消标志复位 → 并发闸门 → 会话串行锁
  │    ├─ TurnPlanner（可选，一次主模型调用）
  │    ├─ ContextAssembler（历史窗口 + 摘要 + 卡片 + 预算）
  │    └─ 编排图：agent →（需要审批则停）→ tools → agent → … → DONE
  │         ├─ 模型调用（server 的 ModelClientFactory）
  │         ├─ 工具调用（本地 Bean / 远程实例 / MCP）
  │         └─ 知识检索（域链 → 通道 → 融合）
  └─ SSE 事件流（runtime 的 StreamSinkRegistry → server 的 WebFlux 出口）
```

按职责切开来是四层，每一层只回答一种问题：

| 层 | 只回答 | 不该出现的东西 |
| --- | --- | --- |
| `server` | "谁来装配、谁能调" | 编排状态机、检索打分 |
| `runtime` | "这一轮怎么走" | ES 客户端、HTTP 细节 |
| `domain` | "算出来是什么" | Spring MVC、Redis 会话 |
| `infrastructure` | "怎么读写外部" | 域链、预算、事件 |

## 4. 三个扩展接缝

整个系统只有三处"想加东西不用改主干"：

| 接缝 | 扩展方式 | 加一个要动哪 |
| --- | --- | --- |
| 存储后端 | 实现 `domain.rag.store.KnowledgeBackend`（store / keyword / vector 三个 Optional） | 新增适配器类 + `KnowledgeBackendsConfiguration` 加一个分支 + `SUPPORTED_TYPES` 加值；`domain` 与 `runtime` 零改动 |
| 工具 | 方法上标 `@Tool` | 本地实例随包扫描；远程实例注册进平台；MCP 连接桥接。编排侧只认 `ToolDescriptor` |
| 接入方 | HTTP + SSE | SDK 三件套只是这份报文的三个便利封装，裸 `curl` 等价 |

> 判据不是"能不能加"，而是"加完之后主干有没有多出一个 if"。三处接缝都是这个标准，所以 `KnowledgeBackend` 才会把 store / keyword / vector 拆成三个 Optional，而不是一个大接口返回 `UnsupportedOperationException`。

## 5. 状态住在哪：唯一真相源

| 状态 | 位置 | 谁写 | 丢了会怎样 |
| --- | --- | --- | --- |
| 账号 / 存储连接 / 模型档案 / 域声明 / 提示词 / MCP | `settings.path` 下 8 份 JSON | 各 Store 类 | 账号回落种子；其余配置需重填 |
| 域历史版本 | `settings.path/domains-history/v<N>.json` | `DomainStore` | 权威文件损坏时回退快照 |
| 会话记忆 | Redis `domainplane:chat:memory:*` | `DualConstraintChatMemory` | 会话接不上上文 |
| 中断断点 | Redis `domainplane:graph:checkpoint:*` | `RedisCheckpointSaver` | `resume` 报 `30001` |
| 切片原文 / 媒体附件 | BlobStore（本地目录） | `ChunkArchive` / `MediaAttachmentStore` | 索引成孤儿，需重灌 |
| 索引 | ES / Qdrant | 摄取链路 | 可重建的派生数据 |
| 在途会话（取消标志、流） | JVM 内存 | `CancellationRegistry` / `StreamSinkRegistry` | 重启即丢，这也是单实例部署的根因 |

最后一行是全系统最关键的一条约束：**会话运行态在堆里，所以现在只能单实例**。`domainplane.single-instance-guard` 只是防止两个进程同时抢同一份配置与 Redis，把它置 `false` 不等于支持多实例。

## 6. 域为什么能当隔离键

多租户系统通常走"一张表 + `tenant_id` 过滤"，代价是每个查询都要记得带条件，漏一次就是跨租户泄露。这里换了个做法：

| 维度 | 合并语义 | 隔离靠什么 |
| --- | --- | --- |
| 工具 | 沿域链累加 | 装配时按域裁剪，调用前二次校验 |
| 知识 | 沿域链累加（祖先域绑了知识体就查得到，子域的不向下） | 索引名由域路径确定性派生，"查错"在物理上等于查另一个索引 |
| 提示词 | 沿域链累加，根域片段即基底 | 拼装时只拼链上的片段 |
| 模型 | 就近覆盖 | 解析时取链上第一个绑定 |

所以越权不是"多发了一条不该发的数据"，而是"查了一个不该存在的索引"——漏写条件不会泄露，只会查不到。这件事的代价写在 `KbIndexes.nameOf` 里：索引名带 8 位 SHA 后缀、限长 80 字符，**人不可读**，排障时必须靠管控台反查而不能靠肉眼认。

## 7. 一次启动发生了什么（不联网的部分）

1. 读 `application.yaml` + 环境变量，绑定各 `@ConfigurationProperties`。
2. `InfraSettingsHolder` 合并两份配置：管控台存的（`infra-settings.json`）优先，一条都没配才用 yaml 的 `knowledge.backends` 合成默认连接与知识体。
3. 账号种子落盘（`accounts.json` 不存在时按 `accounts-seed.json` 写）。
4. 域存储加载 `domains.json`，损坏则回退最近一份历史快照；快照也全坏则拒绝启动。
5. 单实例守卫抢租约（Redis 未配则跳过）。
6. 知识检索工具与能力工具的可见域首算（`KnowledgeToolBinder` / `ModelCapabilityToolBinder`）。
7. 指标采样器启动；7 个定时任务挂上（心跳巡检、指标采样、MCP 重连、域版本巡检、删域清理、切片档案对账、孤儿 blob 回收）。
8. `McpCoordinator` 后台建连——这是唯一在启动后立刻发起的网络动作，失败不影响启动。

## 8. 几个反直觉但有意为之的设计

**`api` 里有一个 `AgentService` 的两份实现，方向相反。** `runtime` 的实现向外发事件，`chat-client` 的实现向内收事件。它们共享接口是为了让"服务端一轮对话"和"SDK 一次调用"在类型上同构；加方法时两边都要改，这是刻意保留的耦合。

**`BlobStore` 这层 SPI 在 `runtime`，不在 `domain`。** 按分层它应该在 `domain`（别的 SPI 都在那），但切片归档与媒体附件的调用方全在 `runtime`，放回去就要给 `domain` 加一个没有第二个使用者的接口。代价是"换存储实现时要多看一个包"，收益是 `domain` 不必知道字节怎么存。

**错误码分两套文案。** `message` 给运维（可以写"图检查点"这种内部术语），`userMessage` 给终端用户（只说"发生了什么 + 能做什么"）。对外出口只出后者，否则"图检查点读写失败"会被读成"图片坏了"。

## 9. 规模与口径

统计口径：`src/main/java` 下 `.java` 的非空白行（含注释），测于 2026-11-02。

- 主代码 382 类 / 53,316 行；测试 188 类 / 26,426 行。
- `server` 占主代码 52%，其中静态资源不算在内（只算 java）。
- Controller 16 个，方法级 mapping 94 个。
- 定时任务 7 个，执行器 5 个（编排 / 检索 / 工具 / 视觉 / 能力）。

这些数字会漂移，**引用时必须带日期与口径**；相对比例（测试/主代码 ≈ 50%、server 过半）比绝对值更值得关注。
