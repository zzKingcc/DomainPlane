# 模型与多模态

模型层要解决的核心矛盾：**上游服务商的参数集各自为政，但平台只能有一套统一的档案模型**。本文讲这套档案怎么建模、能力从哪来、参数怎么下发、以及图片/语音/视频这四类能力怎么挂成工具。

---

## 1. 两层配置：连接与档案

```
ProviderConnection（连哪家、用什么密钥）
   ↑ 被引用
ModelProfile（这一次调用用什么模型、开哪些能力、带什么参数）
   ↑ 被绑定
Domain（哪个域用它）
```

| 层 | 字段 | 变更影响 |
| --- | --- | --- |
| 连接 | `name`、`baseUrl`、`apiKey` | 改密钥不用动档案 |
| 档案 | 15 个字段（见下） | 改档案影响绑定它的所有域 |

分开的理由很实际：一家服务商只有一个密钥，但通常要建多个档案（对话用一个模型、向量用另一个、生图用第三个）。密钥轮换时只改连接，档案不动。

### 档案的 15 个字段

| 字段 | 作用 |
| --- | --- |
| `alias` | 展示名（页面上的名字） |
| `endpoints` | 端点族集合，决定"这个档案能干什么" |
| `input` / `output` | 模态：text / image / audio / video / file |
| `baseUrl` / `apiKey` | 覆盖连接（留空则用连接的） |
| `modelName` | 上游模型标识，原样下发 |
| `temperature` / `maxTokens` | 标准参数（字段仍在，但卡片控件已删，见 §5） |
| `contextWindow` | 上下文窗口，装配预算据此收窄 |
| `thinking` / `returnThinking` | 是否开思考、是否把思考过程回写给前端 |
| `fallbacks` | 备用模型链（**只存不生效**，见 §6） |
| `params` | 自定义参数（键值对，原样透传） |
| `protocol` | `openai` 兼容 / `anthropic` |

---

## 2. 端点族：能力的唯一判据

`endpoints` 是一个字符串集合，取值：

| 族 | 用途 | 能否绑到域 |
| --- | --- | --- |
| `chat` | 对话 | 能 |
| `embedding` | 向量化（灌库 + 查询向量） | 不能（全局唯一，单独一栏） |
| `rerank` | 重排 | 不能 |
| `images` | 生图 | 能 |
| `tts` | 语音合成 | 能 |
| `asr` | 语音识别 | 能 |
| `video` | 生视频 | 能 |

"能绑到域"的族决定能力工具是否可见：域解析到 `chat` 就有对话，解析到 `images` 就有 `generateImage`。判据是纯读的——**档案声明 + 连接可解析**，不试调用。

`embedding` 单独一栏的原因：知识库只有一个向量空间，两个向量模型并存会让同一批切片有两种坐标，检索结果没有可比性。所以它是"全局一个"，不是"每个域一个"。

## 3. 能力由手选模态反查与探测实测共同决定

**能力在添加弹窗里由用户手选输入 / 输出模态**（`input` / `output`），端点族由 `AdminModelProfileController#familiesFromModalities` 从模态本地反查（零上游请求）。保存是纯登记：零上游请求、不读清单、不测维度。

这条是被标准服务商逼出来的：OpenAI / DeepSeek 官方的 `GET /v1/models` 只回 `id / object / owned_by`，根本不声明能力。把"能力"焊在清单读取上，最常见的档案必然落进「未声明类型」这第三种状态 —— 既绑不了域，也当不了向量模型，而且它不报错。所以能力不来自清单，而来自用户手选的模态（本地反查端点族）或运行期实测（下面的探测）。声明错了由运行期给明确的 404 / 400，不需要在配置期造一个谁都不认的中间态。

页面上**没有「识别用途」按钮**。`POST /admin/model-profiles/suggest` 端点仍存在，但只给脚本读服务商 `/models` 清单用，返回 `endpoints` / `input` / `output` / `source=provider` / `note`；管控台不调用它，清单不再是能力来源，结果也不会用来预勾任何勾选框。

> 服务商私有的清单语义（例如某家的 `GET /models?sub_type=chat|embedding|…` 过滤）已整套移除：
> 那套东西只有一家认，且"忽略该参数、原样回全量清单"会被误读成"这个模型命中所有子类型"，
> 历史上就把一个纯对话模型标成了「向量 + 重排 + 生图」。能力要么来自手选模态的本地反查，
> 要么来自实测（下面的探测），清单只当只读参考资料。

探测是卡片上的实测，会把结论写回档案（会真打上游、花少量额度）：

```
POST /admin/model-profiles/test          ← 连通性
POST /admin/model-profiles/detect        ← 单个档案全能力探测（?mode=confirmed|override）
POST /admin/model-profiles/detect-all    ← 批量（只补不删）
```

探测按端点族**串行**真打上游：

| 探什么 | 打到哪 |
| --- | --- |
| 文本 / 看图 / 听音频 / 看视频 / 读文件 | `/chat/completions`（分别构造对应模态的输入） |
| 生图 | `/images/generations` |
| 语音合成 | `/audio/speech` |
| 语音识别 | `/audio/transcriptions` |
| 向量 | `/embeddings` |
| 重排 | `/rerank` |

结果写回档案有三种语义：

| 语义 | 方法 | 什么时候用 |
| --- | --- | --- |
| **只补不删**（默认） | `withConfirmed`（并集） | 单卡探测 `mode=confirmed`（默认）与批量 `detect-all`。探到了就是支持；状态按实际探测结果落库 —— 仅端点确实不存在（404 / 405 / 415 / 501）才记 `UNSUPPORTED` 并自动撤掉 embedding 族，其余一律 `UNCONFIRMED`，不把"没确认到"当"确定没有"去删能力 |
| **整体覆盖** | `withProbeResult`（允许空值） | 单卡探测 `mode=override`，需用户在确认框里显式选。以实测为准，没确认到的模态一起清掉 |
| **手动移除** | `withoutFamilies` | 卡片上点端点族标签的「×」（`PUT /admin/model-profiles/families/remove`）。模态随之剪枝：输出按"剩下的端点族里还有谁能产出它"清，输入只留 `text`（媒体输入只走对话端点），一族都不剩时输入 / 输出一并清空 |

只补不删是默认，因为探测本身**可能失败**（超时、样本被拒、路由不全），拿"这次没确认到"去删能力，
等于让一次网络抖动删掉一份能用的配置。要覆盖就明说。
反过来，探测只有端点确实不存在（404 / 405 / 415 / 501）才写 `UNSUPPORTED`，`unsupportedFamilies()` 会把 embedding 族自动撤销；其余（400/422/5xx/429/超时/网络抖动）一律 `UNCONFIRMED`，不写"不支持"——
这也是为什么端点族标签是可点的。

写回的三条附带规则：

- **连不上服务商地址**（NETWORK）时其余探针标 `NOT_EXECUTED`，不再挨个重试；401 / 配置错**不短路** ——
  网关常按端点授权，chat 401 不代表 embedding 不可用。
- **请求体兼容回退**：`content` 只接受数组、或只认 `max_completion_tokens` 这两类明确的 400 会各回退一次
  （最多 3 次尝试，不循环）；其余 400 原样返回，不猜。
- **超时按端点分级**：chat 60s、embeddings 20s、images 180s、tts 120s、asr 60s、其它 30s。
  一个 20 秒常量会把生图、TTS 一律截成「未确认」——实测里生图 30 秒还没回。
- **2xx 不等于产出**：`/embeddings` 要验 `data[].embedding`，`/chat/completions` 要验 `choices`
  （首项带 `message` / `delta` / `text`）。有的中转对"没有 HTTP 对话能力"的模型回
  `200 {"status_message":"Success."}`，只认状态码就会得到一份"全模态对话模型"的假档案 ——
  实测撞到过：`qwen-audio-3.1-realtime-flash` 经某中转，纯文本、数组 content、`modalities` 三种请求
  全是这个空壳。
- **实时语音模型不走 HTTP**：`*-realtime-*`（Qwen-Audio-Realtime、OpenAI Realtime 等）只用
  WebSocket / WebRTC 的持久连接，音频在 `response.audio.delta` 事件里，既不是 `/chat/completions`
  也不是 `/audio/speech`。探测会如实报「未确认」，并把 chat 那条归为 `PROTOCOL`
  —— 弹框里只给一行短原因「需 WebSocket」，完整说明留在服务端 `note` / 日志里。
  这类档案在当前架构下绑到域上也是调不通的。

每条探针的**诊断**（状态码 / 失败归类 / 脱敏后的回执摘要 / 尝试次数）随 `detect` 返回，
但**页面不摊开这些细节**：只弹一个结果框，分「支持」与「不支持 / 未确认」两区，
失败项固定三列（名称 · HTTP 状态码 · 2~6 字短原因）。回执原文、尝试次数、
内部哨兵状态码（`-1` 连不上 / `-2` 超时）、实时语音长说明都不进弹框，要追细节看服务端日志。
`note` 仍由后端生成，供批量探测 `detect-all` 与日志使用，单卡探测的弹框不再引用它。

保存时补基线模态是纯本地映射，不是猜能力：`chat`→text/text、`embedding`→text/embedding、`rerank`→text/score、`images`→text/image、`tts`→text/audio、`asr`→audio/text、`video`→text/video，多选取并集；用户或脚本显式传了 `input` / `output` 时原样采用。**不补会出事**：`validateForFamily` 要求端点族已知且输入 / 输出模态非空，只删识别不补模态的话，用户看到"保存成功"，到域空间页才撞上"模态未知"。新弹窗走模态→端点族反查，不显式传 `endpoints`；`withBaselineModalities` 只服务脚本显式传 endpoints 的旧契约。

## 4. 协议分派

`protocol` 只有两个值：

| 值 | 走哪 | 说明 |
| --- | --- | --- |
| `openai`（默认） | OpenAI 兼容 `/chat/completions` | 绝大多数服务商 |
| `anthropic` | `/v1/messages` | Anthropic 原生协议 |

分派在构造客户端时完成，不是运行期按响应判。**切换协议会清空 `params`**——两套协议的参数集不重叠，留着只会发出去一堆上游不认识的字。

> 想系统看 OpenAI 规范的端点、通道与模态矩阵（含 Realtime、`/responses`、音频三条路的区别，
> 以及"哪些常见端点其实不是 OpenAI 规范"），见 [15-OpenAI 风格 API 全景](15-OpenAI风格API全景.md)。

## 5. 参数下发：对话走两条通道，其余看适配

参数能不能真的出现在请求体里，只取决于**注入点是否存在**，不取决于卡片上画了什么。按端点族分三种：

```
对话（chat / 流式 / Anthropic 分派）
  → 标准字段：temperature、max_tokens（直连 builder setter）
  → JSON 文本框：其余键原样进 customParameters
  → 对话族不再有 adapter schema

向量（embedding）
  → 卡片上不给参数入口；维度不是配置项，一律取模型原生维度（实测后建索引）

图像 / 重排 / TTS / ASR / 视频
  → ModelEndpointClient 逐字段拼请求体，从不读 profile.params
  → 卡片上不给任何参数入口
```

适配机制已整套删除：`ModelAdapterRegistry`、`resources/adapters/`、`GET /admin/model-adapters`
以及卡片上的绿框 / 「已适配」徽标全部下架。参数面只剩一条通道 —— 用户自填的 JSON 文本框，
由 `CustomParamsGate` 统一把关（温度、单次最大输出也在这里写）。

下面两节记录当初摘掉对话族适配时的取舍，作为这段改造的留档。
### 当初为什么把对话族从适配里摘出来

适配层对对话模型的收益是负的：

- 参数表硬编码在 classpath 的 JSON 里。上游加一个新参数（`reasoning_effort`、`top_k`…）就得改资源文件、重启、等发版，而这一层本来只是"把用户填的键换个名字"。
- `std` / `wire` / `enabledWhen` 把"这个键最后长什么样"拆到三处决定，排查一次要顺着读三段代码。
- 最要命的是它反而**收窄**了能下发的键集合：命中适配后，凡不在 schema 里的键都会被静默丢掉 —— 用户填对了名字也可能不生效，且没有任何报错。

摘掉之后对话族只剩两条通道，"填的就是发的"成为可验证的事实。代价是校验责任交回给上游：键名写错不会被预先拦住，报错来自服务商的 400。`CustomParamsGate` 只保证不把结构性垃圾（非法键名、嵌套过深、超大载荷、凭证字段）发出去。

### 标准参数为什么收回到 JSON 里

曾经 `temperature` / `max_tokens` 在卡片上各有一个数字框，走 `PUT /admin/model-profiles/tuning`。
后来这套控件删掉了（添加弹窗里的同名输入框也一并删除）：卡片右侧同时摆"温度 / 最大输出 / JSON 框"三处输入，用户不知道该改哪，
而 `CustomParamsGate` 又把同名键在 JSON 里拒掉，等于同一个数只能从一条特定的路进。

现在它们和别的私有参数一样写在 JSON 里（`{"temperature": 0.7, "max_tokens": 512}`）。
为了不留"两条路各发一遍"的隐患，保存 JSON 时若发现带了这两个键，会把档案上遗留的老字段
（`temperature` / `maxTokens`）一并清空 —— **以 JSON 为准**是唯一语义，而不是一个用户看不见的优先级。

`CustomParamsGate.STD_CONFLICTS` 因此只剩一个键：

| 被拒键 | 原因 |
| --- | --- |
| `dimensions` | 维度由模型决定，下发它只会让上游返回另一种长度、与本地索引失配 |

这张表曾经有 10 个键（`top_p`、`seed`、`stop`、`response_format`、两个 `penalties`、
`top_logprobs`、`dimensions`、`temperature`、`max_tokens`）。前几个被拒的前提是"命中适配时还能从
schema 的滑杆走到 builder"；对话族摘掉适配之后它们**没有第二个入口了**，继续拒就是纯丢参数。
`temperature` / `max_tokens` 随卡片控件删除一起放开，理由相同。

**上下文长度**（`contextWindow`）的卡片输入框也一并删了：留空即未声明，装配预算按配置值走
（`min(配置预算, 该值 - 输出预留 - 边际)` 只在声明了值时才收紧）。要让某份档案收窄预算，
仍可用 `PUT /admin/model-profiles/context-window` 由脚本写。

### 老键名的迁移

改造前页面上写的是驼峰 UI 键，真实下发靠 adapter 的 `wire` 翻译。翻译层移除后，存量档案里的这些键会**原样带着驼峰名发出去** —— 上游忽略、不报错、参数静默失效，是这次改造最难在测试里发现的一种坏法（配置看着对，请求也成功，就是没生效）。

`ChatParamMigration` 在 `ModelProfileStore.load()` 时跑一遍：

| 旧键 | 新键 | 备注 |
| --- | --- | --- |
| `reasoningEffort` | `reasoning_effort` | |
| `topP` | `top_p` | |
| `topLogprobs` | `top_logprobs` | |
| `responseFormat` | `response_format` | 值包成 `{"type": ...}` |

没有旧键时返回 `null`，不改任何东西，所以可以反复跑；新旧键同时存在时保留新键、丢旧键（新键是用户手填的，旧键是历史残留）。

### 四道闸门

`CustomParamsGate` 管所有 JSON 框：

| 闸门 | 拦什么 |
| --- | --- |
| 黑名单 | 模型名、地址、协议、凭证这些不交给用户 |
| 形状 | 键必须是合法标识符，值只允许标量 / 字符串数组 / 一层简单对象 |
| 量 | ≤ 32 键、≤ 4096 字节 |
| 标准键冲突 | 只剩 `dimensions` 一个键（见上表） |

### 卡片上的「自定义参数（JSON）」文本框

| 项 | 值 |
| --- | --- |
| 可见条件 | `customParams.applies`（= `mayBeChat()`），服务端算好下发 |
| 入口 | `models.html` 统一档案卡片，来源 `GET /admin/model-profiles` → `customParams` |
| 保存 | `PUT /admin/model-profiles/custom-params`，收 `{alias, paramsJson}`（文本，不是 map） |
| 回填 | `customParams.paramsJson`（空参数回**空串**，不回 `{}`：空括号会让人以为"本来有内容被我删了"） |
| 上限与提示 | 上限由服务端把关（`customParams.limits` / `stdKeys` 仍随视图下发，供脚本参考）；卡片上不再展开说明文字，标题后只留一句「JSON · 留空即不发送」 |

温度 / 最大输出改由 JSON 框承载后，`PUT /admin/model-profiles/tuning` 在管控台上没有入口了，
只留给脚本（它仍是**全量替换**：报文必须带上 `params`，否则改一次温度就把自定义参数一起清空）。

收文本而不是 map 是为了报错：JSON 写错一个逗号时，解析在参数绑定阶段就失败了，拿不到原文本，也就没法说"第 2 行第 3 个字符附近"。

**这条 UI 曾经整段丢掉过**（管控台从各页内联脚本迁到 `frontend/src/pages/*.js` 时只搬了绿框，文本框没搬）：后端 `profileView` 一直在下发 `customParams`，保存口也一直在，前端却没有任何读者 —— 表现是"未适配的卡片上什么参数都改不了"，而服务端看起来完全正常。判断这类"掉件"的方式：搜字段名有没有读者（`customParams` 在 `models.js` 里零命中就是丢件），而不是先怀疑后端。

**可见条件也曾经错过**：早期前端用 `bindable`（= `domainBindable()`，问的是"能不能绑到域"）判断要不要出框，而正确判据是 `mayBeChat()`（问的是"值能不能下发"）。两者不等价，"声明了 chat 但输入模态没填"的半识别档案两个都不满足前者，于是卡片上一个框都没有。现在这个结论只由服务端给（`customParams.applies`），前端不再自己拼。

## 6. 解析与回退

```
域 D → 沿链找第一个绑定了 chat 档案的域 → 该档案
        ↓ 没有（或档案不可用）
      → 90005 / 91001
```

注意实际只走**一条**链。`ModelProfile.fallbacks` 这个字段目前**只存不生效**（源码注释"M3 生效，先只存"，全仓 main 里除读写与序列化外没有任何读者），配了也不会被拿去试下一个模型。真正决定"用哪个模型"的只有域绑定 + 域链继承：本域没绑就往上找祖先域，绑了就不能用则直接报错。

`contextWindow` 会向下游传：装配预算取 `min(24000, 窗口余量)`，避免换小窗口模型就撞 400。

## 7. 多模态

### 上行：文字进消息，其余走附件通道

请求体里是**内容块**，不是附件 ID：

```json
{ "contents": [
    { "type": "IMAGE_BASE64", "base64": "...", "mime": "image/png" },
    { "type": "AUDIO_BASE64", "base64": "...", "mime": "audio/mpeg" },
    { "type": "TEXT", "text": "这段录音说了什么" }
] }
```

`ContentType` 共 7 种：TEXT、IMAGE_URL、IMAGE_BASE64、AUDIO_URL、AUDIO_BASE64、VIDEO_URL、VIDEO_BASE64。AUDIO_URL 在入口即被拒——转写要把字节传给 ASR 端点，只有地址取不到内容。

**只有 TEXT 进主模型消息。** 其余内容块不分类型，在编排入口统一存进暂存区换成引用名，本轮注入一份按类型分组的附件清单：图片指到 `seeImage`、音频指到 `transcribeAudio`，暂无取回通道的类型（当前是视频、以及将来新增的文件一类）如实写明"没有取回内容的工具"。模型需要内容时按引用名调工具取回；上游请求里不出现任何媒体字节，也不出现 `input_audio` / `video_url` 之类的私有部件。

这样"用户发没发文件"与"上游模型支持哪种模态"彻底解耦。代价是多一次工具往返；换来的是上游静默丢弃未知部件时，不会再出现"文件明明发了、模型说没收到"。新增一种媒体类型只需在 `ContentType` 加枚举、在 `MediaAttachmentStore.Kind` 加词表，清单会自动把它归到保守分支。

任一附件暂存失败即本轮失败：字节已不在消息里，少一个引用名就是少一份附件，而模型无从知道原本有几个。带图时还会先确认域链上有能承接 `seeImage` 的视觉模型，没有就发 `MODEL_NO_VISION`。

### 暂存区

| 项 | 值 |
| --- | --- |
| 登记表 | Redis `domainplane:media:attachment:{内容哈希}` |
| 字节 | BlobStore `attachments/` |
| TTL | 30 分钟（`vision.attachment-ttl-minutes`） |
| 续期 | 活跃会话每轮续期 |
| 孤儿回收 | 每 5 分钟扫一次，对象年龄 < 5 分钟不回收 |

ID 由内容哈希派生：同一张图传两次是同一个 ID，不占两份空间。

"先落字节、后登记"的顺序 + 5 分钟年龄护栏是一对：反过来的话，巡检可能在"字节已写、登记未写"的窗口里把活附件当孤儿删掉。

### 生成结果怎么回到调用方

能力工具（生图 / 生视频 / 合成语音）产出的媒体分两条路走，**不能合成一条**：

| 路 | 内容 | 落点 |
| --- | --- | --- |
| 工具返回值 | 只有引用名（`img_xxx` / `aud_xxx` / `vid_xxx`） | 图状态 → 模型上下文 → 会话归档（持久） |
| `MEDIA` 事件 | 原始字节（base64）或服务商地址 | 只在 SSE 事件流里过一道，不落任何持久记录 |

返回值不能带字节：它同时进模型上下文与会话归档，一张 1024×1024 的图 base64 上兆，
塞进去等于把整段图像数据写进对话历史。`MEDIA` 事件由 SSE 出口的 `GeneratedMediaRelay`
组装——工具把字节挂到本轮会话缓冲，出口每转发一个事件前先清空缓冲并插入 `MEDIA`。
挂在出口而不是编排层，是因为编排层持有字节就会被检查点带走。

不依赖"工具调用回写"开关：那个开关关掉时没有 `TOOL_RESULT`，但 `MEDIA` 仍会随下一个
事件（哪怕只是 `DONE`）下发。缓冲按轮生灭（`doFinally` 清空），单轮上限 8 份，超限丢最早的。

### 透明底合成白底

`ImageAlphaFlattener`：带 alpha 通道的 PNG 先合成到白底再送上游。原因很朴素——很多视觉模型对透明区域的处理是把 alpha 当黑色，黑色底上的深色文字直接消失。

### 五类能力工具

| 工具 | 端点族 | 判据 |
| --- | --- | --- |
| `generateImage` | `images` | 域能解析到含该族的档案 |
| `generateVideo` + `checkVideo` | `video` | 同上，两个工具**同进同退**（生成是异步的，必须能查状态） |
| `synthesizeSpeech` | `tts` | 同上 |
| `transcribeAudio` | `asr` | 同上 |
| `seeImage` | `chat` + `input` 含 image | 有主模型 ∧ 档案声明视觉输入 |

判据在 `ModelCapabilityToolBinder`，重算信号是模型档案变更（`ModelProfileRegistry.onChange`）。**判据必须与执行侧一致**：只改一处会出现"看得见调不动"或"能用但看不见"。

超时分开配：看图 60s，其余能力 120s（生图/生视频常 30–90s）。

## 8. 常见故障

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `91001 MODEL_NO_VISION` | 这轮带图，域没解析到视觉模型 | 绑一个 `input` 含 image 的档案（卡片无模态编辑口，需重新手选模态或再探测补齐） |
| `91000 MODEL_ENDPOINT_UNSUPPORTED` | 档案没声明该端点族，或协议不支持该端点 | 补 `endpoints`；Anthropic 协议的图/视频端点未适配 |
| `90006` / `90007` / `90008` | 上游欠费 / 凭证无效 / 请求被拒 | 这三类不可重试，看事件体里带的上游原文 |
| 参数改了不生效 | 现在没有键名翻译层了，填什么就发什么：键名与服务商文档不一致时上游静默忽略 | 照服务商文档填线上字段名（`reasoning_effort` 而不是 `reasoningEffort`）；`temperature` / `max_tokens` 写在自定义参数 JSON 框里 |
| 换模型后检索报维度错 | 向量维度变了，索引要重灌 | 重灌 |
| 探测全绿但调用报错 | 探测用的是最小请求，实际参数超出模型能力 | 看上游 400 原文，收窄 `maxTokens` / 关思考 |

## 9. 踩过的坑

**标准字段不能同时写进 `params`。** 会发两遍，上游行为取决于实现。`CustomParamsGate` 只拦 `dimensions` 一个；适配档案作者自己配的时候没人拦（当年 `std: true` 那批键就是这么来的）。

**摘掉一个 schema 会顺手废掉一批"看起来只是限制"的闸门。** 这次 `STD_CONFLICTS` 从 10 个键收窄到 1 个就是被这件事逼出来的：前 9 个键被拒的**理由**是"它们还有另一条路可走"，路一拆，拒绝就只剩副作用。删任何一层之前，先查它周边的拒绝规则是不是还有存在依据。

**探测写回默认是并集，不是覆盖。** 想"降级"某个能力，要么在探测确认框里显式选「覆盖写回」，
要么在卡片上点端点族标签的「×」手动移除。注意探测只有端点确实不存在（404 / 405 / 415 / 501）才写 `UNSUPPORTED`，一次 400 / 5xx / 超时只是 `UNCONFIRMED`，不能当成"确定没有"。

**`max_tokens=1` 会把"请求体不被接受"伪装成"模型不能用"。** 实测两家服务商：一家对裸字符串
`content` 直接 400（要求数组），另一家的新模型只认 `max_completion_tokens`。两者都被归到
「未确认」，卡片上看起来和"这个模型什么能力都没有"一模一样，而真正的原因只写在日志里。
现在的做法：探针用 16 token + 两类明确的 400 各回退一次 + 失败原因（HTTP 状态码与短描述）直接回页面。

**协议切换清空 `params` 是有意的破坏性操作。** 从 OpenAI 切到 Anthropic 再切回来，之前的自定义参数不会回来。

**能力工具的可见性靠 binder 重算，不靠每次请求现算。** 所以改完模型档案，生效点是"下一次 onChange 之后"，不是"下一条消息立刻"——通常是毫秒级，但如果改了 Redis 里的档案而没走接口，binder 不会知道。

**分桶的依据必须和消费的依据是同一个。** 旧版按"是不是纯向量"把档案物理分到两个 Map，`list()` 又按 `isEmbedding()` 从全量重新过滤；双类型档案于是两边各出现一次，前端还得再 `filter(alias !== 当前向量)` 去重。现在只有一张表，"这份档案用来干什么"由消费侧槽位决定，不再由它存在哪决定。

**"成功但要用户再表态"不能套错误信封。** 换向量模型的二次确认响应必须 `code=0` + `success=true`：前端请求层见到非零 `code` 会直接 reject，`requiresConfirmation` 分支根本走不到，用户只会看到"切换失败"。业务字段和信封是两层，别混在一个 `code` 上表达。
