# 知识库

从"配一套存储"到"模型能把资料翻出来"的完整链路：存储模型、索引与隔离、召回与融合、摄取与切片、以及管控台上那些数字到底怎么算。

> **v2 起知识体是数据实体**：唯一 slug、创建时冻结的索引、两路检索落点 + 原文落点、文档归它。
> 域只是绑定它的消费者；删域只解绑，不动原文与索引。设计取舍见
> [`15-知识库v2设计稿.md`](15-知识库v2设计稿.md)。

## 1. 存储模型：三层，别混

```
Connection（连接：连哪台机器）
   ↑ 被引用
KnowledgeBody（知识体：一份数据 = 唯一名 + 冻结索引 + 两路检索落点 + 原文落点）
   ↑ 被绑定（一个域绑一个体；多个域可绑同一个体）
Domain（域：谁用它检索）
```

### Connection

| 字段 | 说明 |
| --- | --- |
| `id` / `name` | 命名实例，页面上的那两列 |
| `type` | `elasticsearch` / `qdrant`（`SUPPORTED_TYPES`） |
| `usage` | 归属段：画在哪张表（2-1 / 2-2），以及知识体的槽下拉能不能选到它。**不参与检索判定** |
| `es{host,port,scheme,username,password,connectTimeout,socketTimeout}` | ES 用 |
| `vector{uri,token,collectionPrefix,metric}` | Qdrant 用 |

Qdrant 连接的填法（镜像部署即开箱可用，服务端无需预建任何东西——集合在首次写入时按需 `PUT` 创建，已存在返回 409 视为成功）：

| 字段 | 填什么 |
| --- | --- |
| `uri` | `http://<host>:6333`，**只到端口**。带 `/dashboard` 之类的后缀会让根响应变成 HTML |
| `token` | 未设 `QDRANT__SERVICE__API_KEY` 时留空；设了才填同一个值 |
| `collectionPrefix` | 留空；多套环境共用一个 Qdrant 时才用来加前缀 |
| `metric` | `cosine`（默认）/ `dot` / `euclid`，**一旦集合建好就不能改**，改了要么重灌要么新建集合 |

端口别填错：`6333` 是 REST（本客户端走这个），`6334` 是 gRPC。`6333` 不通时先确认容器端口映射（`-p 6333:6333`）与防火墙。

去重看 `location()` = 协议 + 主机 + 端口（**不含账号**）。同一个物理实例配两次、换了账号，会被认成同一处。

### KnowledgeBody

| 字段 | 取值 |
| --- | --- |
| `id` / `name` | 标识与展示名 |
| `keyword` | 一条 connection id 或空 |
| `vector` | 一条 connection id 或空 |

**每个槽最多一条连接，不做同槽多路扇出。** "多"体现在"多个连接 / 多个知识体"，不在单个槽里。这条限制让"这一路查在哪"永远只有一个答案。

能力约束（<b>只在「测试连接」与真正检索时体现，保存不拦</b>——保存只负责把配置如实落盘，类型对不对要连上后端才知道）：

| 槽 | 约定的类型 | 违约后果 |
| --- | --- | --- |
| `keyword` | ES（BM25 + ik 分词是 ES 方言） | 检索时该路被 `backendFor` 跳过并留错误日志，关键字召回静默缺失 |
| `vector` | ES 或 Qdrant | 同上，向量召回静默缺失 |

两槽都配 = 混合召回；只配一路 = 单路；一路坏只跳过那一路，不整块失效。

**槽下拉只列"本段"的连接。** 连接的 `usage`（`keyword` / `vector`）决定它画在 2-1 还是 2-2，也决定它能被哪个槽选中：关键字段配的 ES 不会出现在向量下拉里，反之亦然。默认值按类型给（ES → 关键字段、Qdrant → 向量段），老配置没有该字段时也走这个默认。

同一台 ES 想两槽都用，就在两张表各加一条（**同地址、不同 id**）：

| 做法 | 结果 |
| --- | --- |
| 关键字段配 `es-main`，向量段配 `es-main-vec`（同地址） | 两个 id、同一台 → `location()` 相同 → 写入只落一次，不会双写 |
| 只配一条连接、两槽都填它 | 老配置仍可读（下拉会把已选中的那条保留下来并标注"属于关键字段"），但新配置在界面上做不出来 |

**两槽可以绑任意两台连接**，包括"关键字绑 ES-A、向量绑另一台 ES-B"：

| 两槽指向 | 写入 | 读取 | 检索 |
| --- | --- | --- | --- |
| 同一台（`location()` 相同） | 只写一次（按物理地址归并，不是按 id） | 直接读那台 | 两路查同一个索引 |
| 两台不同 ES | 扇出两份 | 逐台合并（见下） | 两路各查各的索引 |
| 一台 ES + 一台 Qdrant | 扇出两份 | 逐台合并 | ES 走 BM25、Qdrant 走 kNN |

**两台不同时，读路径必须逐台合并。** 切片在两台各写一份，"有哪些文档、有几片"这几种读法各有自己的口径（`FanOutStore` 统一负责）：

| 读法 | 口径 | 为什么 |
| --- | --- | --- |
| 文档列表 / 全量扫描 | 两台按 `doc_id` **取并集** | 另一台可能持有它没有的文档（换过知识体、单台上传失败过）。只看一台就是"看着空、其实有" |
| 集合名 | **并集** | 同上 |
| 切片数 / 文档切片数 | 两台**取最大值**，不求和 | 双写会让同一份切片两台各一份，求和就是翻倍；取最大值在单台时与旧行为逐字一致 |
| 按 docId 读回切片 | 关键字那台先答，空则问另一台 | 归档与预览读的是"真正入库的切片" |
| 去重 | **只问关键字那台** | 问两台会把"另一台上恰好有同内容"也算成重复，反而漏灌 |
| 维度 / 探活 | 关键字那台优先 | 维度由唯一的向量模型决定，任何一台给出的值都一样 |

只部署了 Qdrant 时，`keyword` 槽仍只能填 ES，所以知识体只能是"向量单路"（`keyword` 留空）。代价是没有 BM25 关键词兜底，查询里的精确编号、专有名词命中率会低一些——这是取舍不是故障。

### 域绑定

`DomainStore.bodyOf(domain)` 纯查表，**不继承**。没绑 → 该域不检索，也不下发检索工具。

### yaml 与管控台怎么合并

一条规则就够：

| 情形 | 生效配置 |
| --- | --- |
| 管控台配过任何连接（`connections` 非空） | 完全以管控台为准 |
| 管控台一条都没配 | 用 yaml 的 `domainplane.knowledge.backends` 合成一个默认连接 + 默认知识体 |

为什么不逐条合并：那样"删掉一条连接"会变成删不掉（yaml 里那条又冒出来），用户永远说不清表里那行到底是谁的。开关式口径只有一个方向。

`topK` 这类参数不跟着搬家，仍在 yaml 里按**连接 id** 配：

```yaml
domainplane.knowledge.backends:
  es-main:                     # ← 与管控台里的连接 id 对齐
    vector:  { topK: 30, minScore: 0.35 }
    keyword: { topK: 20, minimumShouldMatch: "50%" }
```

找不到就看 `DEFAULT_BACKEND_ID` 声明的那份，再找不到回落到废弃兼容键 `retrieval.vector-top-k` / `keyword-top-k`。

## 2. 索引与隔离

### 一体一索引

```
domainplane_kb_<知识体 slug>_<bodyId 的 SHA-256 前 8 位>
```

例：slug `sales`、体 `kb-1` → `domainplane_kb_sales_1a2b3c4d`

- 名字由**知识体的唯一名（slug）**派生，**在创建体时算好并写进配置**（`KnowledgeBody.index`）：
  之后改名、改展示名、换连接、换域绑定都不改索引名。
- 改名不搬数据，是这条设计的核心收益：索引名一旦冻结，文档、切片原文、向量都在原地。
- 哈希后缀防两件事：slug 撞名不可能（slug 全局唯一），但不同体被删后重建同名仍需区分历史集合，
  以及将来 slug 规则放宽后的截断撞名。
- 老版本按域路径生成的 `domainplane_kb_<域路径>_<hash>` 由 `KnowledgeLegacyMigrator`
  **原样登记**为一个知识体（索引名不改、数据不动、slug 由域路径安全化），启动时自动完成、幂等。
- 代价：名字人不可读。排障靠 `GET /admin/bodies`（含每个体的 `index` / `existsIndex` / 计数）。

### 隔离为什么成立

检索请求只带 `collection + query + topK`，**不带域字段过滤条件**。隔离在物理层就完成了：

- 查错体 → 查的是另一个索引 → 查不到（而不是"查到别人的"）。
- 多个域绑同一个知识体 → **查的是同一个索引**：这是"共用一份资料"的正确形态，不是隔离失效。
  反过来，一个域只绑一个体（D2），所以"这个域查到哪份数据"永远只有一个答案。
- 同一个体被 A、B 两个域共用时，A 域删掉不影响 B 域：删域只删 `domains.json` 里的绑定。

唯一跨域读的两种情况：域链（祖先域绑的体，沿链累加）与未绑域的通配检索（`domainplane_kb_*`）。

### 切片原文

```
BlobStore: kb/chunks/{indexName}/{docId}.json
```

- 原文档案是**权威源**（切片 JSON，剥掉向量）；索引是可重建的派生数据。
  换后端、换向量模型、换落点 = 从原文重建，不是数据迁移。
- 档案按**冻结的索引名**分目录，所以"改名 / 改绑定"不会让档案变成孤儿。
- **删域不删档案**：删域只解绑。`ChunkArchiveReconciler` 遇到"集合不在了"只 WARN，
  绝不删档案——原文的生命周期不再被派生数据反控。
- 删体时才动档案，且由 `DELETE /admin/bodies/{id}?keepRaw=` 决定去留（默认建议保留）。

## 3. 换落点

一份数据落在哪台机器上，可以改——但**不能直接改指针**。指针一改，检索立刻去查新连接，
而新连接上还没有集合，表现是"知识突然全没了"，旧连接上的数据既不会被查也不会被清理。

### 唯一入口

```
PUT /admin/bodies/{id}/routes?dryRun=true   → 预演（只读）
PUT /admin/bodies/{id}/routes                → 执行
{ "kind": "keyword" | "vector", "connection": "es-text02" }
```

`PUT /admin/bodies/{id}` 只改名字 / 说明 / 原文落点；带上不同的连接 id 会被**直接拒**
（`rejectRouteChange`），避免绕过迁移把指针切到一个空集合。

### 执行顺序

```
1) 从原文档案全量捞回该体切片（对账 → 读 archive；archive 全失才 scan 兜底）
2) 目标连接 ping + 必要时删掉上次迁移中断留下的同名集合
3) ensureCollection(冻结索引名, 当前维度)
4) 写入：vector 路重算向量；keyword 路直接写（不 embed）
5) 校验写入条数 == 捞回条数，不等就中止（原落点一个字没动）
6) 切指针（落盘 keyword / vector 字段），索引名不变
```

顺序里第 5 步是关键：**数据写完、条数对上，才切指针**。所以迁移期间检索照常走旧连接，
不存在"重建期间不可用"的窗口——索引名固定，新旧两台可以短暂并存同名集合。

### 三条边界

- **旧集合不删**：响应里 `legacyConnection` 说明旧连接 id，页面提示"同名集合保留未删"。
  删除是运维动作（旧机器上可能还有别的项目在用），而且删错了就没有回退依据。
- **keyword 路通常不重算向量**：档案里的切片本来就剥了向量，keyword 查询也不需要它。
  唯一的例外是目标连接正好与**另一路**同机（`location()` 相同）——那时两条路共用一个集合，
  写成无向量会把另一路的向量抹掉，所以退回重算。
- **原文落点不在这一版**：`SUPPORTED_RAW_LOCATIONS` 目前只有 `local`，传别的值直接拒，
  页面也只渲染白名单里的项（不做假下拉）。对象存储要等 `BlobStore` 多驱动。

### 预演说什么

`dryRun=true` 不读全量档案（几万片要几十秒），只回：文档数、有档文档数、
缺档数（这些迁不过去）、是否要重算向量、模型维度、目标上已有集合的维度、以及 `ready` 与
不能迁的原因。判据与执行路径同源（`KnowledgeBaseService.planRoute` / `migrateRoute`），
所以"预演说能迁"就等于"执行不会被配置拒"。

### 健康：三方维度对照

`GET /admin/bodies/{id}/health` 给每个体一张矩阵：关键字 mapping 维度、向量集合维度、
当前模型原生维度。三者不一致正是"探测全绿、检索报错"最常见的原因——换过向量模型却没重建，
维度不同的向量混在一个索引里，检索不报错、只静默失真。单独一个端点是因为每一格都要连远程，
塞进列表接口会把知识库首屏拖成秒级。

## 4. 召回链路

```
模型调 searchKnowledge
  → KnowledgeSearchService（拼注入文本）
  → CompositeRetriever（并发跑通道 + 融合）
  → RetrievalPlan.channels        ← 这里决定"查哪几个索引、每路查多少"
  → FusionStrategy
  → 取前 injectTopN(8) 片，总字符 ≤ 3000
```

### 检索域怎么算

`RetrievalPlan.channels`：对域 D 与它的每一个祖先域，各开 1~2 条通道（该域绑定的知识体有几路可用就开几条）。

```
查询 default.customer.aftersale
  ├─ default.customer.aftersale   depth 0   体 A（向量 + 关键字）
  ├─ default.customer             depth 1   体 B（关键字）
  └─ default                      depth 2   未绑 → 不开通道
```

**召回沿链向上，不向下**：子域的文档父域查不到。这条与"域是隔离单元"一致——父域不该看见子域的资料。

`depth` 只在 RRF 融合时参与层级衰减（`ancestor-decay` 默认 0.7，距离每远一层乘一次）。分数制融合忽略 depth。

### 融合：两种算法，自动选

`AdaptiveFusionStrategy`：

| 条件 | 用哪个 | 原因 |
| --- | --- | --- |
| 有命中的来源数 ≥ 2 | RRF | 跨索引/跨路的分数不可比，只信排名 |
| 只有 1 个来源 | 分数制 | 单一后端内部分数可比，保留区分度 |

分数制：min-max 归一化后按 `vector-weight=0.6` / `keyword-weight=0.4` 加权。**不承诺落在 [0,1]**——压到 0-1 会让"分数制"与"RRF"在边界处静默漂移。

两路共有的加成：标题命中 ×(1+0.15)、文件名命中 ×(1+0.10)。是**乘法增益**，不是加分——加分在分数尺度不同的后端上不可移植。

### 关键字那一路的阈值

`minimumShouldMatch` 的有效区间是 **40%~50%**：

- `ik_smart` 把"会员退款的时效说明"切成 5 个词（助词"的"也占额度），60% 会要求命中 3 个词，正常问题被打成零命中。
- 30% 及以下等于没限制。

这是后端方言，不要凭直觉调大。

## 5. 摄取

### 支持格式与解析器

| 后缀 | 解析器 | 能拿到什么 |
| --- | --- | --- |
| `txt` | `TxtSplitter` | 靠正则猜结构 |
| `md` / `markdown` | `MarkdownReader` | 标题层级 |
| `docx` | POI `DocxReader` | 标题层级 + 表格 |
| `doc` | POI `DocReader`（HWPF） | 同上（旧二进制） |
| `pdf` | PDFBox `PdfReader` | 文本 + 字号 + 页码 |
| `xls` / `xlsx` | POI `ExcelReader` | 行/列 |

不做的事：不推断字号标题、不还原跨页表格、不处理双栏、不做扫描件 OCR。

### 统一中间形态：Block

```java
Block(kind, level, text, pageNo)
```

`kind` 区分标题/正文/表格等，`level` 是标题层级，`pageNo` 用于回指。切片只看 Block 序列，不关心原始格式——所以加一种格式只需要一个"解析器 → Block 流"。

### 切片

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `chunking.max-chars` | 400 | **长度上限**，不是固定长度：撞到标题就提前断 |
| `chunking.overlap-sentences` | 1 | 相邻片重叠句数 |
| `chunking.min-chars` | 60 | 低于此值并入前一片 |
| `semantic-enabled` | `false` | 语义分块开关 |
| `semantic-similarity-threshold` | 0.6 | 相邻句余弦低于此值断片 |
| `semantic-min-sentences` | 2 | 语义分块最小句数 |

结构感知切片的顺序是：标题先切小节 → 小节内按句子累积到 `max-chars` → 太短的并入前一片。语义分块是在这个基础上再切：小节内部按句子嵌入的相邻余弦切分，**需要向量模型可用，不可用时自动退回结构感知**，导入不中断。

### 限制

| 限制 | 值 | 在哪拦 |
| --- | --- | --- |
| 单文件大小 | 5MB | 容器层 `multipart.max-file-size` + 业务层同值校验（两处必须一致） |
| 单请求体 | 6MB | 含 boundary 与各 part 头，故略大于单文件 |
| 单文档切片数 | 2000 | `IngestLimits`，超限直接拒绝并提示拆分 |
| 扩展名白名单 | 8 种 | `rag.allowed-extensions` |

容器层与业务层的 5MB 必须一致：不一致时容器先拦，用户拿到的是一个与"文件太大"无关的 500，而不是 `60006`。

### 同步导入

上传接口是**同步阻塞**的：提交到摄取线程池后 `future.get()`，切片与向量化完成才返回。队列满即拒（`ingest-queue-capacity` 默认 16）。

为什么不做异步：管控台的语义是"传完就能查到"，异步会引入"文档存在但搜不到"的中间态，而前端拿不到进度。代价是大文件会让请求挂很久——所以有 5MB / 2000 片这两道上限。

### 上传的前置依赖：向量模型

导入链路每一片都要向量化（不只是 `vector` 策略——`keyword` 后端也照算，切片带向量落库），所以**向量模型没配时上传一律被前置拒绝**：`60009 KNOWLEDGE_EMBEDDING_NOT_CONFIGURED`。它的对外文案直接点名"知识库还没有配置向量模型"，`detail` 给出该去哪一页补哪几项；`retryable=false`，原样重发不会变好。

这道前置检查不是为了省一次请求，而是不让错误长在最后一步：模型没配时解析、切片、去重全都白跑，最后在向量化那一步炸成 `60002`（5xx，`detail` 被隐藏），用户只看到一句"文档没能导入"——现场就有人把它读成了"文件格式不对，换一种格式试试"。

管控台「知识库」页把同一条判据放进了上传预检（`/admin/kb/target` 的 `embeddingReady`）：没配模型时上传按钮直接不可点，原因写着"未配置向量模型"，并给出「去模型设置」的跳转。预检与 `upload()` 的拒绝顺序一一对齐：域已登记 → 绑了体 → 体可用 → 向量模型可用 → 能解析出写入落点。

### 去重与覆盖

| 情形 | 行为 |
| --- | --- |
| 同内容（内容哈希相同） | 命中 `DedupLookup`，不重复入库 |
| 同文件名、不同内容 | `60005 KNOWLEDGE_DOCUMENT_DUPLICATE`，提示改名或 `replace=true` |
| `replace=true` | 先写新、确认落库后才删旧（写成"只删不写"比"新旧并存"更糟）；删旧失败只记日志、两份都留 |

### 落盘产物

| 产物 | 位置 | 用途 |
| --- | --- | --- |
| 切片原文 | `BlobStore: kb/chunks/{indexName}/{docId}.json` | 权威源，可重灌；也是管控台「看文档」的数据源 |
| 切片预览 | `export.path/{...}.txt` | 给"用编辑器跟原文对着看"的场景；页面上的「查看」走下面的在线预览，不必去服务器找文件 |
| 索引 | ES / Qdrant | 派生数据 |

管控台「已入库文档」每行的「查看」= 在线切片预览（`GET /admin/kb/documents/{docId}/chunks`）：优先读原文档案（本地 BlobStore，一次往返都不用发），档案缺失再回落到索引读，并在弹层里标明"来源：原文档案 / 索引现读（档案缺失）"。列表里的「切片文件」列仍是导出路径，点一下复制。

`ChunkArchiveReconciler` 每 5 分钟对账一次（护栏：对象年龄 < 5 分钟不处理，避免撞上"刚写完还没登记"的窗口）。

## 6. 换向量模型：三个入口，别混

| 操作 | 干什么 | 什么时候用 |
| --- | --- | --- |
| 重灌（rebuild） | 用新模型重新向量化全部切片 | 换模型且维度不同，必须做 |
| 重建索引（reindex，`/admin/kb/reindex`） | 从切片原文把内容搬到**指定的目标后端**（可换后端 / 换向量模型后重建），维度只能取当前生效的向量模型 | 换了索引 mapping / 分词器，或想把数据搬到另一台存储 |
| 清空（purge） | 只清索引与档案，文档记录保留 | 想从零开始 |

管控台在换向量模型时提供"重灌 / 清空"两个选择，**不静默重算**。原因：向量化的成本与失败面都很大，静默重算意味着一次保存动作触发几小时的后台任务，用户还不知道。

维度变化会被上游拒绝，所以保存模型档案时若维度变了，接口会提示需要重建。

## 7. 管控台上的数字怎么算

知识库页与域空间页的数字来自同一个服务（`KnowledgeStatsService`），三个口径**不要混**：

| 口径 | 含义 | 用在哪 |
| --- | --- | --- |
| 归属本域 | 只算该域自己的索引 | 文档表的"归属域"列 |
| 含子域 | 该域 + 全部子孙 | 删域预演（会删掉多少） |
| **可检索** | 该域 + **已绑体的祖先域** | 域卡片主数字 |

主数字用"可检索"，是为了和 `RetrievalPlan.channels` 同口径——卡片上写 12 篇，模型就真能查到这 12 篇。体总量是基础设施视角（一个体可被多个域共用），只在 `domainCount > 1` 时作附注"体共 N"。

### 时效与熔断

| 机制 | 值 |
| --- | --- |
| 结果缓存 | 60s |
| 失败冷却 | 300s（刻意比 TTL 长，否则永远轮不到它生效） |
| 冷却期内行为 | 复用旧快照，不发远程调用 |

**熔断只对"会抛"的后端有效**：`listCollections()` 是 fail-open 的（catch 后返回空），存储黑洞在统计层表现为"索引为空"而不是异常，进不了熔断。对这类后端能兜住的只有 TTL——每分钟最多烧一次 connectTimeout。要真熔断得让存储层把失败抛出来，那是另一件事。

### 页面必须"先出骨架、再补数"

域空间页的树与开关是纯内存（`/admin/domains`），知识库数字单独走 `/admin/kb/stats`。前端不能把两者放进同一个 `Promise.all`——那等于没拆，慢的那个会把整页拖住。

### 两个「看文档」不是一回事

| 位置 | 做什么 | 数据来源 |
| --- | --- | --- |
| 知识体行的「看文档」 | 把下方文档表的「知识体」筛选设成它，滚到那张表，并回一条提示（几篇 / 为什么 0 篇） | 已有的文档清单（`/admin/kb/documents`）+ 绑定关系 |
| 文档行的「查看」 | 打开切片预览弹层，逐片看正文 | `GET /admin/kb/documents/{docId}/chunks`（档案优先，缺档回落索引） |

知识体行的按钮只能"筛选"，因为文档归属是**推算**出来的（域绑了哪个体，文档就归哪个体）——体没绑域时它名下必然 0 篇，页面必须把这句话说出来，否则用户只会看到"点了没反应"。

## 8. 常见故障对照

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `60007 KNOWLEDGE_BACKEND_MISCONFIGURED` | **装配召回计划时**：绑定指向了不存在的 / 能力不够的知识体（保存不再做能力校验，类型不对也是到这一步才暴露） | 补齐槽位，或把策略改为 `keyword` / `vector` |
| `60000 KNOWLEDGE_BASE_ERROR` | 存储链路故障（连不上、超时、ensureCollection 失败） | 查连接可用性；持续失败看 ES/Qdrant 侧 |
| 上传报 `60000`，日志里是 Qdrant `400 ... untagged enum VectorsConfig` | 旧版本把 `distance` 按配置的小写词表（`cosine`）直接发给 Qdrant，而它的枚举只认 `Cosine / Dot / Euclid`（已修） | 升级到含该修复的版本；无需改配置 |
| 上传报 `60002`，日志里是 `20015 The parameter is invalid` | 旧版本把「向量维度」当请求参数 `dimensions` 下发，而固定维度模型（如 SiliconFlow 的 `bge-m3`）直接拒绝该参数（已改为不下发） | 升级；「维度」只按模型原生维度填（`bge-m3` = 1024） |
| 上传报 `60002`，detail 说「实际返回 N 维，配置的是 M 维」 | 管控台填的维度不是该模型的原生维度；索引按填的值建，写入必然被拒 | 到「模型设置」把该向量模型的维度改成实测值 N，已入库的域再重建索引 |
| ~~`60008 KNOWLEDGE_STORE_UNAVAILABLE`~~ | 枚举里有定义，**全仓无抛点** | 遇到存储故障看到的是 `60000`，不是 60008 |
| 检索永远空 | 域没绑知识体，或绑的体此刻不可用（两路空着 / 连接没填地址）——绑定只落盘不校验，这两种都不报错、只是不开通道 | 域空间页给该域绑体；体的问题去「存储配置」补连接，补好后自动生效 |
| 上传报 `60009` | 向量模型没配（导入链路每片都要向量化） | 到「模型设置」页的「向量模型」段启用 Embedding 模型 |
| 上传报 `60006` | 扩展名不在白名单 / 超 5MB | 换格式或拆分 |
| 上传报 `60005` | 同名文档已存在 | 改名或 `replace=true` |
| 换模型后检索报错 | 维度不一致，索引要重灌 | 重灌 |
| 文档数一直是 0 | `listCollections` fail-open 吞了故障 | 看服务端日志里的 ES 连接错误 |
| 探活提示"未读到版本号" | 地址带了路径后缀（如 `.../dashboard`），根响应不是 JSON；或该地址不是 Qdrant | 连接 URL 只填 `http://host:6333`，不带尾部路径 |
| 探活集合数恒为 0 但库里明明有 | `collectionPrefix` 与实际不符 | 集合名只由域路径派生（见 §2），手建的集合不会被认到 |
| 知识库页（知识体 / 已入库文档）加载要 30 秒左右，刷新第二次又很快 | 旧版 Qdrant 适配器每翻一页都多发一个 `limit:1` 的"探针"请求读 `next_page_offset`，且探针带的是**旧** offset——服务端回的游标不代表"本页之后还有下一页"，翻页原地打转，扫满页面上限才停（8 个切片扫了 125 页、约 250 次往返、29 秒）；warm 快是因为 60s 快照缓存兜住了 | 升级到游标随页返回的版本；服务端日志会打 `[知识库] 慢操作：读取索引[...]的文档列表（后端 QdrantKnowledgeStore）耗时 ... ms`，再出现就按这条日志查哪台后端慢 |

## 9. 踩过的坑

**知识体不继承，但召回沿域链累加。** 这两件事经常被混：子域不会借用父域的知识体（写读落在哪），但子域能查到父域索引里的文档（允许看什么）。前者是为了防"文档写错库"，后者是为了"父域提供公共资料"。

**`usage` 字段不参与检索判定，但它决定谁能选它。** 检索侧只看槽位指向哪条连接，不看 `usage`；但管控台的槽下拉按 `usage` 分流——关键字段配的 ES 不会出现在向量下拉，向量段配的 Qdrant 不会出现在关键字下拉。所以"我在关键字段配了一台 ES，向量下拉里却看到它"是旧版本的取向（只按类型过滤），现在不会了。要在两个槽都用同一台 ES，就在两张表各加一条同地址连接。

**槽下拉会保留"当前已选中的那条"，即使它不属于本段。** 这是为了兼容老配置（一条连接被两槽共用）：直接过滤掉的话，下拉会回落到空值，用户点一次保存就静默丢了一路。这种条目在选项里带 `· 属于关键字段` 标注。

**`minimumShouldMatch` 调大会把正常问题打成零命中。** 有效区间 40%~50%，见 §3。

**翻页游标必须和本页数据一起拿回来。** Qdrant scroll 的 `result.next_page_offset` 就在响应里；为读它再发一次请求，不仅把每页的往返翻倍，更致命的是那次请求带的是**旧** offset——它回答的是"从旧位置的下一个点开始还有没有下一页"，而不是"本页之后还有没有下一页"。于是下一页的游标总会非空，循环原地打转直到 `scanned` 触顶。实测 8 个切片的集合扫了 125 页、约 250 次跨网往返、29 秒，正好等于管控台"知识库页加载慢"的体感。这类 bug 有一个很迷惑的特征：**第二次刷新很快**——60 秒快照缓存把上一次的慢结果兜住了，看上去像"偶发网络抖动"。只读链路另外配了慢操作日志（`[知识库] 慢操作：... 耗时 N ms`，阈值 1.5s），把"哪台后端、哪个索引、多久"直接打出来，省掉靠 jstack 猜的过程。

**同槽多路是做不到的。** 一个槽只能绑一条连接，不做同槽扇出。要"两套 ES 都查"有两条路：开两个知识体各绑一个域（不同域查不同库），或者一条连接绑一个槽、另一条绑另一个槽（同域双写双查，见 §1）。

**索引名与域路径是单向的。** 能从域算出索引名，不能从索引名可靠反推域（截断 + 哈希）。反查要走 `/admin/kb/stats`。

**Qdrant 的响应包装不统一。** 除根端点 `GET /` 外，其余端点都在 `result` 里（`result.collections`、`result.config.params.vectors.size`、`result.points`、`result.count`）；根端点直接返回 `{title, version, commit}`。把它当同类端点解析，结局就是"连接正常但读不到版本号"——探测本身假装失败，最容易把人引到"我是不是部署错了"上去。
