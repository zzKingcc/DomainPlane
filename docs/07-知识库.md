# 知识库

从"配一套存储"到"模型能把资料翻出来"的完整链路：存储模型、索引与隔离、召回与融合、摄取与切片、以及管控台上那些数字到底怎么算。

---

## 1. 存储模型：三层，别混

```
Connection（连接：连哪台机器）
   ↑ 被引用
KnowledgeBody（知识体：一个检索用途，两个槽）
   ↑ 被绑定
Domain（域：谁用它检索）
```

### Connection

| 字段 | 说明 |
| --- | --- |
| `id` / `name` | 命名实例，页面上的那两列 |
| `type` | `elasticsearch` / `qdrant`（`SUPPORTED_TYPES`） |
| `usage` | 只决定"画在哪张表"，**不参与检索判定** |
| `es{host,port,scheme,username,password,connectTimeout,socketTimeout}` | ES 用 |
| `vector{uri,token,collectionPrefix,metric}` | Qdrant 用 |

去重看 `location()` = 协议 + 主机 + 端口（**不含账号**）。同一个物理实例配两次、换了账号，会被认成同一处。

### KnowledgeBody

| 字段 | 取值 |
| --- | --- |
| `id` / `name` | 标识与展示名 |
| `keyword` | 一条 connection id 或空 |
| `vector` | 一条 connection id 或空 |

**每个槽最多一条连接，不做同槽多路扇出。** "多"体现在"多个连接 / 多个知识体"，不在单个槽里。这条限制让"这一路查在哪"永远只有一个答案。

能力硬校验（保存配置时就拦）：

| 槽 | 允许的类型 |
| --- | --- |
| `keyword` | 仅 `elasticsearch`（BM25 + ik 分词是 ES 方言） |
| `vector` | `elasticsearch` 或 `qdrant` |

两槽都配 = 混合召回；只配一路 = 单路；一路坏只跳过那一路，不整块失效。

### 域绑定

`DomainStore.bodyOf(domain)` 纯查表，**不继承**。没绑 → 该域不检索，也不下发检索工具。

### yaml 与管控台怎么合并

一条规则就够：

| 情形 | 生效配置 |
| --- | --- |
| 管控台配过任何连接（`connections` 非空） | 完全以管控台为准 |
| 管控台一条都没配 | 用 yaml 的 `domainplane.knowledge.backends` 合成一个默认连接 + 默认知识体 |

为什么不逐条合并：那样"删掉一条连接"会变成删不掉（yaml 里那条又冒出来），用户永远说不清表里那行到底是谁的。开关式口径只有一个方向。

`topK` 这类参数不跟着搬家，仍在 yaml 里按**连接 id** 配：

```yaml
domainplane.knowledge.backends:
  es-main:                     # ← 与管控台里的连接 id 对齐
    vector:  { topK: 30, minScore: 0.35 }
    keyword: { topK: 20, minimumShouldMatch: "50%" }
```

找不到就看 `DEFAULT_BACKEND_ID` 声明的那份，再找不到回落到废弃兼容键 `retrieval.vector-top-k` / `keyword-top-k`。

## 2. 索引与隔离

### 一域一索引

```
domainplane_kb_<域路径小写安全化，≤80>_<SHA-256 前 8 位>
```

例：`default.customer.aftersale` → `domainplane_kb_default_customer_aftersale_a1b2c3d4`

- 名字由域路径**确定性派生**，同一个域在任何时候算出来都一样。
- 哈希后缀防两件事：安全化后撞名（`a.b` 与 `a_b`）、超长截断后撞名。
- 代价：名字人不可读。排障要靠 `GET /admin/kb/stats` 的索引视图，不能靠肉眼认。

### 隔离为什么成立

检索请求只带 `collection + query + topK`，**不带域字段过滤条件**。隔离在物理层就完成了：

- 查错域 → 查的是另一个索引 → 查不到（而不是"查到别人的"）。
- 同一知识体被多个域共用 → 各域在同一个集群上各占各的索引，互不干扰。

唯一跨域读的两种情况：域链（祖先的索引）与未绑域的通配检索（`domainplane_kb_*`）。

### 切片原文

```
BlobStore: kb/chunks/{indexName}/{docId}.json
```

写入前**剥离向量**——原文是权威源，索引是可重建的派生数据。换后端或换向量模型 = 一次重灌，不是数据迁移。

删域时按 `kb/chunks/{indexName}/` 前缀清，不碰别人的目录。

## 3. 召回链路

```
模型调 searchKnowledge
  → KnowledgeSearchService（拼注入文本）
  → CompositeRetriever（并发跑通道 + 融合）
  → RetrievalPlan.channels        ← 这里决定"查哪几个索引、每路查多少"
  → FusionStrategy
  → 取前 injectTopN(8) 片，总字符 ≤ 3000
```

### 检索域怎么算

`RetrievalPlan.channels`：对域 D 与它的每一个祖先域，各开 1~2 条通道（该域绑定的知识体有几路可用就开几条）。

```
查询 default.customer.aftersale
  ├─ default.customer.aftersale   depth 0   体 A（向量 + 关键字）
  ├─ default.customer             depth 1   体 B（关键字）
  └─ default                      depth 2   未绑 → 不开通道
```

**召回沿链向上，不向下**：子域的文档父域查不到。这条与"域是隔离单元"一致——父域不该看见子域的资料。

`depth` 只在 RRF 融合时参与层级衰减（`ancestor-decay` 默认 0.7，距离每远一层乘一次）。分数制融合忽略 depth。

### 融合：两种算法，自动选

`AdaptiveFusionStrategy`：

| 条件 | 用哪个 | 原因 |
| --- | --- | --- |
| 有命中的来源数 ≥ 2 | RRF | 跨索引/跨路的分数不可比，只信排名 |
| 只有 1 个来源 | 分数制 | 单一后端内部分数可比，保留区分度 |

分数制：min-max 归一化后按 `vector-weight=0.6` / `keyword-weight=0.4` 加权。**不承诺落在 [0,1]**——压到 0-1 会让"分数制"与"RRF"在边界处静默漂移。

两路共有的加成：标题命中 ×(1+0.15)、文件名命中 ×(1+0.10)。是**乘法增益**，不是加分——加分在分数尺度不同的后端上不可移植。

### 关键字那一路的阈值

`minimumShouldMatch` 的有效区间是 **40%~50%**：

- `ik_smart` 把"会员退款的时效说明"切成 5 个词（助词"的"也占额度），60% 会要求命中 3 个词，正常问题被打成零命中。
- 30% 及以下等于没限制。

这是后端方言，不要凭直觉调大。

## 4. 摄取

### 支持格式与解析器

| 后缀 | 解析器 | 能拿到什么 |
| --- | --- | --- |
| `txt` | `TxtSplitter` | 靠正则猜结构 |
| `md` / `markdown` | `MarkdownReader` | 标题层级 |
| `docx` | POI `DocxReader` | 标题层级 + 表格 |
| `doc` | POI `DocReader`（HWPF） | 同上（旧二进制） |
| `pdf` | PDFBox `PdfReader` | 文本 + 字号 + 页码 |
| `xls` / `xlsx` | POI `ExcelReader` | 行/列 |

不做的事：不推断字号标题、不还原跨页表格、不处理双栏、不做扫描件 OCR。

### 统一中间形态：Block

```java
Block(kind, level, text, pageNo)
```

`kind` 区分标题/正文/表格等，`level` 是标题层级，`pageNo` 用于回指。切片只看 Block 序列，不关心原始格式——所以加一种格式只需要一个"解析器 → Block 流"。

### 切片

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `chunking.max-chars` | 400 | **长度上限**，不是固定长度：撞到标题就提前断 |
| `chunking.overlap-sentences` | 1 | 相邻片重叠句数 |
| `chunking.min-chars` | 60 | 低于此值并入前一片 |
| `semantic-enabled` | `false` | 语义分块开关 |
| `semantic-similarity-threshold` | 0.6 | 相邻句余弦低于此值断片 |
| `semantic-min-sentences` | 2 | 语义分块最小句数 |

结构感知切片的顺序是：标题先切小节 → 小节内按句子累积到 `max-chars` → 太短的并入前一片。语义分块是在这个基础上再切：小节内部按句子嵌入的相邻余弦切分，**需要向量模型可用，不可用时自动退回结构感知**，导入不中断。

### 限制

| 限制 | 值 | 在哪拦 |
| --- | --- | --- |
| 单文件大小 | 5MB | 容器层 `multipart.max-file-size` + 业务层同值校验（两处必须一致） |
| 单请求体 | 6MB | 含 boundary 与各 part 头，故略大于单文件 |
| 单文档切片数 | 2000 | `IngestLimits`，超限直接拒绝并提示拆分 |
| 扩展名白名单 | 8 种 | `rag.allowed-extensions` |

容器层与业务层的 5MB 必须一致：不一致时容器先拦，用户拿到的是一个与"文件太大"无关的 500，而不是 `60006`。

### 同步导入

上传接口是**同步阻塞**的：提交到摄取线程池后 `future.get()`，切片与向量化完成才返回。队列满即拒（`ingest-queue-capacity` 默认 16）。

为什么不做异步：管控台的语义是"传完就能查到"，异步会引入"文档存在但搜不到"的中间态，而前端拿不到进度。代价是大文件会让请求挂很久——所以有 5MB / 2000 片这两道上限。

### 去重与覆盖

| 情形 | 行为 |
| --- | --- |
| 同内容（内容哈希相同） | 命中 `DedupLookup`，不重复入库 |
| 同文件名、不同内容 | `60005 KNOWLEDGE_DOCUMENT_DUPLICATE`，提示改名或 `replace=true` |
| `replace=true` | 覆盖更新，旧切片先清 |

### 落盘产物

| 产物 | 位置 | 用途 |
| --- | --- | --- |
| 切片原文 | `BlobStore: kb/chunks/{indexName}/{docId}.json` | 权威源，可重灌 |
| 切片预览 | `export.path/{...}.txt` | 管控台只展示路径，不提供在线查看 |
| 索引 | ES / Qdrant | 派生数据 |

`ChunkArchiveReconciler` 每 5 分钟对账一次（护栏：对象年龄 < 5 分钟不处理，避免撞上"刚写完还没登记"的窗口）。

## 5. 换向量模型：三个入口，别混

| 操作 | 干什么 | 什么时候用 |
| --- | --- | --- |
| 重灌（rebuild） | 用新模型重新向量化全部切片 | 换模型且维度不同，必须做 |
| 重建索引（reindex） | 重建索引结构，切片不动 | 换了索引 mapping / 分词器 |
| 清空（purge） | 只清索引与档案，文档记录保留 | 想从零开始 |

管控台在换向量模型时提供"重灌 / 清空"两个选择，**不静默重算**。原因：向量化的成本与失败面都很大，静默重算意味着一次保存动作触发几小时的后台任务，用户还不知道。

维度变化会被上游拒绝，所以保存模型档案时若维度变了，接口会提示需要重建。

## 6. 管控台上的数字怎么算

知识库页与域空间页的数字来自同一个服务（`KnowledgeStatsService`），三个口径**不要混**：

| 口径 | 含义 | 用在哪 |
| --- | --- | --- |
| 归属本域 | 只算该域自己的索引 | 文档表的"归属域"列 |
| 含子域 | 该域 + 全部子孙 | 删域预演（会删掉多少） |
| **可检索** | 该域 + **已绑体的祖先域** | 域卡片主数字 |

主数字用"可检索"，是为了和 `RetrievalPlan.channels` 同口径——卡片上写 12 篇，模型就真能查到这 12 篇。体总量是基础设施视角（一个体可被多个域共用），只在 `domainCount > 1` 时作附注"体共 N"。

### 时效与熔断

| 机制 | 值 |
| --- | --- |
| 结果缓存 | 60s |
| 失败冷却 | 300s（刻意比 TTL 长，否则永远轮不到它生效） |
| 冷却期内行为 | 复用旧快照，不发远程调用 |

**熔断只对"会抛"的后端有效**：`listCollections()` 是 fail-open 的（catch 后返回空），存储黑洞在统计层表现为"索引为空"而不是异常，进不了熔断。对这类后端能兜住的只有 TTL——每分钟最多烧一次 connectTimeout。要真熔断得让存储层把失败抛出来，那是另一件事。

### 页面必须"先出骨架、再补数"

域空间页的树与开关是纯内存（`/admin/domains`），知识库数字单独走 `/admin/kb/stats`。前端不能把两者放进同一个 `Promise.all`——那等于没拆，慢的那个会把整页拖住。

## 7. 常见故障对照

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| `60007 KNOWLEDGE_BACKEND_MISCONFIGURED` | 策略要求两路，但知识体只配了一路；或关键字槽配了 Qdrant | 补齐槽位，或把策略改为 `keyword` / `vector` |
| `60008 KNOWLEDGE_STORE_UNAVAILABLE` | 存储链路故障（连不上、超时） | 查连接可用性；持续失败看 ES/Qdrant 侧 |
| 检索永远空 | 域没绑知识体（不报错、只是不开通道） | 域空间页给该域绑体 |
| 上传报 `60006` | 扩展名不在白名单 / 超 5MB | 换格式或拆分 |
| 上传报 `60005` | 同名文档已存在 | 改名或 `replace=true` |
| 换模型后检索报错 | 维度不一致，索引要重灌 | 重灌 |
| 文档数一直是 0 | `listCollections` fail-open 吞了故障 | 看服务端日志里的 ES 连接错误 |

## 8. 踩过的坑

**知识体不继承，但召回沿域链累加。** 这两件事经常被混：子域不会借用父域的知识体（写读落在哪），但子域能查到父域索引里的文档（允许看什么）。前者是为了防"文档写错库"，后者是为了"父域提供公共资料"。

**`usage` 字段不参与检索判定。** 它只是页面分表的依据；把一条连接标成 `vector` 用途但被关键字槽引用，保存时会被能力校验拦下，而不是运行期静默失败。

**`minimumShouldMatch` 调大会把正常问题打成零命中。** 有效区间 40%~50%，见 §3。

**同槽多路是做不到的。** 要"两套 ES 都查"，得开两个知识体、绑两个域，或者换一个能覆盖两处的索引——不支持单槽扇出。

**索引名与域路径是单向的。** 能从域算出索引名，不能从索引名可靠反推域（截断 + 哈希）。反查要走 `/admin/kb/stats`。
